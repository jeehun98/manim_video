# GPU 계층 구조 LEVEL 03 — Block 상세 영상화 콘티

총 178초 (2분 58초) · 9:16 세로 쇼츠 · CUDA 소스코드 연동형

이번 영상의 핵심은 Warp 여러 개가 하나의 Block에 속하고, Shared Memory와 동기화를 이용해 하나의 결과를 만들어내는 과정이야.

1편의 Thread, 2편의 Warp와 같은 GPU 구조도를 유지하되, 이번에는 Block 전체가 강조되는 연출로 확장해.

주 화면은 Block과 Warp 구조. 코드 패널은 현재 장면과 관련된 코드만 보여주는 보조 영역으로 구성.

### 고정할 제작 규칙

- GPU → SM → Block → Warp → Thread의 위치와 색상은 기존 영상과 동일하게 유지.
- Block 0 안에 128 Thread = 4 Warp를 표시.
- 선택한 Thread 번호와 색상을 데이터 이동 및 계산 장면까지 유지.
- CUDA 코드에는 줄 번호를 넣지 않고, 테두리·배경을 분리해 가독성 확보.
- 코드는 장면별로 2\~6줄만 발췌하고 글자를 크게 표시.
- Shared Memory는 각 Warp에 하나씩 배치하지 않고, Block 전체가 공유하는 하나의 공간으로 표현.
- 128개의 데이터를 모두 펼쳐야 할 때는 축약해서 표현하되, 실제 연산 대상이 128개라는 정보는 계속 유지.

## 2. 영상에서 사용할 CUDA 소스코드

시각화와 실제 코드가 대응되려면 전체 예제가 일관되어야 해.

```

__global__ void blockSum(
    const float* input,
    float* output
) {
    __shared__ float s[128];

    int t = threadIdx.x;

    s[t] = input[t];
    __syncthreads();

    for (int stride = 64;
         stride > 0;
         stride >>= 1) {

        if (t < stride) {
            s[t] += s[t + stride];
        }

        __syncthreads();
    }

    if (t == 0) {
        output[0] = s[0];
    }
}

// 128 threads, one block
blockSum<<<1, 128>>>(d_input, d_output);

```

128개 float 원소를 하나의 Block으로 더하는 교육용 커널. 입력·출력 GPU 메모리는 미리 준비해야 하며, 여러 Block을 사용하는 일반적인 Reduction 구현은 아니야.

이 커널에서는 4개의 Warp가 동일한 Shared Memory 배열을 이용해 최종 합계 하나를 계산해.

## 3. 초 단위 상세 콘티

### SCENE 01 — Warp에서 Block으로 확장 (0\~34초)

0\~12초

문제 제기와 Block 등장

2편에서 사용한 Warp 0의 32 Thread 화면으로 시작해. 카메라가 줌아웃되면서 Warp 1, Warp 2, Warp 3이 나타나고, 이들을 둘러싸는 Block 0 외곽선을 강조해.

화면 텍스트: `Warp 0 + Warp 1 + Warp 2 + Warp 3 → Block 0`

12\~28초 — Block의 크기

4개 Warp가 각각 32 Thread임을 표시하고, `4 × 32 = 128 Threads` 계산식을 잠시 나타내.

CUDA 코드 패널에는 다음 실행 설정을 표시해.

```
blockSum<<<1, 128>>>(d_input, d_output);
```

128이라는 숫자에 하이라이트를 넣고 Block 내부 128개 Thread 전체에 연결선을 그어.

28\~34초 — Block 크기를 변경할 수 있다

128개 Thread 화면을 잠깐 64개, 256개 Thread 배치 예시와 비교해.

단, 뒤에서 실제 실행하는 Reduction 예제는 128 Thread 기준이므로 다시 128개로 복귀시켜.

### SCENE 03 — Shared Memory 기록 (60\~77초)

여기서부터 CUDA 코드와 실제 데이터 이동을 본격적으로 연결해.

Shared Memory — Block 내부 공유 공간

```
__shared__ float s[128];

int t = threadIdx.x;
s[t] = input[t];
```

60\~67초: `__shared__ float s[128]`에 하이라이트를 넣는 순간 하나의 메모리 영역이 Block 아래 나타나.

67\~73초: `s[t] = input[t]`를 강조하고, 각 Thread의 입력값이 공유 배열의 각 위치에 기록되는 애니메이션을 보여줘.

73\~77초: `s[0]`부터 `s[127]`까지 값이 채워진 상태를 표시해.

Shared Memory 영역은 Block 카드 안에 그리되, 엄밀히는 해당 Block이 실행 중인 SM의 Shared Memory 자원을 사용한다는 점을 작은 라벨로 표시하면 좋아.

### SCENE 04 — 동기화가 필요한 이유 (77\~102초)

89\~97초 — `__syncthreads()` 등장

코드 패널을 아래 한 줄로 전환하고 화면 중앙에 동기화 장벽을 나타내.

```
__syncthreads();
```

네 Warp가 동기화 지점에 도달하는 모습과, 먼저 도달한 스레드들이 다른 스레드들을 기다리는 상황을 연출해.

97\~102초 — 기록의 가시성 확보

모든 참여 스레드가 장벽에 도달한 뒤 Shared Memory의 값이 다음 계산에 사용 가능한 상태가 돼.

시각화에서는 장벽이 사라지면서 공유 메모리의 128개 값이 모두 강조되게 해.

주의: `__syncthreads()`는 모든 스레드를 같은 하드웨어 명령 사이클에 맞추는 기능이 아니야. 블록 내부 실행 장벽과 메모리 순서 보장이 핵심이야.

### SCENE 05 — Reduction: 128개 값을 하나로 (102\~127초)

이번 영상에서 가장 역동적인 장면이 될 수 있어.

공유 메모리의 배열을 유지한 채, 코드의 `stride`가 줄어들 때마다 합산 대상도 절반씩 감소하도록 만들어.

```
for (int stride = 64;
     stride > 0;
     stride >>= 1) {

    if (t < stride) {
        s[t] += s[t + stride];
    }

    __syncthreads();
}
```

### SCENE 06 — 서로 다른 Warp의 협력 (127\~135초)

이 부분에서는 앞선 Reduction 장면을 다시 Block 전체 관점에서 보여줘.

4개의 Warp가 입력 배열의 서로 다른 32개 원소를 담당하고, 모두 동일한 Shared Memory 배열에 접근하는 모습을 표시해.

127\~131초: Warp별로 저장된 32개 원소 영역을 네 가지 색조로 구분.

131\~135초: Reduction의 첫 단계에서 `s[0]`과 `s[64]`처럼 서로 다른 Warp가 처음 기록했던 값들이 하나의 부분 합계로 합쳐지는 장면을 확대해.

같은 Shared Memory를 사용하기 때문에 Warp 경계를 넘어 데이터가 합쳐질 수 있다는 사실을 보여주는 거야.

이 장면은 Warp가 서로 직접 데이터를 전송한다는 의미가 아니라, 같은 Block의 Shared Memory를 통해 기록된 값을 읽는다는 의미로 연출해.

### SCENE 07 — Block이 실제 하드웨어에서 배치되는 위치 (135\~158초)

이제 GPU 구조도를 다시 확대하면서 Block이 어디에서 실행되는지 보여주는 장면이야.

Block을 SM에 배치하는 개념도. 한 SM에 여러 Block이 동시에 상주할 수 있는지는 사용 가능한 하드웨어 자원에 따라 달라져.

135\~139초 — 위치에 대한 질문

전체 Block 화면에서 줌아웃해 GPU와 여러 SM이 보이도록 전환해.

139\~143초 — SM에 배치

기존 Block 0이 SM 0 내부에 배치되는 모습을 보여줘.

이때 Block 전체가 하나의 SM에 배치된다는 사실을 강조해야 해. 한 Block의 Warp들을 여러 SM에 흩어 놓는 방식으로 표현하지 않아야 해.

143\~148초 — 실행 자원 사용

SM 내부의 `Warp Scheduler`, `Register File`, `Shared Memory`를 표시해.

Block 0의 Warp들은 SM의 스케줄러에 의해 실행되고, 필요한 Register와 Shared Memory 자원을 사용한다고 설명해.

단, SM 전체 구조에 대한 상세한 설명은 다음 편으로 남겨둬.

148\~152초 — 동기화 범위

서로 다른 Block 두 개를 보여주고, Block 0의 `__syncthreads()`가 Block 1까지 영향을 미치지 않는다는 사실을 표현해.

152\~158초 — Block의 독립성

각 Block이 자체적인 스레드 그룹과 공유 메모리 영역을 갖도록 표시해.

동일한 SM에 배치된 서로 다른 Block도 일반적인 `__shared__` 배열을 서로 공유하지 않는다는 점을 작은 문구로 강조하면 좋아.

## 5. 1·2편과의 영상화 일관성

이번 편도 이전에 확정한 방식을 그대로 적용하면 돼.

- GPU 구조가 메인: GPU, SM, Block, Warp의 위치와 색상 유지.
- 코드 패널은 보조: 테두리와 배경을 분리하고, 줄 번호 없이 필요한 코드만 크게 발췌.
- 스레드 식별 유지: 선택된 Thread의 번호와 색상을 입력값, Shared Memory 주소, 계산 결과까지 연결.
- Block 전체 강조: Warp마다 독립적인 공유 메모리가 있는 것처럼 그리지 않고 Block 하나가 같은 Shared Memory를 사용하도록 표현.
- 이전 구조 재사용: 1편의 Thread, 2편의 Warp 모델을 새로 만들지 않고 Block 내부 구성 요소로 그대로 활용.

### 가장 중요한 연출: 89\~127초

이번 3편은 `__syncthreads()`에서 멈춘 스레드들이 동기화를 완료하고, Shared Memory의 128개 값이 Reduction을 통해 하나로 합쳐지는 과정이 중심이야.

특히 Reduction에서 활성 스레드 수가 감소해도 Block 자체의 스레드 수는 계속 128개라는 점을 시각적으로 구분해야 해.

이 장면이 정확하게 구현되면 시청자는 Block을 단순한 스레드 묶음이 아니라, 여러 Warp에 속한 스레드들이 메모리와 동기화를 활용해 하나의 계산을 완성하는 협력 단위로 이해할 수 있을 거야.
