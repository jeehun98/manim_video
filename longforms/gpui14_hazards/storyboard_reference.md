GPU 개론 14 — 데이터가 준비되지 않았다면 프로세서는 어떻게 할까?
상세 영상화 콘티 · 9:16 세로형 · Manim 기반 2D 모션그래픽 · 시간 지정 제외

이번 영상은 13편에서 완성한 파이프라인 구조를 그대로 이어받아, 명령어들이 서로 다른 회로에서 동시에 진행될 수 있더라도, 필요한 데이터가 아직 준비되지 않았다면 올바른 계산을 보장할 수 없다는 문제를 보여주는 것이 핵심이야.

시청자가 이해해야 하는 내용은 세 가지야.
1. 문제 발생: 다음 명령어가 이전 명령어의 결과를 너무 일찍 사용하려 한다.
2. 첫 번째 해결: 결과가 준비되지 않았다면 진행을 멈춘다 — Stall.
3. 두 번째 해결: 결과가 이미 만들어졌다면 레지스터에 기록될 때까지 기다리지 않고 직접 전달한다 — Forwarding.
가장 중요한 것은 Stall과 Forwarding을 서로 다른 최적화 기법처럼 독립적으로 소개하지 않는 거야. 하나의 문제를 해결하는 과정에서 기다림이 필요하고, 다시 그 기다림을 줄이기 위한 새로운 경로가 필요해지는 순서로 만들어야 해.
영상의 기본 구조
이번 영상에서는 13편의 명령어 인출·주소 결정·데이터 읽기·결과 기록 구조를 확장해, ALU 연산과 메모리 접근을 명확히 구분한 교육용 5단계 파이프라인을 사용해.
5단계 파이프라인

각 단계는 IF(명령어 인출), ID(명령어 해독 및 레지스터 읽기), EX(ALU 연산 또는 주소 계산), MEM(데이터 메모리 접근), WB(결과 기록)을 의미해.

13편의 단계를 그대로 유지하려고 Load와 ADD가 실제로 다른 일을 하는 부분을 생략하기보다는, ALU와 메모리 접근을 분리한 구조로 자연스럽게 확장하는 것이 정확해.

시각적 색상은 기존 회로 분류와 별개로 다음처럼 통일해.
요소	표현
배경	짙은 남색 #0B1020
명령어 A	파란색 #60A5FA
명령어 B	보라색 #A78BFA
새롭게 추가하는 회로	초록색 #34D399
제어 신호·대기 상태	주황색 #F59E0B
위험한 입력 사용	빨간색 #EF4444
비활성 회로	회색 #64748B

화면에 등장하는 명령어와 숫자는 최소한으로 제한해.

첫 번째 예시는 다음과 같아.
LOAD R1, [100]    Memory[100] = 5
ADD  R3, R1, R2   R2 = 3


처음 R1은 0이라고 가정해. 기대하는 결과는 R3 = 8이야.

두 번째 예시는 ALU 결과를 직접 전달할 수 있다는 사실을 보여주기 위해 사용해.
ADD R3, R1, R2
SUB R4, R3, R5



SCENE 1. 이전 영상의 파이프라인을 불러온다
대응 나레이션
앞서 우리는 서로 다른 명령어가 프로세서 내부의 여러 회로를 동시에 사용하도록 만들었습니다.

그런데 모든 명령어를 이렇게 겹쳐 실행할 수 있을까요?

화면 구성
화면 중앙에 13편에서 완성한 파이프라인 구조를 배치해.

서로 다른 두 명령어 카드 A, B가 각각 다른 단계에 있는 모습을 보여줘.

처음에는 두 명령어 모두 서로 독립적인 작업을 수행해.

예를 들어 LOAD R1, [100]과 LOAD R2, [101]이야.

파이프라인의 단계가 진행되면서 A와 B가 동시에 다음 단계로 이동해.
애니메이션
A와 B의 정보를 담은 카드가 클럭 에지마다 다음 단계로 이동해.

각 단계의 회로가 활성화되는 모습을 짧게 보여준 뒤 정상적으로 R1과 R2가 갱신돼.

여기까지는 13편의 내용이야.

이후 두 번째 명령어 B가 화면에서 사라지고, 새로운 ADD 명령어가 들어와.

ADD R3, R1, R2

A에서 B로 향하는 얇은 연결선을 그려.

이 연결선은 앞선 결과를 다음 명령어가 필요로 한다는 관계를 나타내.

화면 중앙에 다음 질문을 표시해.

다음 명령어가 이전 결과를 사용한다면?
연출 의도
이번 영상의 주제는 두 명령어가 동시에 실행되는 것 자체가 아니야.

동시에 실행되는 명령어들 사이에 데이터 관계가 존재한다는 것이야.

이 관계를 시작부터 시각적으로 분명히 보여줘야 해.

SCENE 2. 첫 번째 명령어가 아직 값을 가져오지 않았다
대응 나레이션
첫 번째 명령어가 메모리에서 숫자 5를 가져와 첫 번째 레지스터에 저장한다고 생각해 보겠습니다.

그리고 두 번째 명령어는 이 값에 3을 더해야 합니다.

화면 구성
복잡한 회로도를 잠시 제거해.

화면 중앙에는 데이터 메모리와 레지스터, ALU만 배치해.

명령어 A는 파란색, B는 보라색으로 표시해.

애니메이션
먼저 메모리의 주소 100을 강조해.

그 안에는 숫자 5가 존재해.

그러나 R1에는 이전 값인 0이 저장되어 있어.

다음으로 ALU를 강조해.

ALU는 R1과 R2를 입력받을 예정이야.

R2는 3이고, R1의 새로운 값은 5여야 한다는 사실을 보여줘.

여기서는 아직 잘못된 계산을 진행하지 않아. 시청자가 먼저 입력값들의 관계를 이해하도록 해.

SCENE 3. 두 번째 명령어가 너무 일찍 값을 읽는다
대응 나레이션
하지만 첫 번째 명령어가 아직 데이터를 가져오는 중이라면 어떨까요?

두 번째 명령어는 새로운 값 5가 아닌, 이전에 저장된 값으로 계산할 수도 있습니다.

문제는 계산에 필요한 값이 아직 준비되지 않았다는 것입니다.

화면 구성
두 명령어의 파이프라인 진행 상태를 보여줘.

A는 메모리 데이터를 읽는 중이야.

B는 앞선 명령어의 결과인 R1을 이용해 계산하려 하고 있어.
애니메이션
첫 번째 장면에서는 A의 메모리 접근을 보여줘.

Memory[100] → 5

하지만 아직 A의 결과가 목적지 레지스터에 기록되지 않았어.

그 상태에서 B가 기존 레지스터 파일의 R1을 읽어.

현재 R1에는 0이 저장되어 있어.

B의 ALU 입력이 다음처럼 바뀌어.

0 + 3

결과가 3으로 나타나려는 순간 동작을 정지해.

기대 결과와 현재 입력 상태를 나란히 보여줘.
너무 일찍 사용한 값
0 + 3 = 3
이전 R1 사용


필요한 값
5 + 3 = 8
새로운 R1 사용




중요한 연출
ALU 자체에 빨간색 경고 표시를 붙이지 않아.

ALU는 전달받은 숫자 0과 3을 정상적으로 더하고 있기 때문이야.

대신 ALU에 들어가는 R1 입력선을 붉게 표시해.

문제의 원인이 계산 회로의 오류가 아니라, 입력 데이터의 준비 시점이라는 사실을 전달해야 해.

SCENE 4. 두 명령어가 사용하는 레지스터 번호를 비교한다
대응 나레이션
그렇다면 프로세서는 이를 어떻게 확인할까요?

앞서 우리는 명령어를 해독해 어느 레지스터를 읽고, 어디에 결과를 기록할지 결정했습니다.

이 정보를 비교하면 됩니다.

앞선 명령어가 결과를 기록할 레지스터와 다음 명령어가 읽으려는 레지스터가 같은지 확인하는 것입니다.

화면 구성
명령어 두 개를 중앙에 크게 배치해.

LOAD R1, [100]

ADD R3, R1, R2

그다음 전체 명령어에서 레지스터 번호만 분리해.

애니메이션
A의 목적지 R1이 명령어에서 분리돼 작은 레지스터 번호 블록으로 이동해.

B의 입력 R1도 같은 방식으로 분리돼.

두 번호가 비교 논리로 전달돼.

비교 결과 MATCH = 1이 출력돼.

여기에서 비교 결과가 같다는 사실만으로 바로 대기시키지 않아.

다음으로 앞선 결과가 아직 필요한 시점에 준비되지 않았는지를 함께 확인해야 한다는 점을 표현해.

이번 편의 제어 회로는 다음 조건을 판단하는 것으로 단순화해.

레지스터 의존성 존재 + 결과 사용 시점에 데이터 미준비

이 조건이 참이면 다음 명령어의 진행을 지연시켜.

SCENE 5. 필요한 값이 없다면 진행을 멈춘다
대응 나레이션
그리고 필요한 값이 아직 준비되지 않았다면, 다음 명령어의 진행을 잠시 멈춥니다.

이를 위해 레지스터의 갱신을 제어하고, 다음 단계로 새로운 연산이 진행되지 않도록 할 수 있습니다.

이처럼 실행을 일시적으로 지연시키는 동작을 Stall이라고 합니다.

화면 구성
파이프라인 전체로 돌아와.

이번에는 새로운 제어 논리 블록을 작게 추가해.

Dependency Check

여기에서 주황색 제어선이 PC와 IF/ID 레지스터의 갱신 제어 입력으로 연결돼.

또 ID/EX 단계에는 실제 연산 대신 빈 동작을 전달할 수 있도록 제어 경로가 추가돼.
애니메이션
처음에 A는 EX 단계에 있고, B는 ID 단계에 있어.

A는 Load 명령어이므로 이후 MEM 단계에서 데이터를 읽어야 해.

B는 R1을 사용해야 하므로 지금 EX로 이동시키면 필요한 값을 사용할 수 없어.

의존성 검사 회로가 이를 감지해.

다음 클럭 경계에서 A는 MEM으로 이동해.

B는 ID에 그대로 유지돼.

그리고 EX에는 B 대신 아무 결과도 기록하지 않는 빈 동작을 전달해.

이를 작은 BUBBLE 표시로 나타내.

이때 PC도 갱신되지 않아 뒤따르는 명령어의 인출 상태가 유지돼.
핵심 시각화
Load-use 의존성에서 발생하는 한 번의 대기
명령어	1	2	3	4	5	6	7	8
LOAD A	IF	ID	EX	MEM	WB	·	·	·
ADD B	·	IF	ID	ID	EX	MEM	WB	·

B가 ID에 한 사이클 더 머무르고, EX에는 버블이 들어간다. 이후 A의 메모리 결과를 B의 EX 단계로 전달할 수 있다고 가정한 예시다.
용어 등장
먼저 실제로 B의 진행이 멈추는 장면을 보여줘.

그다음 화면 가운데에 짧게 표시해.

SCENE 6. 결과가 이미 존재한다면 꼭 기다려야 할까?
대응 나레이션
그런데 반드시 결과가 레지스터에 기록될 때까지 기다려야 할까요?

이번에는 첫 번째 명령어가 덧셈을 수행하고, 두 번째 명령어가 그 결과로 뺄셈을 수행한다고 생각해 보겠습니다.

화면 구성
Stall을 보여주었던 회로에서 확대를 해제해.

기존 두 명령어를 제거하고, 새로운 두 명령어를 화면 중앙에 배치해.
ADD R3, R1, R2
SUB R4, R3, R5


예시 값을 R1 = 5, R2 = 3, R5 = 2로 설정해.

따라서 첫 번째 명령어의 결과는 8이고, 두 번째 명령어의 결과는 6이야.
애니메이션
첫 번째 명령어가 ALU에서 덧셈을 수행해.

5 + 3 → 8

계산이 끝나면 결과 8이 ALU 출력에 나타나.

이 값은 EX/MEM 파이프라인 레지스터에 저장돼.

하지만 아직 R3에는 기록되지 않았어.

두 번째 명령어가 R3를 사용하려는 모습을 보여줘.

여기서 화면을 정지하고, 두 위치를 동시에 강조해.
ALU 계산 결과
8
이미 준비됨


Register R3
0
아직 갱신 전




핵심 연출
시청자는 다음 사실을 확인해야 해.

계산 결과 8은 이미 존재하지만, 목적지 레지스터 R3에는 아직 기록되지 않았다.

기존의 방법대로라면 R3가 갱신될 때까지 기다릴 수 있겠지만, 이미 만들어진 8을 직접 활용할 수도 있다는 새로운 가능성을 보여주는 거야.

이 장면에서는 아직 새 연결을 추가하지 않아.

SCENE 7. 이미 계산한 결과를 다음 ALU로 직접 전달한다
대응 나레이션
첫 번째 명령어의 ALU 계산이 끝났다면 결과값은 이미 만들어져 있습니다.

아직 목적지 레지스터에 기록되지 않았을 뿐입니다.

그렇다면 이 값을 다음 ALU로 직접 전달하면 어떨까요?

앞선 연산 결과가 보관된 경로에서 다음 ALU의 입력으로 연결을 추가하는 것입니다.

화면 구성
프로세서 전체에서 다음 부분만 확대해.
- ALU
- EX/MEM 파이프라인 레지스터
- 레지스터 파일
- ALU 입력 경로
처음에는 기존 데이터 경로만 보여줘.

ALU → 결과 저장 → WB → Register File

이후 EX/MEM 레지스터의 출력에서 다음 명령어가 사용할 ALU 입력 쪽으로 새로운 연결선을 그려.
새 경로 추가 애니메이션
동일한 ALU를 서로 다른 클럭에 사용하는 개념도. 화면의 두 ALU 표기는 서로 다른 명령어의 사용 시점을 나타내며, ALU 두 개를 추가했다는 뜻은 아니다.
세부 애니메이션
먼저 ALU 결과 8이 EX/MEM 레지스터에 저장돼.

그 결과에서 새로운 초록색 배선이 뻗어나가.

배선은 ALU의 입력 선택 회로 앞까지 연결돼.

이때 아직 SUB 명령어의 연산은 시작하지 않아.
