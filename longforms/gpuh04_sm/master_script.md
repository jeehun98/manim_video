# SM — 확정 대본 / 사용자 제공 178초

0–5초

GPU에서는 여러 스레드가 블록을 구성하고, 블록 내부의 스레드들은 워프 단위로 명령을 실행합니다.

5–10초

그렇다면 이러한 블록과 워프는 실제 GPU 하드웨어의 어디에서 실행될까요?

10–13초

바로 SM, Streaming Multiprocessor입니다.

13–19초

SM은 GPU에서 스레드들의 명령을 실제로 실행하는 핵심 하드웨어 장치입니다.

19–21초

하나의 SM을 살펴보겠습니다.

21–29초

SM 내부에는 명령을 실행하는 연산 유닛과 데이터를 저장하는 레지스터, 공유 메모리, 그리고 워프 스케줄러가 있습니다.

29–33초

CUDA에서 정의한 블록은 실행될 때 하나의 SM에 배치됩니다.

33–38초

그리고 해당 블록에 속한 워프들은 SM의 실행 자원을 사용합니다.

38–42초

SM에는 여러 블록이 동시에 배치될 수도 있습니다.

42–45초

그렇다면 SM은 수많은 워프의 명령을 어떻게 처리할까요?

45–48초

여기서 중요한 역할을 하는 것이 워프 스케줄러입니다.

48–52초

워프 스케줄러는 실행할 준비가 된 워프를 선택해 명령을 발행합니다.

52–55초

실제 CUDA 코드를 살펴보겠습니다.

55–60초

화면의 커널은 배열에서 값을 읽고, 두 배로 만든 다음, 결과를 저장하는 프로그램입니다.

60–63초

먼저 스레드는 메모리에서 자신의 데이터를 읽어옵니다.

63–66초

그리고 읽어온 값에 2를 곱해야 합니다.

66–70초

그런데 메모리에서 요청한 데이터가 아직 도착하지 않았다면 어떻게 될까요?

70–74초

해당 값을 필요로 하는 곱셈 명령은 바로 실행할 수 없습니다.

74–78초

이때 워프 전체의 계산이 끝날 때까지 SM이 멈추는 것은 아닙니다.

78–82초

워프 0이 데이터를 기다리고 있다고 가정해 보겠습니다.

82–86초

워프 스케줄러는 실행할 준비가 된 다른 워프를 선택할 수 있습니다.

86–90초

워프 1의 명령을 실행하고, 이후 워프 2의 명령을 실행하는 식입니다.

90–95초

그사이 워프 0이 요청한 데이터가 준비되면, 워프 0도 다시 계산을 진행할 수 있습니다.

95–103초

이처럼 한 워프가 기다리는 동안 다른 워프의 명령을 실행해 대기 시간을 숨기는 방식을 Latency Hiding이라고 합니다.

103–107초

그렇다면 SM에 워프를 많이 배치할수록 무조건 빠를까요?

107–108초

그렇지는 않습니다.

108–113초

SM이 사용할 수 있는 레지스터와 공유 메모리의 용량은 제한되어 있습니다.

113–119초

하나의 블록이 많은 레지스터나 공유 메모리를 사용하면, 동시에 배치할 수 있는 블록과 워프의 수가 줄어들 수 있습니다.

119–122초

여기서 등장하는 개념이 Occupancy입니다.

122–130초

Occupancy는 SM에 최대로 상주시킬 수 있는 워프 수에 비해, 실제로 몇 개의 워프가 상주하고 있는지를 나타내는 비율입니다.

130–134초

하지만 Occupancy가 높다고 반드시 실행 속도가 빠른 것은 아닙니다.

134–140초

이미 충분한 워프로 대기 시간을 숨기고 있다면, 워프를 더 늘려도 성능이 개선되지 않을 수 있습니다.

140–142초

한 가지 더 중요한 점이 있습니다.

142–149초

일반적인 CUDA 코드에서는 스레드와 블록의 개수를 지정할 수 있지만, 각 블록이 실행될 SM을 직접 지정하지는 않습니다.

149–154초

실제 블록의 배치는 GPU의 하드웨어 스케줄링에 의해 결정됩니다.

154–162초

결국 스레드는 개별 실행 문맥이고, 워프는 스레드들을 묶어 명령을 실행하는 단위이며, 블록은 스레드들이 협력하는 논리적인 그룹입니다.

162–169초

그리고 SM은 이러한 블록들을 배치받아 워프의 명령을 실제 하드웨어에서 실행하는 장치입니다.

169–178초

GPU의 높은 처리량은 단순히 연산 장치가 많기 때문만이 아니라, 여러 워프를 활용해 계산과 대기 시간을 효율적으로 관리하는 구조에서도 나옵니다.
