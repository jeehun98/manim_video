# GPU 개론 12 — 하나의 명령어를 실행하는 동안 무엇을 기억해야 할까?

상세 영상화 콘티 · 총 153초(2분 33초) · 9:16 세로 영상 · Manim 기반 2D 모션그래픽

이번 편은 11편에서 완성한 프로세서에 새로운 계산 장치를 추가하는 것이 아니라, 기존 장치가 여러 단계에 걸쳐 동작하도록 저장 회로와 제어 회로를 추가하는 과정이야.

시청자가 최종적으로 이해해야 하는 구조적 변화는 세 가지야.

1. 가져온 명령어를 계속 유지할 수 있도록 레지스터를 추가한다.
2. 중간 계산 결과를 다음 단계까지 보관할 레지스터를 추가한다.
3. 현재 실행 단계를 기억하고 제어 신호를 발생시키는 회로를 추가한다.

명칭은 반드시 기능을 먼저 시각화한 이후 등장시켜.

## 영상 전체의 시각적 구조

10\~12편의 프로세서 확장 흐름

10편 · 기본 명령어 실행

PC → 명령어 메모리 → 해독 → ALU → 레지스터

11편 · 메모리 데이터 접근

데이터 메모리 + Load/Store + 쓰기 경로 선택

12편 · 실행 도중의 정보 보관

명령어 보관 + 중간 결과 보관 + 단계별 제어

# ACT 1. 메모리에서 데이터가 도착하기 전, 무엇을 기억해야 할까?

00:00–00:43 · 이전 편 회로를 재사용해 새로운 문제를 보여준다.

### 00:00–00:05 — 기존 프로세서 복습

나레이션

앞서 우리는 메모리에 저장된 숫자를 가져와 계산하고, 다시 저장할 수 있는 프로세서를 만들었습니다.

화면 연출

11편 마지막의 프로세서 회로도를 그대로 보여줘.

화면 위쪽에는 PC, Instruction Memory, Decoder를 배치하고, 중간에는 Registers와 ALU, 아래쪽에는 Data Memory와 Writeback MUX를 배치해.

메모리에서 숫자 5를 읽어 R1에 저장하는 동작을 빠르게 보여준 뒤, 회로 전체를 다시 정지시켜.

화면 구성

- 상단: 명령어를 가져오는 구조
- 중앙: 레지스터와 ALU
- 하단: 데이터 메모리
- 강조: 11편에서 추가한 보라색 메모리 경로

새로운 명칭이나 구조는 아직 표시하지 않아.

### 00:05–00:10 — 메모리 읽기 과정을 확대

나레이션

그런데 메모리에서 데이터를 가져오는 과정을 조금 더 자세히 살펴보겠습니다.

화면 연출

전체 회로도가 부드럽게 확대되면서 데이터 메모리 주변으로 시선이 이동해.

나머지 회로는 축소하고, 화면 중앙에 다음 요소를 크게 배치해.

`명령어 → 주소 선택 → 메모리 읽기 → 레지스터 기록`

각 요소는 연결된 하나의 흐름으로 표현하지만, 아직 여러 클럭에 나뉜다고 설명하지 않아.

### 00:10–00:16 — 하나의 명령어 제시

나레이션

예를 들어 주소 100에 저장된 숫자 5를 첫 번째 레지스터로 가져온다고 생각해 보겠습니다.

화면 연출

화면 상단에 명령어가 등장해.

`LOAD R1, [100]`

메모리 배열에서는 주소 100의 위치를 강조해.

레지스터 영역에는 R1을 표시하고 초기값은 0으로 설정해.

Data Memory

100

5

Register R1

0

명령어의 목표는 Memory[100]의 5를 R1에 기록하는 것이다.

이 시점에는 R1의 값이 변하지 않아야 해.

### 00:16–00:22 — 명령어를 가져오고 해석한다

나레이션

프로세서는 먼저 명령어를 가져와, 메모리의 어느 위치에서 값을 읽고, 어디에 저장해야 하는지 확인합니다.

화면 연출

Instruction Memory에서 `LOAD R1, [100]`이 출력돼.

명령어는 Decoder로 전달되고, 다음 정보가 분리되어 표시돼.

동작

LOAD

주소

100

목적지

R1

여기서 세 정보는 명령어의 의미를 설명하기 위해 시각적으로 분리한 거야. 실제 비트 필드나 인코딩 형식은 표시하지 않아.

### 00:22–00:25 — 메모리 주소 전달

나레이션

그리고 메모리에 주소 100을 전달합니다.

화면 연출

앞서 분리한 주소 100이 데이터 메모리의 Address 입력으로 이동해.

주소 100의 저장 셀이 강조되고 읽기 요청이 활성화돼.

레지스터 R1은 아직 0을 유지해.

### 00:25–00:29 — 데이터가 아직 준비되지 않았다

나레이션

하지만 메모리에서 값을 읽어 오는 데에는 시간이 걸릴 수 있습니다.

화면 연출

메모리 주소 100은 선택되어 있지만 Read Data 출력에 바로 5를 보여주지 않아.

출력 부분에는 `Waiting` 또는 `Pending`을 표시해.

시간축을 짧게 보여줘.

`읽기 요청 → 데이터 준비 → 결과 전달`

단, 메모리를 오래 기다리는 장면으로 과장하지 말고, 요청 시점과 결과가 준비되는 시점이 다를 수 있다는 사실만 표현해.

### 00:29–00:33 — 목적지 정보를 잃어버린다면?

나레이션

그동안 프로세서는 숫자 5가 어디에 저장되어야 하는지 어떻게 기억할까요?

화면 연출

메모리 Read Data는 계속 `Pending` 상태로 둬.

목적지 R1을 표시하던 제어 신호를 강조해.

이어서 R1의 표시에 `?`를 겹쳐 보여줘.

여기서는 R1이 실제로 사라지는 것이 아니라, 결과가 도착했을 때 어떤 레지스터를 갱신할지 알고 있어야 한다는 문제를 시각화하는 거야.

### 00:33–00:39 — 다음 동작에서 입력이 바뀐다면?

나레이션

만약 다음 동작을 위해 회로의 입력이 바뀐다면, 이전 명령어의 정보까지 달라질 수 있습니다.

화면 연출

화면을 위아래로 나눠.

위쪽에는 명령어 메모리의 현재 출력을 보여줘.

`LOAD R1, [100]`

다음 명령어 주소를 선택하면서 출력이 다음 예시로 바뀌어.

`ADD R3, R1, R2`

아래쪽에는 앞선 LOAD가 아직 완료되지 않은 상태로 나타나.

`Memory Read = Pending`

`Destination = R1`

기존 명령어 메모리의 출력은 변경되었지만, LOAD에 필요한 목적지 R1은 그대로 유지되어야 한다는 사실을 대비해.

기술적 주의

이것은 명령어 메모리 출력을 계속 직접 참조하는 설계에서 발생할 수 있는 문제를 설명하는 가상 상황이야. 단순한 순차 실행 프로세서가 반드시 메모리 읽기 도중 다음 명령어를 가져와야 하는 것은 아니야.

또한 현재 LOAD가 완료되기 전에는 목적지 정보가 실제로 바뀌지 않도록 제어하는 설계도 가능해. 이번 영상에서는 그 정보를 별도 저장하는 방법을 구성하는 거야.

### 00:39–00:43 — 필요한 정보를 별도로 저장하자

나레이션

그렇다면 필요한 정보를 별도의 공간에 저장해 두면 어떨까요?

화면 연출

이전 LOAD 명령어에서 분리한 정보가 화면 중앙에 모여.

`LOAD`

`100`

`R1`

그 옆에 빈 저장 블록이 나타나.

필요한 정보들이 새 저장 블록 안으로 들어가고, 이후 입력 신호가 바뀌어도 블록 내부의 값들은 유지돼.

아직 명령어 레지스터라는 이름은 사용하지 않아.

# ACT 2. 기존 레지스터를 명령어 저장에도 사용한다

00:43–01:12 · 기존 회로의 재사용 → 명령어 보관 → 중간 계산 결과 보관

### 00:43–00:48 — 이전에 만든 저장 회로 재등장

나레이션

우리는 앞서 플립플롭을 조합해 여러 비트의 값을 저장하는 레지스터를 만들었습니다.

화면 연출

7\~8편에서 사용했던 플립플롭 구조를 간략하게 보여줘.

하나의 D 플립플롭이 1비트를 저장하고, 여러 플립플롭이 나란히 배치되며 다중 비트 레지스터를 형성하는 모습을 표현해.

이미 알고 있는 저장 회로

기존 회로를 그대로 사용한다는 인상을 주는 것이 중요해.

### 00:48–00:52 — 명령어 경로에 레지스터 추가

나레이션

이 회로를 명령어가 전달되는 경로에 하나 더 추가하는 것입니다.

화면 연출

프로세서 전체 구조로 복귀해.

기존 연결은 다음과 같아.

`Instruction Memory → Decoder`

이 두 블록 사이에 새 레지스터를 삽입해.

`Instruction Memory → [새 레지스터] → Decoder`

레지스터는 초록색으로 등장해.

입력에는 현재 명령어 `LOAD R1, [100]`이 연결되고, 유효한 클럭 에지에서 명령어가 저장돼.

### 00:52–00:57 — 입력이 바뀌어도 저장된 명령어는 유지된다

나레이션

이제 가져온 명령어를 별도로 저장하고, 필요한 동안 유지할 수 있습니다.

화면 연출

명령어 메모리의 출력이 ADD 명령어로 바뀌어.

하지만 새로 추가한 레지스터의 출력에는 여전히 `LOAD R1, [100]`이 남아 있어.

새 명령어가 메모리 출력에 나타나더라도 저장된 이전 명령어는 유지된다. 레지스터 갱신은 제어 신호에 의해 제한된다.

특히 저장 회로의 출력이 입력과 즉시 동일해지는 것처럼 표현하지 않도록 해.

저장값이 유지되는 동안 다음 명령어를 저장하려면 별도의 갱신 조건이 필요해.

### 00:57–01:01 — 명령어 레지스터라는 이름

나레이션

이렇게 현재 실행할 명령어를 보관하는 회로를 명령어 레지스터라고 합니다.

화면 연출

새로 추가한 레지스터 위에 명칭이 등장해.

`Instruction Register (IR)`

처음에는 `명령어 보관`이라는 한글 설명을 유지하고, 이어서 영어 명칭을 작은 글씨로 표시해.

명칭은 1\~2초만 강조한 뒤 회로의 일부로 남겨둬.

### 01:01–01:05 — 명령어 외의 값도 저장할 수 있다

나레이션

같은 방법으로 계산 과정에서 만들어진 값도 저장할 수 있습니다.

화면 연출

Instruction Register는 화면 상단에 유지해.

중앙의 ALU를 확대하면서 계산 결과 출력에 새로운 저장 회로가 들어갈 수 있는 위치를 보여줘.

초록색 레지스터 블록 하나가 ALU 출력 아래쪽에 등장해.

### 01:05–01:12 — 계산 결과를 다음 단계까지 유지

나레이션

예를 들어 ALU가 계산한 주소를 다음 과정에서도 사용해야 한다면, 그 값을 별도의 레지스터에 보관하는 것입니다.

화면 연출

이 구간에서는 `LOAD R1, [100]`과 같은 명령어를 유지하되, 주소를 계산하는 별도 예시를 잠깐 보여줘.

예를 들어 기존 주소 100에 4를 더하는 상황이야.

`100 + 4 = 104`

ALU 출력 104가 새 레지스터에 저장돼.

그다음 ALU 입력을 다른 값으로 변경하더라도 레지스터에는 104가 남아.

메모리는 저장된 104를 주소 입력으로 받아 읽기를 수행해.

이렇게 하면 명령어를 보관하는 회로와 계산 결과를 보관하는 회로가 같은 저장 원리를 사용한다는 점이 드러나.

여기서는 새로운 주소 계산 명령어를 별도로 정의하지 않고, ALU가 계산한 중간값을 보관하는 용도를 보여주는 정도로만 표현해.

# ACT 3. 현재 어떤 동작을 수행해야 할까?

01:12–01:59 · 정보를 저장하는 회로에서, 동작 순서를 결정하는 회로로 확장한다.

여기부터는 단순히 레지스터를 추가하는 것이 아니라 언제 어떤 장치가 동작해야 하는지 결정하는 구조를 만들어야 해.

시각적으로는 기존 데이터 경로 위에 새로운 제어 영역을 추가하는 방식이 좋아.

### 01:12–01:16 — 저장만으로는 충분하지 않다

나레이션

그런데 정보를 저장하는 것만으로는 아직 충분하지 않습니다.

화면 연출

화면 중앙에 지금까지 추가한 두 가지 저장 회로를 보여줘.

- 명령어를 저장하는 레지스터: `LOAD R1, [100]`
- 중간값을 저장하는 레지스터: `Address = 100`

오른쪽에는 ALU, Data Memory, Register File이 배치돼.

모두 필요한 정보는 가지고 있지만 어느 장치도 활성화되지 않은 상태야.

화면 상단에는 짧게 `무엇을 먼저 실행해야 할까?`라는 질문을 표시해.

연출 의도: 저장된 데이터가 있다는 것과 회로가 올바른 순서로 동작한다는 것은 별개의 문제임을 보여준다.

### 01:16–01:22 — 회로마다 동작해야 할 시점이 다르다

나레이션

프로세서는 언제 명령어를 가져오고, 언제 메모리에서 값을 읽고, 언제 레지스터에 기록해야 할까요?

화면 연출

기존 프로세서의 세 영역을 순서대로 강조해.

0\~2초: 명령어 메모리에서 명령어가 나와 저장되는 장면.

2\~4초: 데이터 메모리의 주소 입력과 읽기 제어가 활성화되는 장면.

4\~6초: 레지스터 쓰기 허용 신호가 활성화되는 장면.

세 동작은 빠른 시각화로 구분하되, 클럭 주기를 실제 초 단위 영상 시간과 일치시키지는 않아.

### 01:22–01:25 — 모든 회로가 동시에 같은 일을 하지는 않는다

나레이션

모든 회로가 매 순간 같은 동작을 수행하는 것은 아닙니다.

화면 연출

세 영역을 모두 표시한 상태에서 각 순간에 필요한 제어만 활성화해.

예를 들어 데이터 읽기 단계에서는 메모리 읽기 제어를 강조하고, 레지스터 쓰기 허용 신호는 비활성화된 상태로 보여줘.

그다음 결과 기록 단계에서는 레지스터 쓰기 제어가 활성화돼.

여기서 주의할 점은 비활성 회로를 전원이 꺼진 장치처럼 표현하지 않는 것이야. 조합 논리 회로의 출력은 계속 변할 수 있지만, 그 결과를 저장하거나 특정 동작을 수행하는 제어가 비활성일 수 있어.

### 01:25–01:28 — 현재 단계를 구분하는 방법

나레이션

따라서 현재 어떤 과정을 수행하고 있는지도 구분해야 합니다.

화면 연출

프로세서 왼쪽에 작은 빈 사각형 하나를 추가해.

그 안에 `현재 단계 = ?`를 표시해.

화면 상단에는 다음 네 가지 동작을 아주 작게 나열해.

`명령어 가져오기 / 주소 결정 / 데이터 읽기 / 결과 기록`

빈 사각형의 값을 바꾸면 어떤 장치가 활성화되는지 달라질 것이라는 인상을 주면 돼.

아직 FSM이라는 용어는 표시하지 않아.

### 01:28–01:32 — 첫 번째 상태: 명령어 인출

나레이션

예를 들어 첫 번째 상태에서는 명령어를 가져옵니다.

화면 연출

현재 단계 표시가 `00`으로 변경돼.

화면 오른쪽에서는 다음 동작이 진행돼.

`PC = 0 → Instruction Memory → LOAD R1, [100]`

명령어가 Instruction Register로 전달되고, 클럭 에지에서 저장돼.

제어 영역에는 `IR Write = 1`을 잠깐 표시해.

이와 함께 PC가 다음에 가져올 명령어를 가리키도록 갱신되는 모습을 보여줄 수 있어.

단, 명령어 레지스터는 이전 LOAD 명령어를 유지하고, PC는 다음 명령어 위치로 이동할 수 있다는 점을 구분해.

### 01:32–01:35 — 두 번째 상태: 주소 결정

나레이션

두 번째 상태에서는 필요한 주소를 결정합니다.

화면 연출

현재 단계가 `00 → 01`로 변경돼.

Instruction Register에 저장된 `LOAD R1, [100]`에서 주소 100이 선택돼.

주소 값이 데이터 메모리의 Address 입력으로 전달돼.

설명용 프로세서에서는 주소가 직접 명령어에 포함되어 있으므로 이 단계에서 별도의 덧셈은 필요하지 않아.

주소 100을 중간 주소 레지스터에 보관한 뒤 다음 단계에서 사용해도 돼.

### 01:35–01:38 — 세 번째 상태: 데이터 읽기

나레이션

세 번째 상태에서는 메모리에서 값을 읽습니다.

화면 연출

현재 단계가 `01 → 10`으로 변경돼.

Data Memory의 Address 입력은 100을 유지해.

읽기 제어가 활성화되고, 메모리 출력에서 5가 나타나.

읽은 데이터는 레지스터 파일에 바로 기록되지 않고, 다음 단계까지 유지될 수 있도록 임시 저장 레지스터로 전달돼.

이 장면에서는 `Memory Data Register`라는 명칭을 굳이 먼저 소개할 필요가 없어. 작은 초록색 저장 블록에 숫자 5가 보관되는 모습만 보여주면 충분해.

### 01:38–01:42 — 네 번째 상태: 결과 기록

나레이션

마지막 상태에서는 읽어 온 값을 레지스터에 기록합니다.

화면 연출

현재 단계가 `10 → 11`로 변경돼.

임시 저장 레지스터의 숫자 5가 Writeback MUX를 통해 레지스터 파일로 전달돼.

명령어 레지스터에 저장된 목적지 정보 R1을 강조해.

`Register Write = 1`이 활성화되고, 클럭 에지에서 R1이 `0 → 5`로 변경돼.

다음 상태로 이동하기 전, 다음과 같은 결과를 잠깐 보여줘.

`Memory[100] = 5`

`R1 = 5`

메모리의 값은 그대로 유지돼야 해.

### 01:42–01:46 — 다음 상태로 이동하는 규칙

나레이션

그리고 각 과정이 끝나면 다음 상태로 이동하도록 만드는 것입니다.

화면 연출

앞서 보여준 네 단계가 단순한 화살표 연결 구조로 바뀌어.

단계별 실행 순서

00

명령어

01

주소 결정

10

데이터 읽기

11

결과 기록

한 명령어 완료 후 다음 명령어로

한 단계씩 순서대로 강조한 뒤 마지막 단계에서 첫 번째 단계로 돌아가는 화살표가 생겨.

단, 메모리가 응답하지 않은 상태에서도 무조건 다음 단계로 넘어가는 애니메이션은 피해야 해.

설명용으로 데이터가 정해진 사이클 안에 준비된다고 가정하거나, 응답이 아직 없다면 현재 단계에 머무는 모습을 보여줘.

### 01:46–01:52 — 현재 상태를 저장하고 제어 신호를 생성한다

나레이션

이때 현재 상태를 레지스터에 저장하고, 그 값에 따라 필요한 제어 신호를 만드는 논리 회로를 추가할 수 있습니다.

화면 연출

이 구간이 ACT 3의 핵심 장면이야.

기존 프로세서 왼쪽에 초록색 레지스터를 추가해.

레지스터에는 현재 상태를 나타내는 2비트 값이 저장돼.

`State Register = 10`

이 값이 오른쪽 논리 회로에 입력되고, 출력으로 메모리 읽기 제어가 활성화돼.

이후 다음 상태 `11`이 계산되고, 클럭 에지에서 상태 레지스터가 갱신돼.

상태가 11로 바뀌면 이전 메모리 읽기 제어는 비활성화되고, 레지스터 쓰기 제어가 활성화돼.

새롭게 추가되는 제어 회로

개념도: 현재 상태와 필요한 조건을 이용해 제어 신호 및 다음 상태를 결정한다. 실제 다음 상태는 명령어 종류나 메모리 응답 여부에도 영향을 받을 수 있다.

연출 주의: 현재 상태가 바뀌는 시점은 클럭 에지야. 상태를 계산하는 논리 회로의 출력이 변하는 것과, 저장된 상태가 갱신되는 순간을 구분해.

### 01:52–01:59 — 이 구조의 이름: FSM

나레이션

이렇게 여러 상태와 상태 사이의 이동을 회로로 구성한 것을 유한 상태 기계, FSM이라고 합니다.

화면 연출

지금까지 만든 `State Register + Control Logic` 두 블록을 하나의 외곽선으로 묶어.

그 위에 이름을 표시해.

Finite State Machine

작게 `FSM · 유한 상태 기계`를 표시해.

이후 화면 오른쪽에는 앞선 네 단계의 상태도, 왼쪽에는 실제 레지스터와 논리 회로를 나란히 보여줘.

중요한 표현 구분

상태도는 FSM이 어떤 규칙으로 동작하는지 나타내는 것이고, 레지스터와 논리 게이트는 이를 하드웨어로 어떻게 구성하는지 나타내는 것이야.

상태도가 회로 그 자체인 것처럼 표현하지 않도록 해.

# ACT 4. 하나의 명령어를 여러 클럭에 나누어 실행한다

01:59–02:14 · 지금까지 추가한 회로를 하나로 묶어 동작을 확인한다.

### 01:59–02:03 — 여러 클럭에 나누어 실행

나레이션

이제 하나의 명령어를 여러 클럭에 걸쳐 실행할 수 있습니다.

화면 연출

전체 프로세서 구조를 다시 보여줘.

상단에는 공통 클럭 파형을 배치해.

아래에는 네 개의 단계가 시간에 따라 하나씩 진행되는 모습을 나타내.

한 명령어의 여러 사이클 실행

| 사이클 | 수행할 동작 | 유지할 정보           |
| --- | ------ | ---------------- |
| 1   | 명령어 인출 | `LOAD R1, [100]` |
| 2   | 주소 결정  | `100`, `R1`      |
| 3   | 메모리 읽기 | `5`, `R1`        |
| 4   | 결과 기록  | `R1 = 5`         |

메모리 읽기가 해당 단계에서 완료되는 것으로 가정한 교육용 예시. 실제 필요한 사이클 수는 설계와 응답 지연에 따라 달라진다.

한 사이클마다 상태 레지스터가 갱신되고, 이전 단계의 값은 필요한 저장 회로에 유지되는 모습을 보여줘.

### 02:03–02:08 — 저장과 제어가 함께 동작한다

나레이션

각 과정에서 필요한 정보를 저장하고, 제어 회로가 순서대로 다음 동작을 선택하는 것입니다.

화면 연출

전체 프로세서에서 저장 회로와 제어 회로를 서로 다른 색으로 강조해.

초록색 레지스터들이 명령어와 주소, 데이터를 보관해.

주황색 FSM은 현재 단계에 따라 필요한 제어 신호를 발생시켜.

두 동작을 동시에 보여주되, 화면에는 두 개의 짧은 문구만 남겨.

`정보를 유지한다`

`다음 동작을 결정한다`

### 02:08–02:14 — 다중 사이클 실행 구조라는 이름

나레이션

이처럼 하나의 명령어를 여러 클럭에 나누어 처리하는 구조를 다중 사이클 실행 구조라고 합니다.

화면 연출

화면 상단에 다음 명칭을 등장시켜.

Multi-cycle Execution

그 아래에는 간단한 시간축을 표시해.

`Clock 1 → Clock 2 → Clock 3 → Clock 4`

각 시점 아래에 해당 단계의 작은 블록을 배치하고, 하나의 LOAD 명령어가 순서대로 진행되는 모습을 보여줘.

이 장면에서는 아직 서로 다른 명령어가 동시에 여러 단계를 사용하는 것으로 표현하면 안 돼.

이번에 완성한 교육용 설계는 하나의 명령어가 여러 클럭에 걸쳐 순차적으로 진행되는 구조야.

# ACT 5. 서로 다른 명령어의 실행을 겹칠 수 있을까?

02:14–02:33 · 완성된 구조에서 다음 확장 가능성을 발견한다.

### 02:14–02:17 — 새로운 가능성 발견

나레이션

그런데 여기서 한 가지 가능성이 생깁니다.

화면 연출

다중 사이클 실행 구조의 전체 회로를 그대로 유지해.

화면에서 데이터 메모리와 명령어 메모리 두 영역을 따로 강조해.

두 메모리가 서로 독립된 블록이라는 사실을 보여줘.

화면에 물음표 하나가 나타나고 다른 모든 텍스트는 사라져.

### 02:17–02:23 — 사용하지 않는 장치가 남아 있다

나레이션

첫 번째 명령어가 메모리에서 데이터를 기다리는 동안, 명령어를 가져오는 회로는 사용되지 않을 수도 있습니다.

화면 연출

첫 번째 LOAD 명령어가 메모리 읽기 단계에 있는 모습을 보여줘.

화면의 중앙에 다음 상태가 표시돼.

`LOAD R1, [100]`

`Data Memory: Waiting`

명령어 메모리와 인출 경로는 비활성 상태를 표시해.

각 회로 위에 상태를 나타내는 작은 표시를 붙여.

- 데이터 메모리: `사용 중`
- 명령어 인출 경로: `대기 중`

단, 이 장면은 설명용으로 명령어 인출과 데이터 읽기가 서로 독립적인 경로를 사용한다고 가정해. 실제로 두 동작이 동일한 메모리 포트나 다른 하드웨어 자원을 공유한다면 동시에 사용할 수 없을 수도 있어.

### 02:23–02:27 — 다음 명령어를 미리 가져온다면?

나레이션

그렇다면 그 시간에 다음 명령어를 미리 가져올 수는 없을까요?

화면 연출

화면 왼쪽에 첫 번째 명령어를 배치해.

`LOAD R1, [100]`

오른쪽에는 두 번째 명령어를 배치해.

`ADD R3, R2, R4`

첫 번째 명령어가 메모리 읽기 단계에 있는 동안, 두 번째 명령어가 인출 단계에 들어오는 모습을 보여줘.

두 명령어는 서로 다른 색으로 표현해.

첫 번째 명령어는 보라색, 두 번째 명령어는 파란색을 사용해.

주의: 아직 파이프라인 구조가 구현된 것은 아니야. 이 장면에서는 동시 실행의 가능성만 제시하고, 실제로 두 명령어가 정상적으로 완료되는 애니메이션까지 진행하지 않아.

### 02:27–02:33 — 다음 편으로 연결

나레이션

다음에는 서로 다른 명령어의 실행 과정을 겹치도록 만드는 구조를 살펴보겠습니다.

화면 연출

화면 중앙에 세 개의 실행 단계가 나란히 등장해.

`Fetch → Decode → Execute`

첫 번째 명령어가 Execute 영역에 있고 두 번째 명령어가 Decode 영역에, 세 번째 명령어가 Fetch 영역에 들어갈 수 있는 자리만 희미하게 표시해.

각 영역 사이에는 작은 빈 사각형을 남겨둬.

그 빈 사각형이 초록색으로 강조되면서 영상이 종료돼.

## 실제 제작에서 주의할 네 가지

첫째, 명령어 레지스터가 없어도 모든 프로세서가 잘못 작동하는 것은 아니야. 이번 영상에서 구성하는 것은 명령어를 별도로 저장해 두고 여러 단계에 걸쳐 처리하는 교육용 프로세서야. 특정한 저장 방식이 유일한 정답처럼 보이지 않도록 해야 해.

둘째, 임시 레지스터는 반드시 저장해야 할 정보가 있을 때 추가해. 특히 `LOAD R1, [100]`처럼 주소가 명령어에 직접 포함된 경우에는 ALU로 주소를 계산하는 장면이 필수는 아니야. 01:05\~01:12의 `100+4=104`는 별도의 주소 계산 상황을 간략하게 보여주는 장면으로 취급하고, 이후 주 실행 예시는 다시 `LOAD R1, [100]`으로 돌아오면 돼.

셋째, 상태 제어와 실제 계산을 혼동하지 않아야 해. FSM이 직접 메모리 데이터를 계산하거나 이동시키는 것이 아니라, 이미 존재하는 데이터 경로가 어느 순간 어떤 동작을 수행할지 제어하는 구조라는 점을 유지해.

넷째, 다중 사이클 실행과 파이프라인은 구별해야 해. 12편에서는 한 명령어의 실행을 여러 클럭에 나누어 처리하고, 13편에서는 그 실행 단계에 서로 다른 명령어가 동시에 존재하도록 구조를 확장할 거야.

### 영상의 가장 중요한 장면

나는 01:46–01:52 구간에 가장 많은 시각적 완성도를 투자하는 것이 좋다고 생각해.

지금까지는 ALU와 레지스터, 메모리만으로 계산과 데이터 이동을 설명했지만, 이제는 현재 상태를 저장한 레지스터의 출력이 제어 논리로 들어가고, 그 결과로 기존 장치들의 제어 신호가 바뀌는 장면이 등장해.

이것이 12편에서 새롭게 구축한 구조의 본질이야.

기존 회로는 그대로 두고, 현재 어떤 과정을 수행 중인지 기억하는 회로를 추가하는 것.

이 장면이 명확하게 구현되면 시청자는 FSM이라는 용어를 외우지 않아도 왜 상태를 저장하는 회로와 제어 논리가 필요한지 이해할 수 있을 거야.
