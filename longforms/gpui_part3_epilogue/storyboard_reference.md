# GPU 개론 3부 마무리 — 하나의 명령어에서 병렬 실행까지

상세 영상화 콘티 · 9:16 세로형 쇼츠 · 롱폼 에필로그 겸 독립 영상 · 시간 지정 제외

이번 영상은 11\~15편의 내용을 순서대로 복습하는 것보다, 하나의 프로세서가 다섯 번의 구조적 확장을 거쳐 여러 명령어를 겹쳐 실행할 수 있게 되는 과정을 하나의 연속된 애니메이션으로 보여주는 것이 중요해.

특히 영상이 끝났을 때 시청자가 다음 변화를 이해하도록 만들자.

데이터를 가져오는 프로세서 → 실행 순서를 제어하는 프로세서 → 서로 다른 명령어를 겹쳐 처리하는 프로세서 → 데이터 의존성을 처리하는 프로세서 → 여러 계산을 동시에 수행하는 프로세서

## 공통 제작 원칙

- 전체 화면은 기존 시리즈의 어두운 남색 `#0B1020`.
- 기존에 존재하던 회로는 회색, 새로 추가한 회로는 초록색 `#34D399`으로 잠시 강조.
- 명령어 A는 파란색 `#60A5FA`, 명령어 B는 보라색 `#A78BFA`.
- 데이터 메모리는 보라색, 주소와 제어 신호는 주황색 `#F59E0B`.
- 새 장면마다 프로세서를 처음부터 다시 그리지 않고, 이전 장면에서 완성한 구조를 유지한 채 추가·확대·축소.
- 장면마다 시청자가 읽어야 할 핵심 문구는 하나로 제한.
- 화면에 모든 회로를 계속 표시하지 않고, 전체 구조와 특정 기능의 확대 장면을 교차 사용.

영상 전체에서 다음 세 명령어를 주요 예시로 유지해.

```
LOAD R1, [100]
ADD  R3, R1, R2
STORE R3, [102]
```

메모리 주소 100의 값은 5, R2의 값은 3이야. 최종적으로 R3와 메모리 주소 102에 8이 기록되는 간단한 프로그램이지.

이후 병렬 실행을 설명할 때는 독립적인 명령어 `SUB R6, R4, R5`를 추가해.

## SCENE 1. 하나의 명령어를 실행하는 컴퓨터에서 출발한다

나레이션 대응

> 컴퓨터는 어떻게 여러 명령어를 동시에 실행할 수 있을까요?
>
> 우리는 앞서 논리 게이트와 레지스터, ALU를 조합해 기본적인 프로세서를 만들었습니다.

### 화면 구성

화면 중앙에 10편에서 완성한 간단한 프로세서를 배치해.

처음에는 ALU 하나만 크게 보여주고, 조금씩 화면을 축소해 레지스터 파일, 명령어 해독 회로, 명령어 메모리, PC가 드러나도록 해.

출발점 — 기본 프로세서

### 애니메이션

명령어 메모리에서 `ADD R3, R1, R2`가 출력돼.

레지스터 파일에 저장된 두 숫자가 ALU로 전달되고, 계산 결과가 R3에 기록돼.

전체 동작은 빠르게 한 번만 보여줘.

이 장면에서는 파이프라인이나 병렬 실행을 아직 언급하지 않아.

### 장면의 결론

화면 상단에 작은 문구를 표시해.

`명령어 하나를 실행하는 기본 구조`

이후 ALU와 레지스터 파일을 화면 중앙에 남긴 상태로 다음 장면으로 이동해.

## SCENE 2. 레지스터에 없는 숫자는 어떻게 가져올까?

나레이션 대응

> 하지만 처음 만든 프로세서는 레지스터에 저장된 값만 계산할 수 있었습니다.
>
> 그래서 데이터를 저장하고 읽을 수 있는 메모리를 연결했습니다.
>
> 이제 필요한 숫자를 가져오고, 계산한 결과를 다시 저장할 수 있게 되었습니다.

### 화면 구성

기존 프로세서를 화면 왼쪽에 축소해.

오른쪽에는 아직 연결되지 않은 데이터 메모리 블록을 새롭게 등장시켜.

메모리 내부에는 여러 주소가 세로로 나열돼.

```
[100]  5
[101]  3
[102]  0
```

### 애니메이션

먼저 ALU가 레지스터 R1의 값을 사용하려는 모습을 보여줘.

하지만 R1에는 필요한 값이 없어.

화면에 `Memory[100] = 5`라는 데이터가 별도로 존재함을 보여줘.

그다음 데이터 메모리가 기존 프로세서 오른쪽에 결합돼.

주소를 입력하는 선과 읽은 데이터를 전달하는 선이 연결돼.

`LOAD R1, [100]`이 실행되면서 주소 100이 선택되고, 5가 R1로 이동해.

이후 `ADD R3, R1, R2`가 실행되며 결과 8이 만들어져.

마지막으로 `STORE R3, [102]`가 실행되고, 메모리 주소 102의 값이 0에서 8로 바뀌어.

### 시각적 강조

메모리에 저장된 값이 레지스터로 이동하고, 계산 결과가 다시 메모리로 돌아가는 왕복 데이터 경로를 보여줘.

새롭게 추가된 데이터 메모리와 연결선만 초록색으로 강조한 뒤 기존 구조의 일부로 통합해.

화면의 문구는 다음과 같이 표시해.

`메모리 → 계산 → 메모리`

## SCENE 3. 회로가 동작하는 순서는 누가 결정할까?

나레이션 대응

> 그런데 명령어를 가져오고, 주소를 결정하고, 데이터를 읽고, 결과를 기록하는 동작은 어떤 순서로 수행해야 할까요?

### 화면 구성

앞 장면에서 실행한 `LOAD R1, [100]`을 다시 보여줘.

명령어 자체를 화면 상단에 크게 표시해.

하단에는 네 가지 동작을 나열해.

`명령어 인출`

`주소 결정`

`데이터 읽기`

`결과 기록`

### 애니메이션

기존 프로세서의 각 회로가 무작위로 동작하는 식으로 표현하지 말고, 처음에는 네 단계가 아직 제어되지 않은 상태로 모두 회색으로 나타나게 해.

이후 첫 번째 동작을 강조하면서 명령어 메모리를 활성화해.

두 번째 동작에서는 주소 경로를 활성화하고, 세 번째에서는 데이터 메모리를, 마지막에는 레지스터 파일 쓰기 경로를 강조해.

시청자가 서로 다른 동작은 서로 다른 시점에 수행하도록 제어할 수 있다는 사실을 확인하도록 해.

### 연결 연출

네 단계의 번호를 각각 `00`, `01`, `10`, `11`로 바꿔.

다음 장면에서 이 값들을 저장할 회로가 추가될 거야.

## SCENE 4. 현재 실행 단계를 기억하는 회로를 추가한다

나레이션 대응

> 우리는 현재 실행 단계를 레지스터에 저장하고, 그 값에 따라 필요한 회로를 제어하는 구조를 추가했습니다.
>
> 이를 통해 하나의 명령어를 여러 클럭에 나누어 실행하는 프로세서를 구성했습니다.

### 화면 구성

기존 프로세서의 제어 영역을 확대해.

그 안에 작은 2비트 레지스터를 추가해.

초기값은 `00`이야.

레지스터 오른쪽에는 제어 논리 블록을 배치해.

### 애니메이션

처음에는 상태 레지스터에 `00`이 저장돼.

이 값이 제어 논리에 전달되고 명령어 인출 회로가 활성화돼.

다음 클럭 경계에서 상태값이 `01`로 변경돼.

주소 결정 회로가 활성화돼.

그다음 `10`에서는 데이터 메모리 읽기, `11`에서는 레지스터 기록이 활성화돼.

네 번째 단계가 완료되면 다음 명령어를 위한 초기 상태로 돌아와.

### 이름 등장

레지스터와 제어 논리를 하나의 외곽선으로 묶어.

Finite State Machine — FSM

그다음 전체 프로세서를 보여주고 짧게 다음 명칭을 표시해.

Multi-cycle Execution

각각의 회로를 어떤 순서로 동작시킬지 결정하는 구조가 추가되었다는 점이 핵심이야.

## SCENE 5. 그런데 모든 회로가 매 순간 사용되는 것은 아니다

나레이션 대응

> 여기서 새로운 가능성이 생겼습니다.
>
> 명령어를 가져오는 회로와 데이터를 읽는 회로는 서로 다른 장치입니다.
>
> 그렇다면 첫 번째 명령어가 데이터를 읽는 동안, 다음 명령어를 미리 가져올 수 있지 않을까요?

### 화면 구성

SCENE 4에서 완성한 다중 사이클 프로세서를 유지해.

이번에는 전체 회로도에서 명령어 메모리와 데이터 메모리만 강조해.

명령어 A는 데이터 메모리에서 숫자 5를 읽고 있어.

반면 명령어 메모리는 회색으로 표시돼.

### 애니메이션

첫 번째 명령어가 데이터 메모리를 사용하는 모습을 보여줘.

`A: Memory[100] → 5`

그다음 사용되지 않는 명령어 메모리를 확대해.

명령어 메모리에 다음 PC 주소가 전달되고, 두 번째 명령어가 출력돼.

`B: ADD R3, R1, R2`

이때 두 메모리에서 동시에 신호가 움직이도록 해.

명령어 B

명령어 인출

Instruction Memory

명령어 A

데이터 읽기

Data Memory

서로 다른 회로가 같은 시간에 서로 다른 명령어를 처리

### 장면의 결론

두 명령어를 하나의 프로세서 외곽선 안에 다시 배치해.

화면 문구는 다음과 같아.

`하나의 프로세서, 서로 다른 두 작업`

두 메모리가 서로 독립적인 접근 경로를 가지고 있다는 전제를 유지해야 해.

또한 12편의 전역 FSM 제어를 그대로 둔 채 두 동작이 동시에 수행되는 것처럼 표현하지 않아야 해. 이제 여러 단계가 동시에 동작하도록 제어 구조를 확장한다는 사실을 다음 장면에서 보여줄 거야.

## SCENE 6. 서로 다른 명령어의 정보를 구분한다

나레이션 대응

> 우리는 각 실행 단계 사이에 레지스터를 추가해, 서로 다른 명령어의 정보가 섞이지 않도록 만들었습니다.
>
> 이제 여러 명령어가 서로 다른 실행 단계를 동시에 사용할 수 있습니다.
>
> 이것이 파이프라인의 기본적인 원리입니다.

### 화면 구성

SCENE 5에서 동시에 동작하던 두 명령어를 그대로 사용해.

이번에는 명령어 처리 단계들을 화면 가운데 가로로 배치해.

`Fetch → Decode → Execute → Memory → Writeback`

12편의 네 단계와 달리, 여기서는 일반적인 ALU 명령어와 Load 명령어를 함께 처리할 수 있도록 Execute와 Memory를 분리한 구조로 정리해.

### 애니메이션 A — 정보 보관

각 실행 단계 사이에 작은 레지스터가 나타나.

기존 파이프라인 레지스터를 재사용하는 것이므로 처음부터 새로운 회로처럼 등장시키지 않고, 13편에서 추가했던 저장 회로를 복원하는 느낌으로 표현해.

명령어 A의 목적지 정보 R1이 한 레지스터에 저장돼.

명령어 B의 연산 정보와 필요한 레지스터 번호는 다른 단계의 레지스터에 저장돼.

두 명령어의 정보가 서로 다른 저장 위치에 보관되는 모습을 보여줘.

### 애니메이션 B — 실행 단계 중첩

이제 명령어 A와 B가 각각 다른 실행 단계로 이동해.

명령어 카드는 클럭 경계에서 한 단계씩 이동하고, 각 단계의 회로는 해당 명령어를 처리해.

명령어 실행 단계 중첩

클럭 1

IF

A

ID

·

EX

·

MEM

·

WB

·

처음다음 클럭

두 명령어가 의존성이나 자원 충돌 없이 진행할 수 있을 때의 단순화된 예시.

### 이름 등장

두 명령어가 서로 다른 단계에서 동시에 진행되는 모습을 보여준 뒤 구조 전체를 하나의 테두리로 묶어.

Instruction Pipeline

이어서 화면의 핵심 문구를 표시해.

`서로 다른 명령어의 실행 단계를 겹친다.`

### 중요한 구분

시청자가 ALU 두 개를 사용하고 있다고 오해하지 않도록, 이 장면의 Execute 단계에는 여전히 ALU 하나만 표시해.

각 명령어가 서로 다른 시점에 ALU를 사용한다는 점이 15편의 다중 ALU와 다른 핵심이야.

## SCENE 7. 하지만 다음 명령어가 이전 결과를 필요로 한다면?

나레이션 대응

> 하지만 모든 명령어가 독립적인 것은 아닙니다.
>
> 앞선 명령어가 만들어야 할 값을 다음 명령어가 필요로 한다면, 아직 준비되지 않은 데이터로 계산할 수도 있습니다.

### 화면 구성

파이프라인 전체 구조에서 명령어 두 개만 확대해.

```
A: LOAD R1, [100]
B: ADD  R3, R1, R2
```

A의 목적지 R1과 B의 입력 R1을 주황색으로 강조해.

두 명령어 사이에 의존성을 나타내는 연결선이 나타나.

### 애니메이션

명령어 A가 메모리에서 5를 읽으려는 모습을 보여줘.

현재 R1에는 이전 값 0이 저장돼 있다고 가정해.

명령어 B는 R1을 읽어 ADD를 수행하려고 해.

화면을 두 부분으로 나눠.

이전 값을 사용하면

## 0 + 3 = 3

필요한 값으로 계산하면

## 5 + 3 = 8

ALU의 연산 자체에는 문제가 없다는 점을 표현하기 위해, 붉은 강조는 ALU가 아니라 오래된 R1 입력 경로에 적용해.

화면에 다음 문구를 표시해.

`필요한 값이 아직 준비되지 않았다.`

## SCENE 8. 값이 준비되지 않았다면 기다린다

나레이션 대응

> 그래서 필요한 값이 준비될 때까지 실행을 잠시 지연시키는 제어를 추가했습니다.

### 화면 구성

기존 파이프라인 회로에 14편에서 추가했던 의존성 검사 논리와 Stall 제어 경로를 다시 나타내.

### 애니메이션

A가 메모리 접근 단계로 이동할 때 B는 아직 자신의 입력을 사용할 수 없어.

의존성 검사 논리가 활성화돼.

명령어 B가 다음 실행 단계로 이동하려던 애니메이션이 멈춰.

A는 계속 진행하고 B는 같은 단계에 유지돼.

다음 실행 단계에는 빈 동작인 Bubble이 삽입돼.

이때 전체 화면을 정지시키지 않아야 해.

A는 계속 진행하고, B만 필요한 만큼 기다리는 것이 핵심이야.

### 화면 표시

`Stall`

`값이 준비될 때까지 실행 지연`

이 문구를 보여준 후 곧바로 다음 장면으로 넘어가.

## SCENE 9. 값이 이미 존재한다면 직접 전달한다

나레이션 대응

> 반대로 결과가 이미 만들어졌다면, 레지스터에 기록될 때까지 기다리지 않고 다음 연산으로 직접 전달하는 경로도 만들었습니다.
>
> 이렇게 데이터가 준비되는 시점에 맞춰 명령어의 실행을 조절할 수 있게 되었습니다.

### 화면 구성

이번에는 ALU의 계산 결과를 사용하는 간단한 예시로 바꿔.

```
A: ADD R3, R1, R2
B: SUB R4, R3, R5
```

### 애니메이션

A의 ALU가 계산을 완료해 결과 8을 생성해.

그 값이 파이프라인 레지스터에 저장돼 있지만, R3에는 아직 최종적으로 기록되지 않았어.

B의 ALU 입력 경로가 확대돼.

기존에는 R3의 이전 값을 읽으려 했지만, 이번에는 A의 결과가 보관된 파이프라인 레지스터에서 연결선을 하나 추가해.

연결선은 기존 ALU 입력 MUX로 향해.

MUX가 앞선 결과 8을 선택하고, 다음 ALU 연산에 사용해.

### 핵심 시각화

### 장면 마무리

앞서 보여준 Stall 장면과 Forwarding 장면을 짧게 나란히 재생해.

왼쪽은 아직 값이 준비되지 않아 기다리는 상황이야.

오른쪽은 값이 이미 존재하므로 직접 전달하는 상황이지.

마지막에 다음 문구를 표시해.

`필요한 값이 언제 준비되는가?`

기억할 용어가 아니라 데이터 준비 시점이 핵심이라는 것을 강조하는 장면이야.

## SCENE 10. 이제 계산 회로 자체를 늘려본다

나레이션 대응

> 그런데 여기까지는 계산을 수행하는 ALU가 하나뿐이었습니다.
>
> 서로 독립적인 계산이 두 개 존재한다면, 하나의 ALU를 번갈아 사용할 필요가 있을까요?

### 화면 구성

프로세서 회로 전체에서 ALU만 크게 확대해.

기존에는 ALU 하나가 두 명령어를 순서대로 처리하는 모습이야.

```
A: ADD R3, R1, R2
B: SUB R6, R4, R5
```

### 애니메이션

A가 먼저 ALU를 사용해 계산을 완료해.

B는 뒤에서 기다려.

A가 끝난 뒤 B가 ALU를 사용해.

그다음 동일한 실행 장면을 초기화해.

화면에 A와 B가 서로 독립적이라는 사실을 다시 강조해.

이 경우에는 입력과 목적지가 서로 겹치지 않으므로 어느 명령어를 먼저 계산하더라도 서로의 결과가 달라지지 않아.

### 핵심 질문

ALU 하나를 중앙에 크게 배치해.

그 옆에 비어 있는 공간을 만들어.

`계산 회로를 하나 더 만든다면?`

이 장면이 15편으로 이어지는 마지막 구조적 확장의 시작이야.

## SCENE 11. ALU를 하나 더 추가한다

나레이션 대응

> 우리는 ALU를 하나 더 추가하고, 각각의 입력과 결과를 전달할 수 있도록 데이터 경로를 확장했습니다.
>
> 이제 서로 다른 두 계산을 같은 시간에 수행할 수도 있게 되었습니다.

### 화면 구성

SCENE 10의 ALU 하나를 화면 왼쪽으로 이동해.

오른쪽에 동일한 ALU 하나를 추가해.

새로 추가한 회로만 초록색으로 강조해.

### 애니메이션

처음에는 ALU 0만 존재해.

이후 ALU 1이 나타나.

그다음 레지스터 파일의 입력 읽기 경로가 확장돼.

각 ALU에 두 개의 입력값과 연산 제어 정보가 전달돼.

ALU 0에는 `5 + 3`, ALU 1에는 `9 - 2`가 전달돼.

두 ALU가 같은 클럭 구간에 계산해.

ALU 0

## 5 + 3

# 8

R3에 기록

ALU 1

## 9 − 2

# 7

R6에 기록

계산 결과 8과 7은 서로 다른 결과 저장 회로에 보관돼.

이후 각각 R3와 R6에 기록돼.

이 장면에서는 두 명령어에 필요한 입력 데이터와 제어 정보가 이미 공급될 수 있는 구조라고 가정해. 단일 명령어 인출·해독 경로를 그대로 두면 매 클럭 두 명령어를 지속적으로 공급할 수 있는 것은 아니므로, 그 부분까지 해결되었다고 주장하지 않아야 해.

### 마지막 강조

새롭게 추가된 ALU와 입력·출력 경로가 기존 프로세서의 일부로 통합돼.

이제 기존 회로도보다 확장된 프로세서가 완성돼.

## SCENE 12. 다섯 번의 확장을 하나의 화면에 정리한다

나레이션 대응

> 처음에는 하나의 명령어를 실행하는 것에서 출발했지만, 이제는 여러 명령어의 실행을 겹치고, 독립적인 계산을 동시에 처리할 수 있는 구조까지 만들어진 것입니다.

이번 마무리 영상에서 가장 중요한 장면이야.

### 화면 구성

SCENE 11에서 완성한 프로세서를 중앙에 배치해.

화면 주변에는 지금까지 추가한 다섯 가지 구조의 이름을 배치해.

다만 모든 회로가 한 번에 빛나는 식으로 연출하지 않아.

추가 순서를 따라 하나씩 강조해.

기본 프로세서에서 확장된 구조까지

### 애니메이션

먼저 모든 새 회로의 강조를 꺼.

기본 프로세서의 ALU, PC, 레지스터 파일, 명령어 메모리만 남겨.

그다음 아래 순서대로 새 회로와 경로가 차례로 밝아져.

첫 번째 확장: 데이터 메모리와 Load/Store 경로.

두 번째 확장: 상태 레지스터와 제어 논리.

세 번째 확장: 파이프라인 레지스터와 동시 단계 실행.

네 번째 확장: 의존성 검사, Stall 제어, Forwarding 경로.

다섯 번째 확장: 두 번째 ALU와 입력·출력 경로.

각 변화가 끝날 때마다 해당 회로의 색상이 잠시 밝게 유지되었다가 기본 색으로 돌아가.

이 장면에서는 새로운 내용을 설명하지 않아. 앞서 보여준 실제 회로의 위치와 역할을 하나씩 되짚는 것이 목적이야.

### 마지막 문구

`Sequential Execution → Instruction-Level Parallelism`

이 표현은 영상이 모든 CPU의 구현을 설명했다는 의미가 아니라, 기본적인 순차 실행에서 여러 명령어의 작업을 겹치는 대표적인 구조까지 확장했다는 의미로 사용해.

## SCENE 13. 계산 회로를 계속 늘리면 성능도 계속 높아질까?

나레이션 대응

> 그렇다면 계산 회로를 계속 추가하면 성능도 끝없이 높아질까요?
>
> 실제로는 그렇지 않습니다.

### 화면 구성

완성된 프로세서에서 ALU만 다시 확대해.

처음에는 ALU가 두 개야.

이후 ALU 네 개, 여덟 개, 열여섯 개로 늘어나는 모습을 보여줘.

그러나 어느 순간 일부 ALU는 사용되지 않고 회색으로 남아 있어.

### 애니메이션

두 개의 ALU가 동시에 계산하는 모습을 보여줘.

그다음 ALU 네 개로 확장해.

하지만 실행할 준비가 된 명령어는 두 개뿐이야.

따라서 나머지 두 ALU는 동작하지 않아.

이후 ALU 여덟 개로 확장해도 일부만 활성화돼.

화면에 다음 문구를 표시해.

`계산 회로의 수 ≠ 항상 같은 비율의 성능 향상`

이 장면에서는 암달의 법칙이나 특정 성능 수치를 소개하지 않아.

단순히 계산 회로를 늘려도 실제로 활용할 수 있는 연산이 충분하지 않으면 성능 향상이 제한된다는 직관을 보여주는 것이 목적이야.

## SCENE 14. 계산보다 먼저 해결해야 할 제약들

나레이션 대응

> 어떤 계산은 앞선 결과를 기다려야 하고, 계산에 필요한 데이터를 공급하는 속도에도 한계가 있기 때문입니다.

### 화면 구성

화면을 두 부분으로 나눠.

왼쪽은 데이터 의존성.

오른쪽은 데이터 공급의 한계야.

### 왼쪽 — 의존성

```
A: ADD R3, R1, R2
B: SUB R4, R3, R5
```

B는 A의 결과 R3를 필요로 해.

ALU가 여러 개 존재하더라도 B가 필요한 값을 사용할 수 있을 때까지는 기다려야 할 수 있어.

### 오른쪽 — 데이터 공급

여러 ALU가 동시에 데이터를 요구하고 있어.

하지만 메모리에서 전달할 수 있는 데이터의 양은 유한해.

메모리 출력 경로를 좁게 보여주고, 여러 ALU가 그 데이터를 기다리는 모습을 보여줘.

계산 의존성

앞선 결과가 필요하다.

데이터 공급

메모리 전송 능력은 유한하다.

### 연출 의도

여기서는 새로운 최적화 기법을 소개하지 않아.

다음 시리즈에서 다룰 병렬 계산의 근본적인 두 제약을 보여주는 것이 목적이야.

## SCENE 15. 다음 파트로 연결한다

나레이션 대응

> 다음에는 이러한 제약이 병렬 프로세서의 구조에 어떤 영향을 미치는지 살펴보겠습니다.

### 화면 구성

완성된 프로세서 구조를 다시 화면 중앙에 배치해.

이때 여러 ALU 중 일부가 작동하고 있고, 다른 일부는 데이터 공급을 기다리고 있어.

### 애니메이션

화면을 천천히 축소해.

기존 프로세서의 전체 외곽선이 드러나.

그다음 ALU들이 더 많이 배치된 새로운 구조의 윤곽선이 화면 주변에 서서히 나타나.

그러나 실제 GPU 구조까지 완성해서 보여주지는 않아.

이번 영상은 GPU 내부 구조를 설명하는 편이 아니라, 그 구조가 필요한 이유를 다음 파트에서 탐구하기 위한 연결이야.

### 최종 문구

`계산 회로를 늘리는 것만으로 충분할까?`

그 아래 작은 글씨로 다음 문구를 표시해.

`Next — Limits of Parallel Computing`

마지막으로 화면의 모든 회로가 어두워지고 질문만 남은 상태에서 영상이 종료돼.

## 특히 중요한 제작 판단

첫째, 새로 등장하는 회로가 하나의 프로세서에 누적되어야 해. 다섯 개의 회로도를 각각 새로 보여주기보다, 기본 구조에서 시작해 기능이 하나씩 추가되는 과정을 유지해야 전체가 하나의 이야기로 이어져.

둘째, 11\~15편의 원래 영상을 짧게 잘라 이어 붙이는 것만으로 제작하지 않는 편이 좋아. 이번 영상은 독립 쇼츠로도 공개할 예정이므로, 기존 콘텐츠를 보지 않은 시청자에게도 의미가 전달되어야 해. 원본 장면을 재사용하더라도 관찰 대상을 명확하게 바꾸는 확대·축소와 전환이 필요해.

셋째, 파이프라인과 다중 ALU를 반드시 구별해야 해. 파이프라인은 서로 다른 명령어가 각기 다른 실행 단계를 동시에 사용하는 구조이고, 다중 ALU는 같은 종류의 실행 단계에서 여러 연산 회로가 동시에 동작할 수 있도록 확장한 구조야.

넷째, 마무리는 용어 정리가 아니라 새로운 질문으로 끝내야 해. 다섯 가지 구조를 완성한 것에서 이야기가 끝나는 것이 아니라, 계산 회로를 늘리는 데에도 한계가 존재한다는 사실을 발견하도록 만들어야 해.

그리고 마지막에는 이렇게 이어지는 거야.

“우리는 하나의 명령어를 실행하는 회로에서 출발해 여러 명령어를 겹치고 독립적인 계산을 동시에 수행하는 구조까지 만들었습니다. 하지만 계산 회로의 수가 곧 계산 성능을 결정하는 것은 아닙니다.”

이렇게 마무리하면 3부의 내용을 정리하면서, 다음에 다룰 병렬 계산의 구조적 한계까지 자연스럽게 연결할 수 있어.
