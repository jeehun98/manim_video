# GPU 개론 15 — 계산 회로를 여러 개 만들면 더 빨라질까?

상세 영상화 콘티 · 9:16 세로 영상 · Manim 기반 2D 모션그래픽 · 시간 지정 제외

이번 영상에서는 14편까지 구축한 프로세서를 유지하면서 ALU 하나가 여러 독립적인 계산을 처리해야 하는 상황을 발견하고, 두 번째 ALU를 실제로 추가하는 과정을 보여줘.

핵심은 단순히 ALU 블록을 복제하는 장면이 아니야.

두 계산이 서로 독립적이다 → 하지만 ALU가 하나라 동시에 계산할 수 없다 → ALU를 추가한다 → 각각의 입력과 제어 정보를 연결한다 → 결과를 보관하고 기록한다 → 이제 어떤 명령어를 어느 ALU에 배정할지 문제가 남는다.

이번 편에서는 명령어 스케줄러를 미리 완성하지 않아. 독립적인 두 명령어가 실행 대기 상태에 있다고 가정하고, 실행 회로를 추가하면 무엇이 가능해지고 어떤 주변 구조가 더 필요한지를 보여주는 데 집중해.

## 영상 전체에서 유지할 예시

```
ADD R3, R1, R2
SUB R6, R4, R5
```

초기 레지스터 값은 다음처럼 설정해.

| 레지스터 | 초기값 | 용도           |
| ---- | --- | ------------ |
| R1   | 5   | ADD의 첫 번째 입력 |
| R2   | 3   | ADD의 두 번째 입력 |
| R4   | 9   | SUB의 첫 번째 입력 |
| R5   | 2   | SUB의 두 번째 입력 |
| R3   | 0   | ADD 결과 저장    |
| R6   | 0   | SUB 결과 저장    |

최종 목표는 `R3 = 8`, `R6 = 7`이야.

두 명령어가 읽는 입력과 기록하는 목적지는 서로 겹치지 않기 때문에, 이번 영상에서는 데이터 의존성을 따로 해결하지 않아도 돼.

### 화면의 공통 규칙

- 배경: 짙은 남색 `#0B1020`
- 명령어 A와 데이터: 파란색 `#60A5FA`
- 명령어 B와 데이터: 보라색 `#A78BFA`
- 새로 추가한 실행 회로와 경로: 초록색 `#34D399`
- 제어 신호와 선택 경로: 주황색 `#F59E0B`
- 비활성 장치: 회색 `#64748B`

기존 프로세서 전체 회로도는 처음, 구조를 추가하는 순간, 마지막에 주로 사용하고, 나머지 장면에서는 실제로 변화하는 부분만 확대하는 것이 좋아.

## SCENE 1. 독립적인 두 명령어를 소개한다

대응 나레이션

> 앞서 우리는 여러 명령어를 겹쳐 실행하면서, 필요한 데이터가 준비되지 않았을 때 발생하는 문제를 살펴봤습니다.
>
> 그런데 서로의 계산 결과를 필요로 하지 않는 두 명령어라면 어떨까요?

### 화면 구성

14편의 마지막 장면에서 이어지도록 기존 파이프라인 구조를 등장시켜.

처음에는 두 명령어가 데이터를 주고받는 모습을 보여줘.

`LOAD R1, [100] → ADD R3, R1, R2`

두 명령어 사이에 결과 의존성을 나타내는 선이 존재해.

이후 이 명령어들을 화면에서 제거하고 새로운 두 명령어를 표시해.

명령어 A

ADD R3, R1, R2

5 + 3 = 8

명령어 B

SUB R6, R4, R5

9 − 2 = 7

### 애니메이션

첫 번째 ADD 명령어에서 입력 R1과 R2를 강조해.

두 번째 SUB 명령어에서 입력 R4와 R5를 강조해.

이후 각 명령어의 목적지 R3, R6을 강조해.

입력과 목적지 레지스터 번호 사이에 서로 겹치는 부분이 없다는 것을 보여줘.

화면 중앙에는 두 명령어 사이에 연결선을 그리려다가, 실제로 전달할 데이터가 없다는 것을 나타내며 선을 제거해.

문구는 짧게 표시해.

`서로의 결과를 필요로 하지 않는 두 계산`

이 장면에서는 아직 ALU 하나라는 제약을 보여주지 않아. 두 계산이 독립적이라는 사실을 먼저 납득시키는 것이 목적이야.

## SCENE 2. 독립적인 계산이라면 순서가 바뀌어도 결과가 같다

대응 나레이션

> 예를 들어 첫 번째 명령어는 두 숫자를 더하고, 두 번째 명령어는 다른 두 숫자를 뺀다고 생각해 보겠습니다.
>
> 두 계산은 서로의 결과를 사용하지 않으므로, 어느 쪽이 먼저 끝나더라도 다른 계산에는 영향을 주지 않습니다.

### 화면 구성

프로세서 회로도를 잠시 숨기고 두 계산식만 화면 중앙에 배치해.

왼쪽에는 ADD, 오른쪽에는 SUB를 보여줘.

### 애니메이션

처음에는 ADD를 먼저 계산해.

`5 + 3 = 8`

그다음 SUB를 계산해.

`9 − 2 = 7`

최종 결과 `R3 = 8`, `R6 = 7`을 표시해.

이어서 순서를 바꿔 SUB부터 수행한 뒤 ADD를 수행해.

결과는 동일하게 나타나.

실행 순서를 바꿔도 같은 결과

ADD → SUB

5 + 3 = 8

9 − 2 = 7

R3=8, R6=7

SUB → ADD

9 − 2 = 7

5 + 3 = 8

R3=8, R6=7

마지막에 두 결과를 하나의 상자 안에 모아.

`순서가 달라도 결과는 유지된다`

이후 두 계산식은 화면 위쪽에 작게 남기고, 아래에서 기존 ALU 회로도가 등장해.

## SCENE 3. 하지만 계산 회로는 하나뿐이다

대응 나레이션

> 하지만 지금까지 만든 프로세서에는 ALU가 하나뿐입니다.
>
> 따라서 두 명령어가 동시에 계산할 준비를 마쳤더라도, 하나의 ALU에서는 같은 순간에 두 연산을 수행할 수 없습니다.

### 화면 구성

기존 프로세서의 ALU 부분만 중앙에 확대해.

하나의 ALU에 입력 A와 입력 B, 제어 신호, 출력이 연결되어 있어.

그 위에 두 명령어 카드가 대기 중인 모습을 보여줘.

### 애니메이션

먼저 ADD 명령어가 ALU에 들어가.

입력값 5와 3이 전달되고, 제어 신호가 `ADD`로 바뀌어.

ALU 출력에 8이 나타나.

그동안 SUB 명령어는 ALU 앞에서 대기해.

ADD의 연산이 끝난 뒤 SUB가 들어가.

입력값이 9와 2로 교체되고, 제어 신호가 `SUB`로 바뀌어.

ALU 출력에 7이 나타나.

### 문제를 강조하는 장면

이제 두 명령어가 동시에 ALU로 향하는 모습을 잠깐 보여줘.

하나의 ALU에는 현재 선택된 입력과 연산 제어 정보가 한 세트만 들어갈 수 있어.

두 명령어의 입력을 동시에 같은 입력 단자에 전달할 수는 없다는 점을 시각화해.

이때 ALU에서 오류가 발생하거나 두 값이 충돌하여 이상한 숫자가 나오는 방식으로 표현하지 않아.

하나의 연산 회로가 같은 순간에 서로 다른 두 연산을 모두 수행할 수 없다는 자원 제한을 보여주면 돼.

## SCENE 4. ALU를 하나 더 추가한다

대응 나레이션

> 그렇다면 계산 회로를 하나 더 추가하면 어떨까요?
>
> 우리는 앞서 덧셈과 뺄셈을 수행할 수 있는 ALU를 만들었습니다.
>
> 이 회로를 하나 더 배치하면, 각각의 ALU가 서로 다른 명령어를 처리할 수 있습니다.

### 화면 구성

기존 ALU를 화면 왼쪽에 배치해.

오른쪽에는 새로 추가할 ALU를 위한 빈 공간을 마련해.

### 애니메이션

기존 ALU가 작은 회로 블록으로 축소돼.

옆에 동일한 형태의 ALU 블록이 하나 더 나타나.

새 ALU는 초록색 외곽선으로 강조해.

두 ALU 모두 동일한 덧셈과 뺄셈 기능을 가진다는 점을 보여줘.

여기에서 두 번째 ALU가 특별히 뺄셈 전용인 것처럼 표현하지 않아야 해.

둘 다 ADD와 SUB를 수행할 수 있고, 이번 예시에서는 각각 서로 다른 명령어를 담당하도록 하는 거야.

### 연출상 중요한 부분

새로 추가된 ALU는 이전에 학습한 구조를 재사용하는 것이므로 내부 논리 게이트나 가산기의 원리를 다시 설명하지 않아.

기존 회로를 복제해 새로운 실행 자원을 만든다는 사실에 집중해.

## SCENE 5. 두 ALU에 각각 다른 명령어를 전달한다

대응 나레이션

> 첫 번째 ALU에서는 덧셈을 수행하고, 두 번째 ALU에서는 뺄셈을 수행하는 것입니다.

### 화면 구성

앞 장면에서 추가한 두 ALU를 유지해.

화면 상단에는 명령어 A와 B를 배치해.

ALU 0과 ALU 1에는 아직 입력 데이터가 연결되어 있지 않아.

### 애니메이션

명령어 A가 ALU 0 위로 이동해.

`ADD R3, R1, R2`

명령어 B는 ALU 1 위로 이동해.

`SUB R6, R4, R5`

이제 두 ALU가 서로 다른 명령어를 담당한다는 사실이 명확해져.

ALU 0

## 5 + 3

ADD 실행

# 8

ALU 1

## 9 − 2

SUB 실행

# 7

두 ALU의 연산은 같은 클럭 구간에 진행돼.

하지만 여기서 실제 회로 연결이 완성되었다고 표현해서는 안 돼.

지금은 독립적인 계산 회로 두 개가 있다면 가능한 동작을 보여준 것이고, 다음 장면부터 그 동작에 필요한 입력과 출력 경로를 구체적으로 추가할 거야.

## SCENE 6. ALU를 추가했지만 입력은 어디서 가져올까?

대응 나레이션

> 그런데 ALU를 두 개 배치하는 것만으로는 충분하지 않습니다.
>
> 각 ALU에는 자신이 계산할 숫자와 어떤 연산을 수행할지 나타내는 제어 정보가 전달되어야 합니다.

### 화면 구성

두 ALU만 남기고 명령어 카드를 화면 상단에 작게 배치해.

각 ALU에는 입력 A, 입력 B, 연산 선택 신호가 있어.

처음에는 어느 입력선도 연결되지 않은 상태야.

### 애니메이션

ALU 0의 입력 단자 세 개를 차례로 강조해.

`Operand A`

`Operand B`

`Operation`

그다음 ALU 1에도 동일한 입력 단자들이 존재한다는 사실을 보여줘.

두 ALU에 들어가야 할 값들을 표시해.

|         | ALU 0  | ALU 1  |
| ------- | ------ | ------ |
| 첫 번째 입력 | R1 = 5 | R4 = 9 |
| 두 번째 입력 | R2 = 3 | R5 = 2 |
| 연산 제어   | ADD    | SUB    |

### 핵심 연출

ALU가 두 개라고 해서 명령어가 자동으로 두 ALU에 전달되는 것은 아니라는 점을 보여줘.

명령어에 포함된 레지스터 번호와 연산 종류를 각각의 ALU 입력으로 전달하는 구조가 필요해.

이 장면에서는 전체 입력 경로를 한꺼번에 추가하지 않고, 각 ALU가 서로 다른 입력 데이터와 제어 신호를 필요로 한다는 사실만 강조해.

## SCENE 7. 레지스터 파일에서 두 계산의 입력을 가져온다

대응 나레이션

> 따라서 레지스터 파일에서 읽은 값과 명령어의 제어 정보를 각 ALU에 전달할 수 있도록 입력 경로를 확장합니다.

### 화면 구성

화면 중앙에 Register File을 배치해.

양옆에는 ALU 0과 ALU 1이 존재해.

기존 레지스터 파일에서 값들을 읽는 모습을 먼저 보여줘.

이후 두 ALU가 같은 클럭 구간에 서로 다른 입력을 받아야 한다는 점을 강조해.

### 애니메이션

먼저 ALU 0으로 두 값이 전달돼.

`R1 = 5`

`R2 = 3`

다음으로 ALU 1에 필요한 입력을 강조해.

`R4 = 9`

`R5 = 2`

여기서 레지스터 파일의 읽기 포트가 두 개뿐이라면 네 값을 동시에 읽을 수 없다는 제약을 보여줘.

따라서 이번 교육용 구조에서는 레지스터 파일의 읽기 경로를 확장해.

기존 두 개의 읽기 포트에 두 개를 더 추가하는 거야.

개념도: 두 명령어가 각각 두 개의 피연산자를 읽을 수 있도록 레지스터 파일의 읽기 대역폭을 확장한 구조.

### 추가 설명 연출

레지스터 파일을 완전히 다른 장치로 교체하지 않아.

기존 Register File의 외형을 그대로 유지하면서, 추가 읽기 포트만 초록색으로 나타나게 해.

추가된 경로를 따라 R4와 R5의 값이 ALU 1에 전달돼.

두 ALU 모두 입력이 준비되면 해당 입력 경로를 각각 파란색과 보라색으로 강조해.

기술적 주의: 실제 설계에서는 값들을 이전 클럭에 미리 읽어 각각의 실행 대기 레지스터에 저장하거나, 별도의 레지스터 파일 뱅크를 사용하는 방식도 가능해. 이번 영상은 두 명령어가 동시에 레지스터 파일을 읽는 구조를 선택한 교육용 예시야.

## SCENE 8. 두 ALU가 서로 다른 연산을 수행한다

대응 나레이션

> 그리고 두 ALU가 만든 결과를 각각 보관하고, 올바른 목적지 레지스터에 기록할 수 있는 경로도 필요합니다.

이 장면은 계산 결과가 동시에 생성되는 모습과 그 결과가 어디에 기록되어야 하는지를 연결하는 것이 중요해.

### 화면 구성

두 ALU가 나란히 배치돼 있어.

두 ALU의 입력과 연산 제어 정보는 이미 연결되어 있어.

화면 중앙에서 두 연산을 동시에 수행해.

### 애니메이션

ALU 0의 제어 신호가 `ADD`로 설정돼.

`5 + 3 → 8`

ALU 1의 제어 신호는 `SUB`로 설정돼.

`9 − 2 → 7`

두 결과가 거의 동시에 나타나.

이때 각 결과값 아래에 목적지 레지스터 정보를 함께 표시해.

`8 → R3`

`7 → R6`

### 새로운 저장 구조

두 결과를 각각 별도의 결과 보관 레지스터에 저장해.

`Result 0 = 8, Destination = R3`

`Result 1 = 7, Destination = R6`

두 저장 회로는 기존 파이프라인 레지스터의 개념을 확장한 것으로 표현해.

새로운 종류의 메모리를 만든 것이 아니라, 두 명령어의 결과와 목적지 정보를 각각 유지할 저장 공간을 확보한 것이야.

### 화면 강조

저장된 결과와 목적지 정보가 하나의 묶음으로 유지되는 모습을 보여줘.

명령어 A가 만든 8은 R3와 연결되어야 하고, 명령어 B가 만든 7은 R6과 연결되어야 해.

## SCENE 9. 결과를 동시에 기록하려면 무엇이 더 필요할까?

### 화면 구성

레지스터 파일을 다시 확대해.

왼쪽에는 ALU 0의 결과 8이 있어.

오른쪽에는 ALU 1의 결과 7이 있어.

레지스터 파일의 쓰기 포트가 하나뿐인 기존 구조를 먼저 보여줘.

### 애니메이션

두 결과가 동시에 하나의 쓰기 포트로 향해.

하지만 하나의 쓰기 포트에서는 같은 클럭 에지에 서로 다른 두 레지스터로 두 결과를 독립적으로 기록할 수 없어.

따라서 두 가지 설계 선택이 가능하다는 점을 간결하게 보여줘.

첫 번째는 결과를 한 번에 하나씩 기록하는 방식이야.

두 번째는 레지스터 파일의 쓰기 포트를 추가해 두 결과를 같은 클럭 에지에 기록하는 방식이야.

이번 편에서는 두 번째 쓰기 포트를 추가하는 구조를 선택하자.

두 개의 쓰기 포트를 사용하는 교육용 예시. 포트 수 증가는 면적, 배선, 제어 복잡도에 영향을 준다.

### 연출

클럭 에지에서 두 쓰기 포트가 동시에 활성화돼.

그 결과 R3와 R6이 각각 갱신돼.

`R3: 0 → 8`

`R6: 0 → 7`

두 결과가 올바른 목적지에 기록되는 모습을 충분히 보여줘.

이제 단순히 계산 회로가 두 개 있는 상태를 넘어, 실제로 두 연산의 입력과 출력까지 처리할 수 있는 구조가 완성된 거야.

## SCENE 10. 기존 프로세서와 확장된 프로세서를 비교한다

대응 나레이션

> 이제 서로 독립적인 두 명령어를 동시에 계산할 수 있는 구조가 만들어졌습니다.
>
> 이처럼 하나의 프로세서 안에 여러 실행 회로를 배치한 구조를 다중 실행 유닛 구조라고 합니다.

### 화면 구성

기존 프로세서와 확장된 프로세서를 나란히 보여줘.

기존

ALU 0

한 번에 한 연산

확장

ALU 0

ALU 1

독립적인 두 연산 동시 처리 가능

### 애니메이션

왼쪽 기존 프로세서는 ADD가 끝난 뒤 SUB가 시작돼.

오른쪽 확장된 프로세서는 ADD와 SUB가 같은 클럭 구간에 수행돼.

둘의 동작을 병렬로 재생해 비교해.

오른쪽 결과가 더 일찍 준비되는 모습을 보여주되, 프로그램 전체가 두 배 빠르게 실행된다고 표현하지는 않아.

이후 확장된 프로세서만 화면에 남겨.

두 ALU, 확장된 읽기·쓰기 경로, 별도의 결과 저장 회로를 초록색으로 순서대로 강조해.

마지막에 구조의 이름을 붙여.

Multiple Execution Units

이름은 모든 회로가 연결되고 실제로 두 계산을 수행한 뒤 등장시켜.

## SCENE 11. ALU가 두 개라면 언제나 두 배 빠를까?

대응 나레이션

> 그렇다면 실행 회로를 두 개로 늘리면 계산 속도도 두 배가 될까요?
>
> 반드시 그렇지는 않습니다.

### 화면 구성

두 개의 ALU를 크게 보여줘.

처음에는 두 ALU가 모두 동작하고 있어.

그다음 화면의 명령어를 변경해.

`ADD R3, R1, R2`

`SUB R4, R3, R5`

두 번째 명령어는 첫 번째 명령어의 결과인 R3를 필요로 해.

### 애니메이션

ALU 0이 ADD를 수행해.

ALU 1은 SUB를 실행하려고 하지만, 입력으로 필요한 R3의 결과가 아직 준비되지 않았어.

ALU 1이 입력을 기다리는 모습을 보여줘.

여기서 14편의 Forwarding 경로를 짧게 다시 강조해.

결과가 준비되면 직접 전달할 수 있지만, 준비되지 않은 결과를 즉시 사용할 수는 없다는 점을 보여줘.

### 장면 결론

두 ALU 중 하나는 활성화되어 있고 다른 하나는 대기 상태야.

화면에 짧게 표시해.

`ALU가 여러 개여도 독립적인 작업이 필요하다.`

## SCENE 12. 계산 회로 외의 장치도 충분해야 한다

대응 나레이션

> 두 명령어가 같은 데이터에 의존한다면, 여전히 앞선 결과를 기다려야 할 수 있습니다.
>
> 또한 두 명령어에 필요한 데이터를 동시에 읽거나, 계산 결과를 기록할 수 있는 하드웨어 자원도 충분해야 합니다.
>
> 따라서 실행 회로를 추가하는 것뿐 아니라, 여러 회로가 동시에 동작할 수 있도록 데이터 경로와 제어 구조도 함께 확장해야 합니다.

### 화면 구성

SCENE 10에서 완성한 두 ALU 구조를 다시 가져와.

이번에는 ALU가 아니라 주변 회로를 강조해.

먼저 Register File의 읽기 포트를 강조해.

그다음 결과 저장 회로를 강조해.

마지막으로 쓰기 포트를 강조해.

### 애니메이션

입력 읽기 포트가 부족한 경우를 보여줘.

ALU가 두 개 있어도 하나는 필요한 입력을 전달받지 못하므로 대기하게 돼.

다음으로 쓰기 포트가 부족한 경우를 보여줘.

두 ALU의 계산 결과가 존재해도 동시에 기록할 수 없다면 결과 저장 및 기록 단계에서 추가 처리가 필요해.

이후 확장된 포트와 저장 경로가 활성화되면서 정상적인 동시 실행 구조가 복원돼.

### 강조할 내용

두 ALU만 화면에 놓으면 계산 능력이 늘어난 것처럼 보이지만, 실제로 두 명령어를 처리하려면 그 주변의 하드웨어도 함께 확장되어야 한다는 사실을 보여줘.

화면의 결론은 다음 문구로 충분해.

`계산 회로의 수만 늘린다고 성능이 결정되지는 않는다.`

## SCENE 13. 이제 어떤 명령어를 어느 ALU로 보내야 할까?

대응 나레이션

> 지금까지 우리는 하나의 명령어를 실행하는 회로에서 출발해, 여러 명령어를 겹쳐 처리하고, 서로 다른 계산을 동시에 수행하는 구조까지 만들었습니다.
>
> 그런데 여기서 새로운 질문이 생깁니다.
>
> 실행 회로가 여러 개라면, 어떤 명령어를 어느 회로에 전달해야 할까요?
>
> 그리고 필요한 데이터가 준비되지 않은 명령어가 있다면, 다른 명령어를 먼저 실행하도록 선택할 수도 있을까요?
>
> 다음에는 여러 실행 회로에 명령어를 배정하는 구조를 살펴보겠습니다.

### 화면 구성

완성된 프로세서에서 두 ALU만 남겨.

그 위에 여러 명령어가 대기 중인 모습을 보여줘.

```
ADD R3, R1, R2
SUB R6, R4, R5
ADD R7, R3, R8
SUB R9, R10, R11
```

각 명령어는 하나의 작은 카드로 표현해.

### 애니메이션

먼저 첫 번째 ADD가 ALU 0으로 향해.

두 번째 SUB는 ALU 1로 향해.

세 번째 ADD는 첫 번째 명령어의 결과 R3를 필요로 하므로 아직 실행할 수 없는 상태야.

네 번째 SUB는 앞선 명령어들의 결과를 필요로 하지 않아.

그런데 두 ALU에 다음 작업을 배정해야 하는 상황이 되면, 어떤 명령어를 먼저 선택하는 것이 좋을까?

화면에서 세 번째 명령어는 주황색 대기 표시가 나타나고, 네 번째 명령어는 초록색 준비 표시가 나타나.

이후 두 명령어 사이에 선택을 나타내는 커서가 나타나.

하지만 실제로 어느 명령어를 먼저 배정할지 결정하지 않고 화면을 정지해.

### 마지막 문구

`다음: 어떤 명령어를 먼저 실행할까?`

`GPU 개론 16 — Instruction Scheduling`

다음 편에서는 실행할 준비가 된 명령어와 그렇지 않은 명령어를 구분하고, 여러 실행 회로에 작업을 배정하는 구조를 추가하게 돼.

## 제작 시 반드시 주의할 부분

1\. ALU 하나를 복제하는 순간과 동시에 실행할 수 있는 순간은 구분해야 해. ALU를 하나 더 추가한 뒤에도 각각의 입력, 제어 정보, 결과 저장 경로가 필요하다는 사실을 보여줘야 구조 확장의 의미가 전달돼.

2\. 두 ALU가 서로 다른 기능을 가진 것처럼 표현하지 않아야 해. 이번 예시에서 ALU 0이 ADD, ALU 1이 SUB를 담당하는 것은 일시적인 작업 배정일 뿐이야. 두 ALU 모두 덧셈과 뺄셈이 가능하다고 설정해.

3\. 13편의 파이프라인과 이번 편의 차이가 명확해야 해. 기존 파이프라인은 서로 다른 명령어가 서로 다른 실행 단계를 이용하는 구조였어. 이번 편에서는 같은 실행 단계에서 실제 연산을 수행할 수 있는 회로가 여러 개 존재하도록 확장하는 거야.

4\. 레지스터 파일의 포트 수는 설계 선택이야. 이번 영상에서는 동시 읽기와 동시 기록을 설명하기 위해 포트를 늘리지만, 실제 프로세서는 뱅킹, 버퍼, 시간 분할, 여러 클럭에 걸친 기록 등 다른 방법도 사용할 수 있어.

5\. 실행 회로를 추가했다고 매 클럭 두 명령어를 자동으로 공급할 수 있는 것은 아니야. 이번 편에서 두 명령어는 이미 실행 대기 상태에 있다고 가정해야 해. 명령어를 여러 개 가져오고 해독하며 실행 회로에 배정하는 문제는 16편에서 다루는 것이 자연스러워.

### 이번 영상에서 가장 중요한 장면

SCENE 3과 SCENE 4의 연결이 첫 번째 핵심이야.

서로 독립적인 계산인데도 ALU가 하나뿐이라 같은 순간에 처리할 수 없다는 제약을 보여준 뒤, 기존에 만들었던 ALU를 하나 더 배치하는 것으로 해결 방향을 제시하는 거지.

두 번째 핵심은 SCENE 7\~9야.

ALU를 두 개 배치하는 것만으로 끝나지 않고, 각 회로가 서로 다른 데이터를 받아 결과를 보관하고 기록할 수 있어야 한다는 사실을 실제 회로 연결로 보여줘.

이번 15편은 결국 다음 문장으로 요약할 수 있어.

“서로 독립적인 계산이 존재한다면, 실행 회로를 여러 개 배치해 같은 시간에 처리할 수 있다. 하지만 그러기 위해서는 입력과 출력 경로도 함께 확장해야 한다.”

이 흐름이 유지되면 16편에서 명령어를 선택하고 배정하는 회로가 왜 필요한지도 자연스럽게 이어질 거야.
