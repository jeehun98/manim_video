# Global Memory — 확정165초

0–8초

GPU에서는 레지스터가 스레드의 계산값을 보관하고, 공유 메모리는 같은 블록의 스레드들이 데이터를 공유하고 재사용하도록 합니다.

8–12초

그렇다면 GPU가 처리하는 대규모 데이터는 어디에 저장될까요?

12–15초

바로 전역 메모리, Global Memory입니다.

15–21초

전역 메모리는 GPU의 여러 SM과 블록에서 접근할 수 있는 대용량 메모리 공간입니다.

21–26초

일반적으로 레지스터나 공유 메모리보다 용량이 크지만, 접근 지연도 상대적으로 큽니다.

26–28초

실제 CUDA 코드를 살펴보겠습니다.

28–34초

두 배열을 더하는 커널에서 각 스레드는 전역 메모리의 배열 A와 B에서 값을 읽어옵니다.

34–37초

그리고 두 값을 더한 결과를 배열 C에 저장합니다.

37–41초

이때 읽어온 값과 중간 결과는 레지스터에 보관될 수 있습니다.

41–48초

즉, 전역 메모리에서 데이터를 가져와 계산한 뒤, 결과를 다시 전역 메모리에 저장하는 것입니다.

48–50초

그런데 여기서 흥미로운 문제가 발생합니다.

50–56초

같은 양의 데이터를 읽더라도, 스레드들이 접근하는 메모리 주소에 따라 실제 메모리 요청량이 달라질 수 있습니다.

56–60초

하나의 워프에 속한 32개 스레드를 생각해 보겠습니다.

60–65초

각 스레드가 4바이트의 실수 하나를 읽는다면, 필요한 데이터는 모두 128바이트입니다.

65–70초

먼저 32개 스레드가 연속된 주소의 데이터를 읽는 경우입니다.

70–76초

주소가 적절히 정렬되어 있다면, 필요한 데이터는 연속된 128바이트 영역에 모여 있습니다.

76–81초

이때 GPU는 메모리 접근을 32바이트 단위의 네 개 섹터로 처리할 수 있습니다.

81–86초

그렇다면 스레드들이 서로 여덟 개 원소 간격으로 떨어진 주소를 읽으면 어떻게 될까요?

86–92초

각 스레드가 읽는 데이터는 여전히 4바이트이고, 전체 필요한 데이터도 128바이트로 같습니다.

92–100초

하지만 요청한 주소들이 넓은 범위에 흩어져 있기 때문에, 이 예시에서는 32개의 서로 다른 섹터에 접근해야 합니다.

100–103초

네 개였던 섹터가 32개로 늘어난 것입니다.

103–109초

즉, 실제 계산에 사용하는 데이터는 같지만, 섹터 기준으로 처리해야 하는 데이터 양은 여덟 배로 증가합니다.

109–117초

이처럼 같은 워프의 스레드들이 요청한 메모리 주소를 분석해, 필요한 메모리 접근으로 묶어 처리하는 것을 Memory Coalescing이라고 합니다.

117–122초

여기서 중요한 것은 단순히 데이터를 얼마나 많이 읽느냐가 아닙니다.

122–127초

스레드들이 어떤 주소에 접근하는지가 메모리 시스템의 효율을 바꿀 수 있다는 것입니다.

127–132초

물론 섹터 수가 여덟 배로 증가했다고 실행시간까지 여덟 배가 되는 것은 아닙니다.

132–137초

실제 성능은 캐시와 메모리 대역폭, 다른 연산의 실행 시간에도 영향을 받습니다.

137–149초

앞서 살펴본 공유 메모리의 Bank Conflict가 메모리 뱅크에 접근하는 방식의 문제였다면, 코얼레싱은 워프의 전역 메모리 주소들이 얼마나 효율적으로 처리되는가의 문제입니다.

149–158초

결국 전역 메모리는 GPU 전체가 접근하는 대용량 저장 공간이지만, 그 성능은 단순히 메모리의 용량이나 속도만으로 결정되지 않습니다.

158–165초

GPU 최적화에서는 같은 계산을 수행하더라도, 스레드들이 데이터에 접근하는 주소 패턴을 어떻게 구성하는지가 중요합니다.
