# Register — 사용자 확정175초

0–5초

GPU에서는 스레드가 워프와 블록을 구성하고, SM에 배치되어 명령을 실행합니다.

5–9초

지금까지는 이러한 GPU의 실행 구조를 살펴봤습니다.

9–14초

그렇다면 스레드가 계산하는 동안 사용하는 데이터는 어디에 저장될까요?

14–18초

이번에는 GPU의 실행 구조에서 메모리 계층으로 관점을 옮겨보겠습니다.

18–21초

가장 먼저 살펴볼 것은 레지스터입니다.

21–27초

레지스터는 GPU에서 연산에 필요한 값과 중간 결과를 빠르게 저장하는 하드웨어 자원입니다.

27–30초

하나의 스레드가 두 숫자를 더하는 계산을 생각해 보겠습니다.

30–32초

실제 CUDA 코드를 살펴보겠습니다.

32–36초

스레드는 배열 A와 B에서 각각 하나의 값을 읽어옵니다.

36–41초

그리고 두 값을 더해 중간 결과를 만든 다음, 출력 배열 C에 저장합니다.

41–46초

이 과정에서 입력값과 중간 결과를 보관하기 위해 레지스터가 사용될 수 있습니다.

46–51초

하지만 코드에 등장하는 지역 변수 하나가 반드시 레지스터 하나에 대응하는 것은 아닙니다.

51–55초

실제 레지스터의 할당은 컴파일러가 결정합니다.

55–58초

그렇다면 레지스터는 스레드 안에 존재하는 메모리일까요?

58–59초

그렇지는 않습니다.

59–64초

레지스터는 실제 하드웨어 실행 장치인 SM의 레지스터 파일에 존재합니다.

64–69초

각 스레드는 이 자원의 일부를 할당받아 자신만의 계산 값을 유지합니다.

69–71초

그런데 여기서 문제가 발생합니다.

71–75초

SM이 보유한 레지스터의 총량은 제한되어 있습니다.

75–79초

예를 들어 하나의 블록에 128개의 스레드가 있다고 생각해 보겠습니다.

79–85초

스레드마다 레지스터를 32개 사용하면, 블록 하나에는 4,096개의 레지스터가 필요합니다.

85–91초

하지만 스레드마다 64개를 사용하면, 필요한 레지스터는 8,192개로 증가합니다.

91–95초

같은 블록이라도 레지스터 사용량이 두 배가 된 것입니다.

95–102초

이처럼 레지스터 사용량이 많아지면, 하나의 SM에 동시에 배치할 수 있는 블록과 워프의 수가 줄어들 수 있습니다.

102–105초

이러한 자원 제약과 관련된 개념이 Register Pressure입니다.

105–108초

이전 영상에서 살펴본 Occupancy와도 연결됩니다.

108–114초

상주할 수 있는 워프가 줄어들면, 메모리 대기 시간을 숨기는 데 불리해질 수 있기 때문입니다.

114–117초

그렇다면 레지스터가 부족할 때는 어떻게 될까요?

117–121초

컴파일러는 일부 값을 레지스터 대신 다른 메모리 공간에 저장할 수 있습니다.

121–124초

이를 Register Spilling이라고 합니다.

124–127초

일반적으로 이러한 값은 로컬 메모리에 저장됩니다.

127–133초

하지만 로컬 메모리라는 이름과 달리, 실제 저장에는 디바이스 메모리 계층이 사용됩니다.

133–137초

따라서 값을 읽고 저장하기 위한 추가적인 메모리 접근이 발생할 수 있습니다.

137–143초

결국 레지스터를 많이 사용하는 것이 항상 좋은 것도, 적게 사용하는 것이 항상 좋은 것도 아닙니다.

143–150초

충분한 레지스터는 중간값을 빠르게 처리하는 데 유리하지만, 과도한 사용은 동시에 실행할 수 있는 워프의 수를 제한할 수 있습니다.

150–158초

여기서 중요한 점은 레지스터 사용량이 단순히 저장 공간의 문제가 아니라, GPU 전체의 실행 효율에도 영향을 준다는 사실입니다.

158–166초

결국 레지스터는 스레드의 계산을 빠르게 지원하는 저장 공간이면서, SM의 병렬 실행 규모를 제한할 수도 있는 하드웨어 자원입니다.

166–175초

GPU 최적화에서는 연산을 얼마나 빠르게 수행하는지만큼, 그 연산에 필요한 데이터를 어디에 저장하고 얼마나 효율적으로 사용하는지도 중요합니다.
