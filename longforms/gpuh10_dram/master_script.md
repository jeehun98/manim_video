# Memory Controller & DRAM — 확정164초

0–5초

GPU에서 전역 메모리는 여러 SM과 블록이 접근할 수 있는 대용량 메모리 공간입니다.

5–10초

그런데 전역 메모리라는 공간의 데이터는 실제로 어디에 저장되어 있을까요?

10–15초

여기서 구분해야 할 것이 논리적인 메모리 공간과 물리적인 저장 장치입니다.

15–23초

전역 메모리는 CUDA 프로그램이 접근하는 주소 공간이고, 그 데이터를 실제로 저장하는 장치는 일반적으로 DRAM입니다.

23–28초

그렇다면 SM에서 발생한 메모리 요청은 어떻게 DRAM까지 전달될까요?

28–30초

GPU의 전체 구조를 살펴보겠습니다.

30–35초

여러 SM에서 발생한 메모리 요청은 캐시와 메모리 시스템을 통해 처리됩니다.

35–40초

앞서 살펴본 L1과 L2 캐시에 필요한 데이터가 없다면, DRAM에 접근해야 할 수 있습니다.

40–45초

이때 중요한 역할을 하는 하드웨어가 메모리 컨트롤러, Memory Controller입니다.

45–51초

메모리 컨트롤러는 DRAM에 대한 읽기와 쓰기 요청을 조정하고, 실제 메모리 동작을 제어합니다.

51–53초

실제 CUDA 코드를 살펴보겠습니다.

53–58초

스레드가 전역 메모리의 배열 A에서 하나의 값을 읽는다고 생각해 보겠습니다.

58–63초

요청한 데이터가 캐시에 존재하지 않아 DRAM 접근이 필요한 상황을 가정해 보겠습니다.

63–67초

이 요청은 메모리 시스템을 거쳐 해당 메모리 컨트롤러로 전달됩니다.

67–71초

메모리 컨트롤러는 DRAM에서 필요한 데이터를 읽도록 명령을 처리합니다.

71–76초

그리고 읽어온 데이터는 다시 메모리 시스템을 통해 요청한 SM으로 전달됩니다.

76–81초

데이터가 준비되면 스레드는 해당 값을 이용한 계산을 진행할 수 있습니다.

81–85초

그렇다면 메모리 컨트롤러가 단순히 주소를 전달하는 장치일까요?

85–86초

그렇지는 않습니다.

86–92초

DRAM은 거대한 숫자 배열처럼 보이지만, 실제 내부는 여러 뱅크와 행, 열로 구성되어 있습니다.

92–94초

하나의 뱅크를 살펴보겠습니다.

94–100초

DRAM은 데이터를 읽기 위해 필요한 행을 활성화하고, 그 안에서 원하는 데이터에 접근합니다.

100–105초

만약 필요한 행이 이미 활성화되어 있다면, 새로운 행을 열어야 하는 경우와 처리 과정이 달라집니다.

105–110초

메모리 컨트롤러는 이러한 DRAM의 동작과 타이밍을 고려해 메모리 요청을 처리합니다.

110–116초

따라서 같은 양의 데이터를 읽더라도 물리적인 접근 상태에 따라 지연시간이 달라질 수 있습니다.

116–120초

그렇다면 GPU의 DRAM은 모두 같은 종류일까요?

120–124초

대표적으로 GDDR과 HBM이 있습니다.

124–129초

GDDR은 일반적인 그래픽카드에서 널리 사용되는 고속 메모리입니다.

129–136초

반면 HBM은 메모리 칩을 수직으로 적층하고 넓은 데이터 인터페이스를 활용해 높은 대역폭을 제공합니다.

136–141초

두 방식 모두 GPU의 전역 메모리를 구현하는 물리적인 DRAM 기술입니다.

141–149초

결국 전역 메모리는 CUDA 프로그램에서 사용하는 논리적인 주소 공간이고, DRAM은 데이터를 실제로 저장하는 물리적 장치입니다.

149–153초

그리고 메모리 컨트롤러는 이 DRAM에 대한 읽기와 쓰기를 조정하는 하드웨어입니다.

153–157초

GPU의 메모리 계층은 SM과 캐시에서 끝나는 것이 아닙니다.

157–164초

그 뒤에는 메모리 요청을 처리하는 컨트롤러와, 실제 데이터를 보관하는 DRAM의 물리적 구조가 존재합니다.
