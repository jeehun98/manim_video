# GPU 개론 11 — 레지스터에 없는 데이터는 어떻게 계산할까?

상세 영상화 콘티 · 총 174초(2분 54초) · 9:16 세로 영상 · Manim 기반 2D 모션그래픽

이번 편의 핵심은 10편에서 완성한 프로세서에 데이터 메모리와 새로운 데이터 경로를 실제로 추가하는 과정이야.

메모리, Load, Store라는 용어를 먼저 보여주는 대신, 시청자가 다음과 같은 구조적 변화를 순서대로 발견하도록 구성하는 게 좋아.

이번 편에서 확장할 하드웨어

영상 후반에 완성할 구조의 개념도. 실제 구현에서는 ALU의 두 입력, 메모리 읽기·쓰기 제어, 목적지 레지스터 선택 등을 각각 연결한다.

## 전체 연출 방향

기존 회로를 없애지 않는 것이 가장 중요해.

10편에서 이미 만든 PC, 명령어 메모리, 해독 회로, 레지스터, MUX, ALU는 화면에 유지해. 이번에는 데이터 메모리와 쓰기 경로를 추가하는 장면만 새로운 내용으로 보여주면 돼.

중앙에는 레지스터 → ALU → 데이터 메모리 → 레지스터라는 연결 구조만 크게 보여주는 것이 좋아.

# ACT 1. 레지스터만으로 모든 데이터를 저장할 수 있을까?

00:00–00:30 · 기존 프로세서 구조에서 새로운 제약을 발견한다.

### 00:00–00:06 — 앞서 완성한 기본 프로세서

나레이션: 앞서 우리는 명령어를 순서대로 가져오고, 해독하고, 실행하는 기본적인 프로세서 구조를 만들었습니다.

화면 연출

10편 마지막에 완성했던 프로세서 전체 구조를 화면 중앙에 배치해.

상단 왼쪽에는 PC, 오른쪽에는 Instruction Memory가 있고, 아래쪽에 Decoder, Registers, ALU가 있어.

PC가 주소 0을 선택하고 명령어가 해독 회로로 전달되는 모습을 짧게 재생해.

이후 레지스터의 숫자 5와 3이 ALU에서 계산되는 장면으로 연결해.

연출 의도: 이전 편에서 사용한 장치의 형태를 그대로 유지해 11편이 같은 회로를 확장하는 이야기라는 사실을 전달해.

### 00:06–00:10 — 레지스터의 숫자로 계산한다

나레이션: 이제 레지스터에 저장된 숫자를 이용해 여러 계산을 수행할 수 있습니다.

화면 연출

프로세서 전체를 축소하고 레지스터 세 개와 ALU만 확대해.

R1에 5, R2에 3을 표시해.

ALU 내부에서 ADD 경로가 활성화되고 출력에 8이 나타나.

R3가 클럭에 맞춰 8로 갱신되는 과정을 보여줘.

### 00:10–00:15 — 지금까지의 가정

나레이션: 그런데 지금까지는 계산할 숫자가 이미 레지스터에 저장되어 있다고 가정했습니다.

화면 연출

R1의 5와 R2의 3을 밝게 강조해.

그다음 두 숫자 위에 `처음부터 저장되어 있던 값`이라는 작은 문구를 표시해.

화면에서 R1과 R2의 숫자가 사라지고 빈 레지스터가 남아.

ALU에는 더 이상 유효한 입력 예시가 표시되지 않아.

여기서는 실제 레지스터가 물리적으로 완전히 비어 있다는 의미보다, 설명에 사용할 피연산자 값이 아직 준비되지 않았다는 뜻으로 표현해.

### 00:15–00:19 — 계산할 숫자가 수천 개라면?

나레이션: 만약 계산해야 할 숫자가 수백 개, 수천 개라면 어떨까요?

화면 연출

기존 레지스터 네 개가 화면 왼쪽에 나타나.

오른쪽에서는 `1, 2, 3, 4, 5, ...` 같은 숫자 카드들이 빠르게 늘어나.

숫자들은 4개에서 16개, 64개, 수백 개로 확장되는 느낌으로 표현해.

시청자가 실제로 수천 개의 숫자를 세지 않아도, 저장할 데이터가 훨씬 많다는 것을 인식할 수 있도록 화면 밖까지 이어지는 숫자 배열을 사용해.

### 00:19–00:23 — 저장 용량의 한계

나레이션: 레지스터의 개수와 저장할 수 있는 데이터의 양은 제한되어 있습니다.

화면 연출

레지스터 영역을 화면 중앙에 고정해.

수많은 숫자 카드 중 네 개만 레지스터에 들어가고, 나머지는 저장할 공간이 없는 상태로 남아.

상단에 `제한된 레지스터 용량`이라는 문구를 표시해.

이때 레지스터가 실제로 꽉 차서 오류가 발생한다는 표현보다, 프로세서 내부의 빠른 저장 장소만으로는 모든 데이터를 동시에 보관하기 어렵다는 점에 집중해.

### 00:23–00:30 — 별도의 저장 공간을 만들자

나레이션: 그렇다면 모든 숫자를 레지스터에 보관하는 대신, 별도의 저장 공간에 두고 필요한 값만 가져오면 어떨까요?

화면 연출

레지스터 영역을 화면 왼쪽으로 이동시켜.

오른쪽에 빈 사각형 저장 공간을 추가해.

화면에 흩어져 있던 숫자 카드들이 오른쪽 저장 공간 안으로 정렬돼 들어가.

왼쪽에는 소수의 레지스터, 오른쪽에는 많은 숫자가 들어 있는 별도 저장 공간이 남아.

아직 `Memory`라는 명칭은 등장시키지 않아.

핵심: 문제를 제시한 뒤 해결용 구조를 먼저 만든다.

# ACT 2. 저장된 데이터의 위치를 어떻게 지정할까?

00:30–00:57 · 저장 장소를 만들고, 위치 선택 기능을 추가한 후 이름을 소개한다.

### 00:30–00:34 — 여러 숫자가 저장된 공간

나레이션: 예를 들어 여러 숫자가 저장된 공간을 생각해 보겠습니다.

화면 연출

오른쪽 저장 공간을 중앙으로 확대해.

여러 개의 칸이 세로로 정렬된 배열을 보여줘.

처음에는 8개의 칸을 표시하고, 각 칸에는 서로 다른 숫자가 저장되어 있어.

그중 첫 번째와 두 번째 칸만 밝게 강조하고 나머지는 회색으로 표현해.

### 00:34–00:38 — 첫 번째 위치에는 5, 두 번째에는 3

나레이션: 첫 번째 위치에는 5가, 두 번째 위치에는 3이 저장되어 있습니다.

화면 연출

첫 번째 칸에 5, 두 번째 칸에 3을 크게 표시해.

예시의 일관성을 위해 실제 주소 표시는 다음과 같이 정의하자.

`100 → 5`

`101 → 3`

첫 번째와 두 번째라는 표현은 설명상 순서이고, 실제로는 주소 100과 101이라는 위치 식별자를 부여할 거야.

이때 주소 숫자는 아직 작은 글씨로만 보여줘.

### 00:38–00:43 — 필요한 값을 어떻게 선택할까?

나레이션: 여기서 특정한 숫자를 가져오려면, 어느 위치에 있는 값인지 지정할 수 있어야 합니다.

화면 연출

저장 공간 아래쪽에 하나의 출력선을 추가해.

모든 칸을 동시에 출력선으로 보내는 방식이 아니라, 하나의 위치가 선택되어 출력에 나타나는 모습을 보여줘.

처음에는 첫 번째 칸의 값 5가 출력되고, 다음에는 두 번째 칸의 값 3이 출력돼.

그런데 어떤 기준으로 칸이 선택되는지 아직 설명하지 않았으므로, 왼쪽에 `선택 정보 ?`를 표시해.

### 00:43–00:47 — 주소라는 개념의 등장

나레이션: 이처럼 저장 공간의 각 위치를 구분하는 값을 주소라고 합니다.

화면 연출

저장 공간 왼쪽에 각 칸의 위치를 나타내는 숫자를 표시해.

`100`, `101`, `102`, `103`…

상단에 `Address`라는 명칭을 등장시켜.

이후 주소 100과 101을 교대로 강조해.

주소를 숫자 데이터와 혼동하지 않도록 주소는 주황색, 저장된 값은 보라색으로 표시해.

### 00:47–00:51 — 주소에 따라 데이터 읽기

나레이션: 주소를 전달하면 해당 위치에 저장된 데이터를 선택해 읽어 올 수 있습니다.

화면 연출

저장 공간 왼쪽에 `Address Input`을 연결해.

입력값이 100이면 주소 100 칸이 강조되고 출력에 5가 나타나.

입력값을 101로 바꾸면 주소 101 칸이 강조되고 출력이 3으로 바뀌어.

주소 선택 애니메이션 참고

Address

# 100

1005101310201030

Read Data

# 5

영상에서는 클릭 UI 대신 주소 숫자가 100에서 101로 변하면서 선택된 칸과 출력값이 부드럽게 바뀌는 애니메이션으로 구현해.

### 00:51–00:57 — 데이터 메모리라는 이름 부여

나레이션: 이렇게 주소를 이용해 데이터를 보관하고 읽고 쓸 수 있는 저장 공간을 데이터 메모리라고 합니다.

화면 연출

저장 공간의 외곽에 하나의 테두리가 생겨.

그 위에 `Data Memory`라는 명칭을 표시해.

왼쪽에는 `Address`, 오른쪽에는 `Read Data`, 아래쪽에는 `Write Data`와 `Write Enable` 입력이 단계적으로 추가돼.

다만 이때 쓰기 동작을 자세하게 보여주지는 않고, 읽기 기능까지 설명한 구조에 쓰기 가능성을 예고하는 수준으로 끝내.

기술적 주의: 메모리 읽기와 쓰기는 서로 다른 제어 동작이야. 메모리 블록에 주소를 전달하는 것만으로 자동으로 값이 변경되는 것처럼 표현하면 안 돼.

# ACT 3. 메모리에서 읽은 값을 어디로 보낼까?

00:57–01:33 · 기존 ALU 결과 경로에 메모리 읽기 경로를 추가하고 MUX를 구성한다.

이번 구간은 11편에서 가장 중요한 구조 확장 장면이야.

새로운 데이터 메모리를 만들었지만, 그것만으로 기존 프로세서에서 메모리의 값을 사용할 수 있는 것은 아니지.

이미 만들어 둔 레지스터 파일과 연결할 필요가 있어.

### 00:57–01:01 — 메모리에서 읽기만 해서는 계산할 수 없다

나레이션: 그런데 메모리에서 숫자를 읽어 왔다고 해서 바로 계산이 끝나는 것은 아닙니다.

화면 연출

화면 오른쪽에 데이터 메모리를 배치해.

주소 100을 선택하고 출력에 5가 나타나는 장면을 보여줘.

왼쪽에는 기존 레지스터와 ALU가 있어.

메모리의 `Read Data = 5` 출력선은 아직 어디에도 연결되어 있지 않아.

화면 상단에 `읽어 온 5를 어디에 연결할까?`를 표시해.

### 01:01–01:06 — 기존 ALU의 입력은 레지스터에서 왔다

나레이션: 지금까지 우리가 만든 ALU는 레지스터에서 전달된 값을 이용해 계산했습니다.

화면 연출

기존 8편 데이터 경로를 다시 강조해.

레지스터의 R1=5와 R2=3이 두 개의 선택 경로를 통해 ALU로 전달돼.

ALU 내부 ADD 경로가 활성화되고 8을 출력해.

여기서 ALU 입력은 두 개라는 점을 명확히 유지하고, 데이터 메모리는 아직 경로에 포함하지 않아.

### 01:06–01:11 — 메모리 결과를 레지스터로 보내자

나레이션: 따라서 메모리에서 읽은 값도 레지스터에 저장할 수 있도록 새로운 연결이 필요합니다.

화면 연출

오른쪽 데이터 메모리에서 왼쪽 레지스터 방향으로 새로운 보라색 경로가 나타나.

다만 기존 ALU 출력도 레지스터로 돌아오고 있으므로, 두 경로가 하나의 입력을 공유해야 한다는 문제가 생겨.

두 경로가 레지스터의 Write Data 입력 앞에서 나란히 멈춰.

아직 두 경로를 직접 합치지는 않아.

### 01:11–01:15 — 기존의 계산 결과 저장 경로

나레이션: 기존에는 ALU의 계산 결과가 레지스터로 돌아갔습니다.

화면 연출

데이터 메모리의 새 경로는 잠시 어둡게 처리해.

ALU에서 출력된 8이 기존 쓰기 경로를 따라 레지스터 R3의 입력에 전달되는 모습을 보여줘.

이어서 클럭 에지에서 R3가 8로 갱신돼.

이전 영상에서 이미 설명한 동작이므로 4초 이내로 간결하게 표현해.

### 01:15–01:20 — 두 번째 결과 경로 추가

나레이션: 여기에 메모리에서 읽은 데이터가 돌아오는 경로를 하나 더 추가하면 어떨까요?

화면 연출

메모리에서 읽은 숫자 5의 출력선을 레지스터 쓰기 입력 방향으로 연장해.

기존 ALU 출력선과 새로운 메모리 출력선이 나란히 배치돼.

화면 중앙에 두 개의 후보 값을 표시해.

`ALU Result = 8`

`Memory Read = 5`

레지스터에 기록할 수 있는 데이터의 출처가 두 개라는 사실을 보여줘.

### 01:20–01:24 — 둘 중 하나를 선택해야 한다

나레이션: 그리고 두 경로 중 하나를 선택해 레지스터에 기록하도록 만드는 것입니다.

화면 연출

ALU 출력과 메모리 출력의 두 배선이 하나의 빈 선택 블록으로 들어가.

선택 블록의 출력은 레지스터의 쓰기 데이터 입력으로 이어져.

처음에는 ALU 결과 8을 선택하고, 다음에는 메모리 결과 5를 선택해.

이때 선택되지 않은 입력선은 제거하지 말고 회색으로 유지해.

### 01:24–01:28 — MUX의 재등장

나레이션: 여기서 앞서 살펴본 MUX를 다시 사용할 수 있습니다.

화면 연출

선택 블록에 `MUX`라는 명칭이 등장해.

아래쪽에는 `Select` 제어선이 추가돼.

상단의 ALU 결과, 아래쪽의 메모리 결과가 MUX로 연결되고, 그중 하나가 레지스터의 Write Data 입력으로 전달돼.

새롭게 추가되는 Writeback MUX

ALU 결과메모리 결과

레지스터에 기록할 데이터의 출처를 선택한다. 실제 기록은 목적지 레지스터 선택 및 쓰기 허용 조건이 만족될 때 수행된다.

이 장면에서 8편에서 다뤘던 MUX와의 차이를 아주 짧게 보여주면 좋아.

8편의 MUX는 ALU에 어떤 데이터를 입력할지 선택했어.

이번 MUX는 레지스터에 어떤 결과를 저장할지 선택하는 거야.

원리는 같지만 배치되는 위치와 용도가 달라졌다는 점이 핵심이지.

### 01:28–01:33 — 레지스터가 두 종류의 결과를 저장할 수 있다

나레이션: 이제 레지스터에는 ALU의 결과뿐 아니라 메모리에서 가져온 값도 저장할 수 있게 되었습니다.

화면 연출

ALU와 데이터 메모리, Writeback MUX, 레지스터를 모두 한 화면에 배치해.

ALU Result를 선택하면 R3에 8이 저장되고, Memory Read를 선택하면 R1에 5가 저장되는 두 가지 상황을 짧게 전환해.

이때 MUX가 값의 출처를 선택하는 것과 목적지 레지스터를 선택하는 것은 별개라는 사실이 표현돼야 해.

따라서 화면 아래에 두 신호를 구분해 표시해.

`Write Data Source`

`Destination Register`

# ACT 4. 새로운 데이터 이동을 명령어로 지정한다

### 01:33–01:39 — 아직 제어해야 할 정보가 남아 있다

나레이션: 하지만 실제로 어떤 주소의 데이터를 읽고, 어느 레지스터에 기록할지는 여전히 결정해야 합니다.

화면 연출

완성된 데이터 경로 위쪽에 세 개의 빈 제어 항목이 나타나.

`Memory Address = ?`

`Write Data Source = ?`

### 01:39–01:43 — 기존 명령어 해독 회로 재사용

나레이션: 앞서 우리는 이러한 동작을 명령어로 표현하는 방법을 만들었습니다.

화면 연출

`ADD R3, R1, R2` 명령어가 ALU의 연산 종류와 레지스터 주소를 지정했던 장면을 2초 정도 재현해.

이후 화면에 남은 새 제어 정보인 메모리 주소와 데이터 출처 선택으로 강조 영역이 이동해.

### 01:43–01:49 — 메모리에서 가져오는 명령을 만들어 보자

나레이션: 그렇다면 메모리의 특정 위치에서 값을 읽어 레지스터에 저장하라는 명령도 만들 수 있겠지요.

화면 연출

명령어 블록 안에 다음 세 정보가 차례로 나타나.

`읽을 주소: 100`

`저장 위치: R1`

`동작: 메모리 읽기`

아직 LOAD라는 단어는 표시하지 않아.

명령어가 해독되면 메모리 주소 100과 목적지 R1, MUX의 메모리 입력 선택 신호가 설정되는 과정을 보여줘.

### 01:49–01:51 — Load 명령어 등장

나레이션: 이것이 Load 명령어의 기본적인 역할입니다.

화면 연출

앞서 표시했던 세 가지 동작 정보를 하나의 가상 명령어로 묶어.

`LOAD R1, [100]`

명령어 위쪽에 `Load`라는 명칭이 크게 나타나고, 아래쪽에는 `Memory → Register`라는 간단한 방향 표시를 보여줘.

여기서는 기존 9편의 8비트 ADD 명령어 형식을 그대로 적용하려고 하면 안 돼. 주소 100을 포함하는 새로운 명령어 형식이 필요하기 때문이야.

이번 영상에서는 사람이 읽을 수 있는 명령어 표기만 사용하고, 정확한 비트 인코딩은 생략하는 것이 자연스러워.

### 01:51–01:56 — 주소 100의 숫자 5를 R1에 가져오기

나레이션: 예를 들어 주소 100에 저장된 숫자 5를 첫 번째 레지스터로 가져올 수 있습니다.

화면 연출

메모리 주소 100이 강조돼.

그 위치의 저장값 5가 Read Data 출력으로 나타나.

Writeback MUX가 메모리 출력을 선택해.

MUX 출력에 5가 나타나고 R1의 쓰기 데이터 입력으로 전달돼.

유효한 클럭 에지에서 R1이 `0 → 5`로 갱신돼.

마지막 화면 상태: `R1 = 5`, `Memory[100] = 5`

읽기가 메모리 값을 제거하지 않는다는 점을 명확히 보여줘.

### 01:56–02:02 — 계산 결과를 다시 메모리에 저장하고 싶다면?

나레이션: 반대로 계산한 결과를 레지스터에만 보관하지 않고, 메모리에 다시 기록하고 싶을 수도 있습니다.

화면 연출

이번에는 R3에 저장된 8을 강조해.

데이터 메모리 주소 102에는 초기값 0이 저장되어 있어.

R3의 값 8에서 메모리 방향으로 새로운 보라색 경로가 나타나.

기존 Load 경로와 방향이 반대라는 점을 보여줘.

### 02:02–02:06 — 메모리에 쓸 주소 지정

나레이션: 이번에는 레지스터의 값을 메모리로 전달하고, 기록할 주소를 지정하면 됩니다.

화면 연출

R3 출력이 메모리의 Write Data 입력으로 연결돼.

`Address = 102`가 설정되고, `Write Enable` 신호가 활성화돼.

메모리의 주소 102가 밝아지면서 기존 값 0이 8로 변경돼.

주소를 전달하는 것과 실제 쓰기 제어를 구분할 수 있도록, 메모리 값이 변하는 순간에만 Write Enable을 초록색으로 강조해.

### 02:06–02:12 — Store라는 이름 부여

나레이션: 이처럼 레지스터의 값을 메모리의 지정된 위치에 기록하는 동작을 Store라고 합니다.

화면 연출

지금까지 구현한 동작이 하나의 명령어 표기로 정리돼.

`STORE R3, [102]`

# ACT 5. 레지스터에 없는 두 숫자를 실제로 계산한다

여기서는 새로운 회로를 추가하지 않아.

오직 지금까지 만든 구조만 이용해 메모리에 저장된 숫자 두 개를 더한 뒤 다시 메모리에 기록하는 프로그램을 실행해.

이 장면이 11편 전체의 결론이야.

### 02:12–02:17 — 메모리의 숫자 두 개를 가져온다

나레이션: 이제 우리는 메모리에 저장된 5와 3을 각각 레지스터로 가져올 수 있습니다.

화면 연출

화면 중앙에 확장된 데이터 경로를 보여줘.

상단에는 다음 가상 명령어를 표시해.

`LOAD R1, [100]`

메모리 주소 100에서 5를 읽어 R1에 저장하는 애니메이션을 수행해.

이어서 두 번째 명령어를 보여줘.

`LOAD R2, [101]`

마지막 화면에는 R1=5와 R2=3이 표시돼.

이때 두 Load 명령어가 동시에 처리되는 것처럼 보이지 않도록, 한 명령어의 결과 저장 후 다음 명령어를 실행하는 순서로 보여줘.

### 02:17–02:20 — ALU에서 계산한다

나레이션: ALU로 두 값을 더하면 결과인 8이 만들어집니다.

화면 연출

세 번째 명령어를 표시해.

`ADD R3, R1, R2`

R1과 R2에서 두 개의 읽기 경로가 활성화돼.

ALU가 ADD 연산을 수행하고 결과 8을 출력해.

Writeback MUX는 이번에는 메모리가 아니라 ALU 결과를 선택해.

R3가 8로 갱신돼.

### 02:20–02:23 — 계산 결과를 메모리에 저장한다

나레이션: 그리고 이 결과를 다시 메모리에 기록할 수도 있습니다.

화면 연출

네 번째 명령어를 표시해.

`STORE R3, [102]`

R3의 값 8이 메모리 Write Data 입력으로 전달돼.

주소 102가 선택되고 쓰기 동작이 발생하면, 메모리의 값이 `0 → 8`로 바뀌어.

이제 메모리에는 다음 상태가 남아.

`Memory[100] = 5`

`Memory[101] = 3`

`Memory[102] = 8`

### 02:23–02:28 — 기존 구조의 한계 회상

나레이션: 기존에는 계산할 숫자가 레지스터에 미리 저장되어 있어야 했습니다.

화면 연출

화면을 좌우로 나눠.

왼쪽에는 이전 10편의 구조를 배치해.

`Registers → ALU → Registers`

오른쪽에는 이번 11편의 확장 구조를 배치해.

`Memory ↔ Registers → ALU`

새롭게 추가된 데이터 메모리와 읽기·쓰기 경로만 보라색으로 강조해.

### 02:28–02:33 — 메모리 데이터까지 계산할 수 있다

나레이션: 하지만 이제는 별도의 메모리에서 데이터를 가져오고, 계산한 뒤 다시 저장할 수 있게 된 것입니다.

좌우 비교를 종료하고 확장된 프로세서 구조 하나만 크게 보여줘.

회로를 따라 다음 순서로 신호를 강조해.

`Memory → Registers → ALU → Registers → Memory`

전체 회로 아래에 다음 문구를 표시해.

`데이터 읽기 → 계산 → 결과 기록`

여기서는 새로운 기능이 추가된 부분만 보라색으로 남기고, 기존 ALU와 레지스터는 10편에서 사용한 색상을 유지하면 좋아.

# ACT 6. 데이터를 가져오는 데 시간이 걸린다면?

### 02:33–02:36 — 새로운 문제 발견

화면 연출

완성된 프로세서 구조를 유지해.

데이터 메모리에서 레지스터로 이어지는 읽기 경로만 강조하고, 나머지 회로는 어둡게 처리해.

### 02:36–02:41 — 메모리 읽기에 시간이 걸린다

나레이션: ALU의 계산과 달리, 메모리에서 데이터를 읽어 오는 데에는 시간이 걸릴 수 있습니다.

데이터 메모리에서 주소 100을 선택해.

메모리의 읽기 요청과 데이터가 준비되는 시점 사이에 간격이 존재한다는 것을 보여줘.

### 02:41–02:48 — 그동안 무엇을 기억해야 할까?

나레이션: 그동안 프로세서는 어떤 명령어를 수행하고 있었는지, 읽어 온 결과를 어디에 저장해야 하는지 기억해야 합니다.

요청한 주소

100

기록할 레지스터

### 02:48–02:54 — 12편으로 연결

나레이션: 다음에는 하나의 명령어가 여러 단계에 걸쳐 실행될 때, 그 과정의 정보를 어떻게 유지하는지 살펴보겠습니다.

`주소 결정 → 데이터 읽기 → 레지스터 기록`

## 제작 시 반드시 지킬 기술적 조건

1\. 주소와 데이터는 서로 다른 정보다. 주소 100은 메모리에서 어느 위치를 선택할지 지정하는 값이고, 그 위치에 저장된 숫자 5는 실제 계산할 데이터야. 두 값을 같은 색상으로 표현하지 않아야 해.

2\. 데이터 메모리와 명령어 메모리의 역할을 구분한다. 이번 영상에서는 이해하기 쉽도록 별도의 블록을 사용하지만, 실제 프로세서에서 두 메모리가 반드시 완전히 분리된 물리 장치여야 하는 것은 아니야.

3\. Load와 Store의 방향을 일관되게 유지한다. Load는 메모리에서 레지스터로 읽어 오는 동작이고, Store는 레지스터 값을 메모리에 기록하는 동작이야. 특히 Store는 일반적인 레지스터 저장 결과를 생성하는 ALU 연산과 구분해야 해.

4\. MUX 선택과 저장 시점은 별개다. MUX는 레지스터 쓰기 입력에 어떤 데이터가 연결될지 선택하는 회로야. 실제 레지스터 저장은 목적지 레지스터와 쓰기 허용, 클럭 등의 조건에 따라 수행돼.

5\. 메모리 접근 지연을 과장하지 않는다. 메모리 종류, 주소, 캐시 상태, 구현 방식에 따라 지연은 달라져. 이번 영상에서는 정확한 사이클 수보다 데이터를 기다리는 동안 필요한 정보를 유지해야 한다는 구조적 문제에 초점을 맞추는 게 좋아.
