# GPU 개론 — 계산의 원리에서 GPU의 구조와 한계까지

2026-11-02 · 사용자 추가 자료 반영 · 구성 검토 단계 · 대본·발화시간 미확정

## 방향

출발 질문은 “컴퓨터는 어떻게 계산하고, GPU는 그 계산 구조를 어떻게 설계했을까?”로 한다. 시청자는 프로그래밍이나 컴퓨터 구조를 배운 적이 없어도 시작할 수 있다. 목표는 부품 이름 암기보다 GPU의 구조가 필요한 이유와 성능이 나오는 조건을 설명하는 것이다.

범위는 GPU 개론 하나에 집중한다. CUDA 문법·API·컴파일·커널 최적화 실습은 후속 별도 기획으로 둔다. 메모리 접근 효율과 Roofline은 하드웨어의 성능을 이해하기 위한 개론 수준으로 다룬다.

1장은 일반적인 계산 장치의 원리로 시작한다. 2장부터 NVIDIA GPU를 구체 사례로 쓰고 SM·Warp·Tensor Core가 모든 GPU의 공통 명칭인 것처럼 표현하지 않는다. 그래픽의 많은 데이터에 대한 계산에서 출발한 역사적 맥락은 2편의 설계 목적 설명 안에 간결하게 넣는다.

## 첫 4편의 역할과 중복 방지

첨부안의 첫 편 후보인 “계산을 빠르게 만드는 두 가지 방법”은 시리즈 전체의 질문 또는 1장 롱폼 제목으로 활용한다. 쇼츠 01에서는 계산 한 번의 구조를 먼저 이해시키고, 속도 지표의 본격 비교는 03에 둔다. 첫 영상에 ALU·CPU/GPU 차이·Latency·Throughput을 모두 넣으면 이후 세 편과 겹치므로 범위를 나눈다.

### 01 — 계산 한 번을 따라가기

질문: 화면에 적은 `3 + 5`를 회로는 어떻게 처리할까?

장면 순서: 두 입력과 ADD 명령 제시 → 저장된 입력을 연산 회로에 공급 → 결과 8 생성 → 결과 저장 → “계산은 명령에 따라 데이터를 읽고, 연산하고, 결과를 남기는 과정”으로 마침.

교육용 데이터 경로 모형이며 실제 명령이 한 클록에 끝나는 장면으로 표시하지 않는다. 정수 덧셈 예제와 이후 부동소수점 연산 유닛 설명을 구별한다.

### 02 — 설계 선택 이해하기

질문: 같은 칩 예산을 어디에 사용할까?

장면 순서: 연산·제어·저장·데이터 공급의 역할 → 서로 다른 작업 특성 → CPU/GPU의 설계 강조점 비교 → GPU의 그래픽 기원 → “좋은 설계는 처리할 작업과 제약에 따라 달라진다”로 마침.

기능 블록의 면적은 설명용이며 실제 트랜지스터 비율로 제시하지 않는다. CPU도 병렬성을 활용하고 GPU도 제어 회로와 캐시가 필요하다는 전제를 유지한다.

### 03 — 속도를 두 지표로 보기

질문: 첫 답이 빨리 나오는 것과 답이 많이 나오는 것은 같을까?

장면 순서: 같은 수의 독립 작업 → 첫 완료까지의 시간 비교 → 일정 시간에 끝난 작업 수 비교 → 두 지표를 각각 표시 → “Latency와 Throughput을 구분해야 빠르다는 말을 정확히 할 수 있다”로 마침.

### 04 — 병렬화의 조건 확인하기

질문: 같은 덧셈 개수라면 장치를 늘릴수록 빨라질까?

장면 순서: 독립 덧셈을 여러 유닛에 분배 → 앞 결과가 필요한 계산 사슬로 교체 → 대기 발생 → Pipeline은 독립 작업의 서로 다른 단계를 겹칠 수 있음을 별도 표시 → “자원뿐 아니라 작업의 의존성이 병렬 실행을 결정한다”로 마침.

병렬화 효과의 개념 비교이며 CPU/GPU 실제 속도 수치로 표현하지 않는다.

## 롱폼의 구성

| 장 | 논리 흐름 | 완결 시 전달할 결론 |
| --- | --- | --- |
| 1 | 한 번의 계산 추적 → 작업 특성 → 설계 예산 → 속도 지표 → 독립 작업·의존 작업·Pipeline 비교 | GPU 이해의 출발점은 계산의 수와 관계, 처리량을 구분하는 것이다. |
| 2 | 칩 전체 지도 → SM의 그룹화 → 제어와 실행 → 명령별 유닛 → 행렬 연산 특화 | GPU는 연산 유닛을 많이 넣는 데 더해 이를 움직일 자원을 조직한 구조다. |
| 3 | 실행 상태 → 그룹 실행 → Lane별 데이터 → 대기와 다른 작업 발행 → 분기 | 많은 실행 흐름을 유지하고 준비된 작업을 진행해야 자원을 활용할 수 있다. |
| 4 | 상태 저장 → 메모리 역할 → 지연과 공급량 → 주소 배치 → 재사용과 성능 상한 | 성능은 연산 능력과 데이터 공급, 실제 작업 특성이 함께 결정한다. |

쇼츠의 설명 애셋과 실험은 재사용한다. 롱폼은 각 쇼츠의 도입을 반복하는 대신 한 실험의 조건을 계속 바꿔 관찰하는 방식으로 재편집한다. 필요하면 별도 연결 씬을 작성한다. 씬 하나에는 주장 하나만 담고 독립 렌더·교체가 가능하도록 한다.

## 제작 기준

- 내부 기획은 문제 → 해결 원리 → 구현 → 비용·한계 순으로 점검한다. 영상에 네 항목을 기계적으로 나열하지는 않는다.
- 처음 등장한 Register는 01에서 역할만, 14에서 다중 실행 상태와 물리 자원으로 심화한다. SM·Warp도 소개 편과 작동 원리 편의 설명 범위를 나눈다.
- 전문 용어는 현상을 먼저 보여준 뒤 붙인다. 초반에는 코드와 추상적 계층도를 동시에 제시하지 않는다.
- 개별 쇼츠는 이전 편 요약·다음 편 예고 없이 완결한다. 장 사이 연결은 제작 내부 구조로만 관리한다.
- 쇼츠는 세로 9:16, 롱폼은 가로 16:9로 제안한다. 같은 애셋을 각 화면비에 맞춰 배치한다.
- 쇼츠의 기획 목표는 90–150초로 두되 대본 검토와 실제 발화시간에 따라 조정한다. 지금은 초 단위 타임라인을 작성하지 않는다.
- CUDA Thread와 물리 연산 유닛을 일대일 대응시키지 않는다. Warp의 32 Lane은 논리적 실행 그룹이며 32개 물리 유닛의 한 클록 실행을 뜻하지 않는다.
- Roofline은 병목과 상한을 이해하는 모형으로 소개하며 실제 성능을 정확히 예측하는 공식처럼 표현하지 않는다.
