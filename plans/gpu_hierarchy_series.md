# GPU 내부의 계산 — 하나의 Thread에서 GPU 전체까지

작성: 2026-10-28. 상태: 사용자 제안에 따른 10편 구성 기준안(거의 확정). 편별 대본 미확정, TTS·발화시간 미제공. 기존 8장·별도 쇼츠 원고 방식은 아래 구성으로 대체한다.

## 제목과 중심 질문

- 롱폼 제목: **GPU 내부의 계산 — 하나의 Thread에서 GPU 전체까지**
- 부제: 하나의 Thread에서 Warp, Block, SM, GPU 전체까지.
- 중심 질문: 왜 GPU는 계산을 여러 단위로 나누고, 각 단위에 서로 다른 자원을 제공하는가?
- 최종 발견: 계산을 묶어 실행하고, 가까운 데이터를 재사용하고, 준비된 작업으로 대기를 덮기 위해 서로 다른 조직 단위가 필요하다. 최적화는 그 조직 안에서 실제 제한 요인을 찾는 일이다.
- 대상: 배열·반복문·행렬곱의 뜻은 알지만 CUDA 실행 모델은 처음인 시청자.
- 범위: NVIDIA CUDA의 기본 실행 모델. 모든 제조사의 GPU에 Warp 32개 규칙을 일반화하지 않는다. 설계 의도는 문서화된 동작의 장점을 설명하는 관점이며 역사적 설계 경위를 단정하지 않는다.

## 전체 서사와 시각 문법

각 편은 `질문 → 구조의 역할 → CUDA 표현 → 실제 동작 → 해당 질문의 결론`으로 완결한다. 쇼츠 10편을 순서대로 결합한 것이 롱폼이며, 별도의 롱폼 내레이션이나 쇼츠 전용 원고를 만들지 않는다. 이전 영상 복습과 이후 영상 예고는 넣지 않는다. 롱폼에서는 같은 계산 대상과 화면 상태를 이어 논리를 연결한다.

도입은 `C[i] = A[i] + B[i]`로 읽기·계산·쓰기를 보여준다. 이후 각 편은 해당 구조를 가장 명확히 드러내는 작은 실행 예제를 사용한다. 배열·타일·Thread의 색과 표기는 통일하고, 마지막 편에서 `C = AB`의 단순 GEMM과 타일 GEMM을 비교한다. 모든 편을 억지로 한 kernel로 설명하지 않는다. 도입 덧셈에 FMA를 넣지 않는다.

화면은 다음 세 구조를 연결한다.

| 구분 | 표현 | 연결 방식 |
|---|---|---|
| 프로그램의 작업 구분 | Thread → Block → Grid | 묶음의 포함 관계 |
| 하드웨어 실행 | Block의 Thread를 Warp로 묶음 → SM에서 실행 → 여러 SM으로 GPU 구성 | 배치·명령 발행 화살표 |
| 데이터와 자원 | Thread별 Register, Block의 Shared Memory, SM의 L1, GPU의 L2, Device Memory | 접근·재사용 화살표 |

`Thread → Warp → Block → SM → GPU`는 관찰 범위를 넓히는 순서다. 물리적 상자 다섯 개를 중첩한 구조도로 고정하지 않는다. Grid는 GPU 안에 설치된 하드웨어 부품으로 그리지 않는다. 한 Block을 한 SM에 배치한 뒤 그 Block의 Warp들이 실행되는 모습을 보인다. 여러 Block이 한 SM에 상주할 수 있음을 함께 표현한다.

줌아웃할 때 출력 원소, 출력 타일, Block 색상과 식별자를 유지한다. 메모리 지도는 옆에 나타나고 접근 범위를 강조한다. 확대 중에도 범례로 논리 단위와 하드웨어를 구분한다. 롱폼은 16:9, 쇼츠는 9:16을 기획 기준으로 하되 같은 도형·데이터를 각 화면비에 재배치한다.

## 10편 구성 — 쇼츠 완성본의 순차 결합

1–5편은 누가 계산하는지, 6–9편은 데이터가 어디에 있는지, 10편은 같은 계산의 성능이 왜 달라지는지를 설명한다. 6편부터는 이미 펼쳐진 GPU 지도를 유지하고 해당 저장 자원으로 확대한다. 전체가 끝없이 줌아웃하는 연출을 강제하지 않는다.

각 90–150초, 통합 18–23분은 편집 목표다. 10편의 개별 범위 합계는 15–25분이므로 전체 목표를 함께 만족하려면 평균 약 108–138초로 구성해야 한다. 이를 발화시간 추정이나 확정 타이밍으로 사용하지 않는다.

| 편 | 구조·질문 | 한 편의 핵심 주장 | CUDA 예제 설계 후보 | 시각적 증거 |
|---|---|---|---|---|
| 01 | Thread — GPU의 스레드 하나는 무엇을 할까? | Thread는 개별 index와 상태로 데이터 작업을 맡는 실행 문맥이다. | 경계 검사 있는 원소별 덧셈, 전역 index, 지역 변수 | 한 원소의 읽기·계산·쓰기와 서로 다른 index |
| 02 | Warp — 왜 GPU는 32개의 스레드를 묶어서 실행할까? | NVIDIA GPU는 Warp의 활성 lane에 명령을 발행하며, 같은 Warp 안에서 경로가 갈라질 때 효율이 낮아질 수 있다. | 동일 조건식을 가진 kernel에 Warp 내 조건이 같은 입력과 섞인 입력 적용 | 32 lane의 공통 명령·개별 데이터·활성 mask |
| 03 | Block — 스레드들은 어떻게 서로 협력할까? | Block은 Thread들이 Shared Memory와 barrier를 사용해 협력하는 범위다. | Block 단위 배열 역순 복사: 공동 적재→barrier→다른 Thread가 적재한 값 읽기 | 여러 Warp가 같은 Block의 데이터를 공유하고 준비를 맞춤 |
| 04 | SM — GPU는 기다리는 동안에도 어떻게 계산할까? | SM은 준비된 다른 상주 Warp의 명령으로 대기를 덮을 수 있다. | 독립 작업이 많은 kernel과 launch 설정, 준비·대기 상태 개념도 | 메모리 대기 시간은 유지하면서 다른 Warp가 실행 |
| 05 | Grid — 수천 개의 스레드는 어떻게 배치될까? | Grid는 Block의 논리적 집합이며 가용 실행 용량에 따라 SM에 배치된다. | 배열 덧셈의 `<<<grid, block>>>`, `blockIdx`, 경계 검사 | 논리 Block 지도와 물리 SM 배치를 별도로 연결 |
| 06 | Register — GPU에서 가장 가까운 저장 공간은 어디일까? | Thread별 값도 SM의 유한한 Register 자원을 사용하며 사용량 증가에 비용이 따른다. | 여러 누적값을 끝까지 사용하는 kernel 변형, compiler 자원 보고 확인 | Thread별 값과 SM Register 할당, 압박·spill 경로 |
| 07 | Shared Memory — 왜 GPU는 같은 데이터를 다시 읽지 않을까? | 명시적 재사용으로 반복 전송을 줄일 수 있지만 접근 bank도 고려해야 한다. | 타일 전치의 직접 접근과 Shared 타일, padding 변형 | Global→Shared 공동 적재, 재사용, bank별 요청 |
| 08 | Global Memory — GPU는 왜 연속된 주소를 좋아할까? | Warp의 주소 분포가 요청에 필요한 메모리 섹터 수에 영향을 준다. | 연속 접근과 stride 접근 kernel, 유효 주소·배열 크기 명시 | 같은 lane 수·읽기 크기에서 주소와 섹터 비교 |
| 09 | Memory Hierarchy — GPU에는 왜 여러 종류의 메모리가 있을까? | 접근 범위·관리 방식·용량·이동 비용이 다른 저장 자원이 함께 필요하다. | 반복 입력을 사용하는 kernel의 변수·Shared 선언·Global 접근 대응 | Register, Shared, L1, L2, DRAM을 GPU 지도에 표시 |
| 10 | GPU Optimization — 같은 계산인데 GPU 실행 속도가 달라지는 이유 | GEMM의 데이터 재사용과 상주 자원 절충이 실제 실행을 바꾼다. | 같은 입력·정밀도·출력의 단순 GEMM과 타일 GEMM | 동일 출력 검증과 적재량·Warp 준비 상태·자원 사용 비교 |

표의 코드 항목은 실제 구현을 위한 설계 후보이며 실행 검증된 코드가 아니다. 사용자 예시의 `{ep.code}`는 자리표시자이므로 최종 대본·화면에는 실제 코드로 대체한다.

## 편별 독립성과 중복 범위

- 01과 06: 01은 Thread마다 값이 있다는 사실, 06은 그 값들이 사용하는 물리적 자원의 한계와 spill을 다룬다.
- 03과 07: 03은 협력 범위와 올바른 동기화, 07은 데이터 재사용과 bank 접근 비용을 다룬다. 03에서 bank·padding을 미리 설명하지 않는다.
- 04와 10: 04는 실행 준비된 Warp 선택과 지연 은닉, 10은 GEMM에서 타일 재사용과 자원·Occupancy 절충을 다룬다.
- 08과 09: 08은 Warp의 주소와 요청 섹터, 09는 전체 저장 자원의 역할과 경로를 다룬다.
- 10은 앞편 복습으로 시작하지 않는다. 두 GEMM의 같은 결과·다른 실행을 처음부터 제시하고 필요한 개념을 그 비교 안에서 설명한다. Roofline은 필요할 때만 짧게 사용하며 별도의 새 강의로 확장하지 않는다.
- 07의 제목은 질문형 후보다. GPU가 자동으로 재읽기를 모두 제거한다는 답으로 연결하지 않고, 프로그램이 데이터를 재사용하도록 설계해야 함을 결론으로 삼는다.
- Warp Shuffle과 Multi-GPU는 이번 필수 범위에서 제외한다. 후속 주제 연결은 내부 참고이며 영상 내 예고로 쓰지 않는다.

## 공통 구성과 화면 계약

사용자가 제시한 약 140초 구성을 순서의 기준으로 사용한다. `0–10초 질문 / 10–35초 구조 / 35–65초 코드 대응 / 65–110초 동작 / 110–140초 결론`은 편집 예시다. 90초 편에 140초 구간을 강제하거나 문장 길이를 비례 배분해 타이밍을 확정하지 않는다. 실제 발화시간 안에서 각 편을 설계한다.

- 구조가 주 화면이고 카메라 전환을 주도한다. 코드 강조는 구조가 등장한 뒤 따른다. 코드 설명 중에도 하드웨어 대상과 연결선을 유지한다.
- 코드 대응은 직접 대응(Thread·Block·Grid), 간접 대응(Warp·SM), 자원 대응(Register·Shared·Global)으로 구별한다. 모든 구조에 일대일 대응 키워드를 붙이지 않는다.
- 하단은 실행 데이터·주소·병목·수식을 표시하고 자막 영역을 별도로 확보한다. 화면당 코드 전체 대신 관련 부분만 크게 표시한다.
- 가로형은 구조 중심 영역과 옆의 코드 영역, 세로형은 위의 구조와 아래의 코드 영역으로 재배치한다. 같은 역할과 색상을 유지하되 가로 화면을 잘라 세로 화면을 만들지 않는다.
- 각 편의 결말은 해당 질문에 대한 답이다. 이전 편 참조·다음 편 예고·구독 유도 등 결합을 방해하는 별도 꼬리를 넣지 않는다.
- 결합본은 같은 화면비의 01–10 완성본을 순서대로 이어 붙인다. 연결 내레이션·추가 대본 없이 성립해야 한다. 쇼츠의 세로형과 같은 내용의 가로형을 만들고 가로 롱폼은 가로형 10편을 결합한다. 세로 완성본 결합도 가능하다.
- 각 편 내부는 주장 하나의 교체 가능한 씬들로 나눈다. 독립 쇼츠 한 편과 내부 제작 씬 하나를 동일 단위로 취급하지 않는다.

## 실행 코드·시각화·Virtual Lab 계약

GPU Virtual Lab은 향후 활용 방향이며 이번 기획에서 Lab 자체를 구현하지 않는다. 코드 예제는 다음 조건으로 설계해 영상과 실험이 같은 내용을 가리키게 한다.

1. 화면의 snippet과 실행용 `.cu` 원본을 연결한다. 실행용 원본에는 할당·초기화·launch·오류 확인·결과 검증·해제를 포함한다. 화면에는 생략한 부분을 명시한다.
2. 입력 크기·배열 배치·block/grid·정밀도·출력 기준을 기록하고 CPU 참조 결과와 비교한다. GEMM은 부동소수점 허용 오차를 명시한다. 일부 크기만 지원하면 그 조건을 분명히 둔다.
3. 시각화의 index·lane·주소·bank·sector는 같은 입력과 코드에서 산출한다. 간단한 수학적 모델과 실제 하드웨어 측정을 구별한다.
4. Warp 발행 순서·SM 배치·latency의 개념도를 실제 장치 trace처럼 제시하지 않는다. CUDA 소스만으로 특정 스케줄을 보장하지 않는다.
5. Register 수·spill·분기 명령은 소스만 보고 단정하지 않고 선택한 compiler·대상 architecture의 산출물을 확인한다. 의도한 현상이 최적화로 사라지면 예제를 조정한다.
6. 성능 비교는 GPU·toolchain·입력·측정 범위·반복 및 동기화 조건을 기록한다. H2D/D2H와 kernel 시간을 구분한다. 실제 GPU가 없으면 실행·성능 검증 미완료로 남기고 수치를 만들어 넣지 않는다.

## 정확성·과장 방지 기준

- Thread는 CUDA의 개별 실행 문맥이다. 가장 작은 물리적 연산기나 CUDA core와 동일시하지 않는다. `threadIdx`는 Block 내부 index다. 1차원 배열의 전역 index 예시는 `blockIdx.x * blockDim.x + threadIdx.x`다.
- Warp의 32 Thread가 항상 같은 순간에 모두 활성이라는 뜻은 아니다. Independent Thread Scheduling 이후에도 Warp 기반 명령 발행과 분기 비용 설명은 유효하지만 영구적인 lockstep을 가정하지 않는다. Shuffle에는 올바른 참여 mask와 동기화 조건을 적용한다.
- 기본 Block 모델에서 한 Block은 한 SM에서 실행한다. 모든 Thread가 한 사이클에 동시에 연산한다는 뜻은 아니다. Cluster·Distributed Shared Memory·cooperative grid synchronization은 이번 범위 밖이며 기본 모델의 설명을 절대적 금지로 일반화하지 않는다.
- `__syncthreads()`는 Block 범위다. 일부 Thread만 도달하는 잘못된 분기 예제를 정상 코드처럼 제시하지 않는다. 타일을 덮어쓰기 전 기존 데이터를 모두 소비했는지도 보인다.
- Bank Conflict는 같은 bank의 서로 다른 주소를 다루는 상황으로 설명한다. 동일 주소 읽기의 broadcast를 단순 충돌로 세지 않는다.
- Occupancy는 처리량이나 연산기 사용률 자체가 아니다. 높다고 항상 빠르지 않으며, 준비된 Warp 부족·명령 의존성·대역폭 등 조건을 함께 본다. Register spill이 발생하면 local memory 트래픽으로 이어질 수 있다.
- Register, Shared Memory, L1, L2, Device Memory를 모든 접근이 반드시 순차 통과하는 계단으로 그리지 않는다. Shared Memory는 명시적으로 관리되는 공간이며 L1 cache와 의미가 다르다. 물리적 자원 공유 방식과 용량은 GPU 세대에 따라 다르다.
- GEMM은 이해를 위한 scalar FMA 기반 타일 kernel이다. Thread 하나가 출력 원소 하나를 맡는 방식은 교육용 매핑이며 일반적인 모든 고성능 GEMM의 규칙이 아니다. Tensor Core의 행렬 명령·fragment 매핑은 별도 범위다.
- Roofline의 기본 상한은 `P ≤ min(P_peak, BW × I)`다. `I = FLOP / byte`의 byte는 선택한 메모리 경계의 트래픽이다. FMA는 일반적 처리량 표기에서 2 FLOP으로 센다. 메모리별 Roofline과 정밀도·연산 경로의 조건을 맞춘다.
- Roofline 아래의 점을 무조건 Memory Bound 또는 Compute Bound라고 단정하지 않는다. 작은 작업·launch 비용·지연·동기화·명령 의존성 등으로 어느 상한에도 도달하지 못할 수 있다. 가상 사례에는 실측 benchmark가 아니라는 표시를 한다.

## 기존 작업과 제작 순서

실제 파일 확인 시 `episodes/gpuops01_fma/`부터 `gpuops13_layernorm/`까지 존재한다. 새 기본편은 기존 개별 최적화 소재와 연결하되 기존 대본·발화시간을 가져와 확정하지 않는다. 기존 화면은 정확성과 새 원고의 적합성을 확인한 뒤 재사용한다.

1. 이 기획을 기준으로 전체 원고를 작성하고 검토한다. 이 문서 자체는 낭독 대본이 아니다.
2. 원고 작업을 시작할 때 `longforms/_template/`를 복사해 편별 프로젝트를 만든다. 10편의 원고가 통합 대본을 이룬다. 검토 후 각 편을 독립 씬의 `spec.md`·`script.txt`로 나눈다.
3. 각 편은 가로·세로에 공통인 독립 질문과 결론을 갖는 `narration.md`·`tts_script.txt`·`brief.md`를 작성한다. TTS 원고는 화면 변화별 빈 줄로 구분하고 제목·번호·타임코드를 넣지 않는다.
4. 사용자 검토 후 확정 원고의 음원 또는 문장 종료 시각으로 길이를 확정한다. 편집 예산·글자 수로 실제 타이밍을 대신하지 않는다.
5. 그 다음 화면·자막·타이밍 자료를 만들고 미리보기와 최종 렌더를 진행한다. 씬별 mux 후 concat한다. 대본 단계에서는 없는 Scene이나 렌더 ID를 등록하지 않는다.
