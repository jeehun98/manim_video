# AI 컴파일러 — 텐서 프로그램에서 하드웨어 실행까지

2026-10-17 사용자 방향 반영. 기존 plans/ai_compiler_series.md의 정규식·파싱·IR 중심 기초 시리즈와 구분한다. 기존 파일과 번호는 유지하고 새 제작 ID는 aicomp를 사용한다.

일반 컴파일러 원리의 복습을 시리즈 본론으로 삼지 않고, 머신러닝 계산의 의미·구조와 실제 컴파일 시스템을 다룬다. 이전 「계산의 두 얼굴」은 메모리·커널·실행 그래프·의미 보존 등 넓은 최적화 문제를 다뤘다. 이 구분은 내부 제작 참고이며 영상 안에서 복습·예고하지 않는다.

## 구성 방향

2026-10-18 사용자 후속 계획 반영. 후속 구성의 이름은 「AI 컴파일러의 내부」다. 기술을 하나씩 정의하는 강의보다, 신경망 프로그램이 실행 코드로 바뀌는 과정에서 자연스럽게 발생하는 질문을 따라간다. 1편의 기초적인 설명 톤을 유지하되 각 영상에 새로운 기술적 발견을 둔다.

전체 서사: **무엇인가 → 어디에서 동작하는가 → 언제 컴파일하는가 → 어떤 정보를 받아 어떻게 실행 프로그램을 만드는가.**

2~5편에서 시스템의 큰 구조·컴파일 시점·그래프 포착·중간 표현을 먼저 세운다. Shape Inference나 Bufferization 같은 세부 구현은 6편부터 다룬다. 아래 순서는 제작 내부의 연결이며 영상 속 복습·다음 편 예고로 사용하지 않는다.

## 02 제작 방향

작업 제목은 「신경망 코드가 실행되기까지, 컴파일러는 어디에 있을까? — Framework, Compiler, Runtime」이다. 사용자 구성 피드백에 따라 Eager/Compiled 비교보다 세 역할의 연결을 중심에 둔다.

- 하나의 신경망 프로그램을 따라 Framework의 표현·실행 지원 → Compiler의 분석·변환·실행 프로그램 생성 → Runtime의 실제 작업 관리 순으로 설명한다. 처음부터 ‘컴파일 경로의 예’라고 표시한다. 후반에만 Eager의 준비된 연산 구현 호출 경로를 짧게 더해 고정 단계가 아님을 보여준다.
- 두 경로 모두 런타임 기능을 통해 실제 작업이 실행되고 하드웨어에서 계산된다. 프레임워크·컴파일러·런타임은 기능적 계층이며 반드시 별도 프로그램이나 고정된 직렬 상자는 아니다.
- 컴파일러가 매번 실행에 개입하는 모습으로 그리지 않는다. 준비된 코드의 호출과 컴파일을 구분한다. Eager도 내부 구현의 컴파일 기술을 활용할 수 있으므로 ‘컴파일 기술이 전혀 없는 실행’으로 정의하지 않는다.
- 책임 범위와 경로를 발견하는 데 집중한다. AOT·JIT의 시점 비교는 03의 중심으로 남긴다.

## 공통 계산과 화면 문법

반복 사용할 계산은 `Y = ReLU(XW + b)`다. 필요할 때만 해당 질문에 맞게 예시를 확장한다.

05는 예외적으로 하나의 행렬곱 `C=AB`만 끝까지 추적한다. 큰 MatMul 블록 → 출력 한 칸과 i·j·k 축 → Load·Multiply·Accumulate·Store를 보여주고, 너무 빨리 분해했을 때 명시적인 MatMul 테두리가 사라지는 순간을 핵심으로 삼는다. 추상 개념의 정의보다 프로그램의 정보가 드러나거나 사라져 가능한 분석이 달라지는 순간을 시리즈의 시각화 원칙으로 유지한다.

후속 시각화: 06은 실제 원소 없이 축 크기만 전파, 07은 기호 N과 관계가 이동, 08은 유효 조건에 따른 코드 재사용·다른 처리, 09는 다른 텐서 이름 아래 같은 메모리 강조, 10은 텐서 값과 실제 버퍼 대응 변화로 구성한다. 구체적 대본은 편별로 검토한다.

- 프로그램의 표현: Python → Graph → IR.
- 컴파일러의 판단: Shape → 조건 검사 → 변환.
- 실행 가능한 프로그램: 생성된 코드·라이브러리 호출·런타임 실행.

위 흐름은 개념적 안내이며 모든 시스템의 고정된 pass 순서가 아니다. 분석과 변환이 여러 수준에서 반복될 수 있다.

1편의 ‘낮은 수준의 명령을 뒤집어 행렬곱 구조를 드러내는’ 연출을 공통 문법으로 활용한다. 04는 Python 코드에서 포착된 그래프가 나타나고 포착 범위가 드러나게 한다. 05는 같은 계산이 여러 IR로 형태를 바꾸게 한다. 06은 실제 원소 없이 Shape 정보만 흘려 출력 Shape와 제약을 드러낸다. 개념적 역방향 비교를 실제 컴파일 단계의 필수 역순 복원으로 설명하지 않는다.

03에서는 같은 신경망을 세 시간축에 놓아 실행 전에 코드 생성, 첫 호출 중 코드 생성, 이미 준비된 코드 선택을 비교한다. Runtime Dispatch 자체는 코드 생성이 아니다. 장단점 나열보다 컴파일러가 언제 등장하고, 실행 중 언제 개입하지 않으며, 조건 변화로 언제 다시 필요해지는지 보여준다.

03 대본은 AOT → JIT의 첫 호출 → 유효한 코드 재사용 → Runtime Dispatch로 확장한다. 마지막에는 공통 시간축 위에 생성·선택·실행을 정리한다. Dispatch를 AOT·JIT와 동급인 세 번째 컴파일 방식으로 표시하지 않으며, 시간축 간격은 성능 비교나 실제 소요 시간이 아니다. AOT의 입력 조건 활용, JIT 첫 호출 예시의 한정, 재사용의 유효 조건은 짧게 설명하고 Guard 실패·재컴파일 상세는 제외한다.

## 실제 시스템과 연결할 때의 기준

사용자 제안 사례는 PyTorch `torch.compile`의 그래프 포착·컴파일 결과 캐싱과 XLA의 StableHLO 같은 고수준 표현을 활용한 분석·변환·대상별 컴파일이다. 개별 대본 작성 시 공식 문서로 해당 경로와 조건을 확인한다. 한 시스템의 구성을 모든 AI 컴파일러의 필수 구조로 일반화하지 않는다.

04의 graph break·fallback 동작은 시스템과 모드별로 구분한다. 06의 ‘결과’는 원소 값이 아니라 Shape와 제약이며 데이터 의존 크기에는 제한이 있음을 설명한다. 07은 모든 크기를 무조건 기호화할 수 있다는 뜻이 아니고, 10은 alias·수명·의미 보존 조건 안에서 버퍼를 재사용한다는 뜻이다.
