# 계산의 두 얼굴 — 시리즈 제작 계획

작성일: 2026-10-14. 상태: 시리즈 기획 및 01편 제작. 01편은 피드백 반영 수정 대본 기준 107초로 구현하며, 실제 TTS 음원은 아직 제공되지 않았다. 후속 편은 기획 단계다.

## 2026-10-14 수정 기준

모든 영상은 이전 편 복습·요약과 다음 편 예고 없이 독립적으로 완결한다. 아래 표의 다음 질문은 내부 기획 연결이며 영상 대사로 사용하지 않는다. 01편은 「Transpose는 정말 행렬을 뒤집을까? — 수학과 GPU의 다른 계산법」으로 변경하고 View, 후속 MatMul의 세 경로, 반복 사용에 따른 전체 비용까지 다룬다. 02편은 재배열 최적화, 03편은 신경망 전체에서 materialize/view/layout 선택의 유불리에 집중한다. 이전 범위 배정과 충돌하면 이 수정 기준을 우선한다.

- 소개 문구: 같은 수식, 다른 실행 비용 — 수학에서 GPU와 AI 컴파일러까지.

수학은 입력과 출력의 관계를 정의한다. 하드웨어 비용은 그 관계를 실현하는 실행 경로에서 발생한다. 컴파일러는 허용되는 의미를 보존하면서 실행 경로를 선택하고 바꾼다.

기존 GPU 연산과 최적화 시리즈가 개별 연산의 구현을 설명했다면, 이번 시리즈는 동일한 문제를 푸는 여러 실행 경로를 비교한다. 기존 시리즈 시청을 필수로 요구하지 않는다. GPU는 구체적인 관찰 대상이며, 시리즈의 범위는 데이터 배치·병렬 실행·수치적 의미·신경망 그래프·컴파일러까지다.

## 시청자와 완주 목표

행렬과 신경망의 기본 개념을 아는 시청자를 기준으로 한다. CUDA 코드 경험은 요구하지 않는다. Warp, stride, occupancy 등은 문제가 먼저 드러난 뒤 이름을 붙인다.

완주 후 시청자는 다음을 구별할 수 있어야 한다.

1. 수식의 연산량과 데이터를 이동시키는 비용.
2. 논리적인 텐서의 모양과 실제 저장 배치.
3. 개별 커널의 성능과 전체 실행 경로의 성능.
4. 실수 산술에서의 동치, 부동소수점 실행 결과, 프로그램이 허용하는 오차와 의미.
5. 변환의 합법성을 판단하는 문제와 빠른 경로를 예측하는 문제.

## 편별 내용 경계와 시각화

### 01 — 산술이 없는 전치의 비용

- 행렬의 정의 `B[i,j] = A[j,i]`를 먼저 보여준다. 작은 4×4 행렬의 원소 하나를 끝까지 추적한다.
- 행렬을 row-major 주소 띠로 펼친다. 연속 복사와 전치의 읽기·쓰기 주소를 비교한다. 복사와 전치는 같은 출력을 만드는 두 경로가 아니라 데이터 이동 기준선 비교임을 명시한다.
- Warp의 연속 접근과 간격 접근에서 요청한 원소 수와 접근한 메모리 구간 수를 구분한다. 교육용 4개 lane 예시에서 실제 32-thread warp로 확장한다.
- FP32 `N×N`의 별도 출력 생성은 논리적 최소 읽기·쓰기 합계 `8N² bytes`다. 캐시·트랜잭션 낭비까지 포함한 실제 DRAM 측정량과 동일시하지 않는다.
- Coalescing의 필요성까지 설명하고 Shared Memory 구현은 02편에 남긴다. View 가능성은 다음 편들을 여는 짧은 예고로만 둔다.

### 02 — 추가 공간으로 접근을 바꾸기

- 01편의 주소 띠를 그대로 이어받아 Global → Shared → Global 경로를 만든다.
- Tiling으로 Global Memory 읽기와 쓰기를 각각 모으고, 다른 스레드가 쓴 타일을 읽기 전에 필요한 block 동기화를 보여준다.
- Shared Memory에서도 열 방향 접근에 bank conflict가 생길 수 있음을 드러낸다. FP32·32 banks·4-byte bank 단위의 단순 모델에서 `32×32`와 `32×33`을 비교한다.
- 작은 화면의 4-bank 모형과 실제 32-bank 설명을 구별한다. Padding은 저장하는 유효 원소 수를 늘리지 않고 주소 배치를 바꾼다.
- 특정 커널에서 충돌을 없애는 사례를 모든 dtype·접근·GPU의 보편적 속도 보장으로 확대하지 않는다.

### 03 — 이동하지 않는 전치와 소비자의 비용

- 연속 저장된 2×3 행렬을 3×2 view로 해석한다. 원소 단위 stride `(3,1) → (1,3)`를 같은 저장소 위에 표시한다.
- 별도 전치 배열 생성, view만 생성, MatMul이 전치 operand를 직접 읽는 경로를 같은 수학적 출력 기준으로 비교한다.
- 메타데이터 처리에도 작은 비용은 있지만 원소 전체를 이동하지 않는다는 점을 강조한다. 후속 연산이 해당 stride를 효율적으로 지원하는지는 별도 문제다.
- MatMul의 전치 operand 지원과 일반적인 kernel fusion을 같은 구현이라고 부르지 않는다. 라이브러리·컴파일러가 내부 변환이나 packing을 수행할 가능성도 남긴다.
- View의 저장소 공유에 따른 aliasing은 짧게 표시하고, 비교 예시는 입력을 수정하지 않는 경우로 제한한다.

### 04 — 같은 GEMM, 다른 재사용

- 같은 입력 크기·dtype·산술 결과의 GEMM에서 원소를 반복해서 가져오는 경로와 타일을 재사용하는 경로를 비교한다.
- FLOPs와 byte 이동량을 따로 세고, `Arithmetic Intensity = FLOPs / bytes`를 관찰 결과에 붙인다.
- Roofline은 `성능 ≤ min(계산 처리량 한계, 대역폭 × AI)`의 단순 상한 직관으로 제시한다. 어느 메모리 계층의 bytes를 세는지 명시한다.
- 타일을 무한히 키우면 좋다는 결론 직전에 자원 예산을 드러내 05편으로 연결한다.

### 05 — 병렬성을 담는 공간

- 같은 전체 작업을 서로 다른 block 크기와 자원 사용으로 배치한다. SM을 유한한 좌석·레지스터·공유 메모리 예산으로 표현한다.
- Occupancy는 SM의 최대 지원 warp 대비 활성 warp 비율이다. 전체 실행에 요청한 스레드 수와 구분한다.
- 지연을 숨길 만큼의 병렬성, block당 자원 사용, residency 제한을 설명한다. 레지스터 spilling은 조건부 결과로만 보여준다.
- 높은 occupancy가 항상 빠르거나 낮은 occupancy가 항상 느리다고 말하지 않는다. Fusion과 값의 수명은 08편에서 상세히 다룬다.

### 06 — 수학적 합과 컴퓨터의 합

- 같은 값들을 다른 괄호와 reduction tree로 더한다. 실수 산술에서는 같고 유한 정밀도에서는 달라지는 장면을 분리한다.
- FP32 예시 후보: `[1e8, -1e8, 1]`. 실제 dtype과 각 단계 반올림 결과를 대본 확정 전에 검산한다.
- 속도, 수치 오차, 재현성은 다른 평가 축이다. 결정적인 병렬 tree도 가능하며 모든 GPU reduction이 매번 다른 답을 내는 것은 아니다.
- 10편에서 회수할 질문: 어느 정도의 결과 차이가 허용되는가?

### 07 — 저장할까, 다시 계산할까?

- 저렴한 중간값을 저장하고 다시 읽는 경로와 소비 위치에서 재계산하는 경로를 먼저 비교한다. 재계산이 메모리 접근을 줄여 빨라질 수 있는 조건을 보여준다.
- 신경망 activation checkpointing은 별도 확장 장면이다. 일부 activation을 저장하지 않고 backward에서 재계산해 메모리를 절약한다.
- Checkpointing은 일반적으로 계산 시간을 더 쓸 수 있다. 더 큰 batch나 실행 가능성의 이점과 동일 조건에서의 step latency를 구별한다. 항상 빨라진다는 예시로 쓰지 않는다.
- 학습 예시는 상태를 바꾸지 않는 연산부터 시작한다. RNG·상태·부작용을 가진 연산의 재실행에는 의미 보존 조건이 필요하다.

### 08 — Fusion의 적정 범위

- 같은 짧은 연산 체인을 분리·부분 결합·전체 결합해 중간 저장량과 살아 있는 값의 수명을 동시에 그린다.
- 줄어든 Global Memory 접근과 증가할 수 있는 레지스터 수, spilling, occupancy 제약을 비교한다.
- 05편은 병렬 배치와 자원 예산, 08편은 결합 경계가 그 예산을 바꾸는 문제에 집중한다.
- 성능이 뒤집히는 정량 그래프는 실측이 있을 때만 사용한다. 실측이 없으면 조건별 가능한 경로로 표현한다.

### 09 — 계산 그래프에서 실행 계획으로

- 공통 예시 `H = ReLU(XWᵀ + b)`, `Y = HVᵀ`를 사용한다. 학습 확장에서는 이 그래프의 backward까지 범위를 명시한다.
- 논리 그래프를 유지하고, 아래 실행 계획에서 전치 생성 여부·레이아웃·Fusion 경계·중간 저장 선택을 바꾼다.
- 모든 조합이 실제 지원되거나 유리한 것은 아니다. 의존성·커널 지원·자원 제약으로 후보를 거른다.
- 학습 시 H의 저장/재계산은 backward 계획까지 포함해 비교한다. Forward에서 불필요한 중복 계산을 일부러 넣어 checkpointing으로 설명하지 않는다.

### 10 — 합법성과 비용을 함께 판단하기

- 01편의 Transpose를 다시 꺼내 물리적 재배치, view, 소비 연산의 layout 지원을 그래프 전체 관점에서 비교한다.
- 후보 생성 → 의미와 제약 확인 → 비용 예측 → 필요 시 측정·선택 흐름을 보여준다. 모든 컴파일러가 동일한 절차나 autotuning을 수행한다고 일반화하지 않는다.
- 수학적 동치와 bitwise 동일성은 다르다. dtype·반올림·허용 오차·연산 재결합 옵션·aliasing·부작용 등이 변환 허용 범위를 정한다.
- Cost Model에는 크기·dtype·layout·하드웨어·이동량·자원 사용·launch 비용 등이 들어갈 수 있다. 하나의 FLOPs 숫자로 최적 경로를 결정하지 않는다.
- 마지막 결론: 최적화는 관계를 실현하는 여러 경로 중 허용되고 유리한 경로를 찾는 일이다.

## 공통 서사와 화면 문법

각 편은 `기존 직관 → 실행 경로 비교 → 예상과 다른 결과 → 원인 관찰 → 해당 질문의 독립적인 결론`을 따른다. 정의와 약어는 시각적인 문제가 생긴 뒤 도입한다. 06편은 “같은 출력” 대신 “실수에서 같은 식”에서 출발하며 수치 결과 차이가 핵심이다.

- 수식·행렬은 논리적 관계를 나타내고 주소 띠·메모리 상자·스레드는 실행을 나타낸다. 둘 사이 대응을 원소 하나의 색으로 추적한다.
- 세로형 숏폼은 위쪽에 수학적 표현, 가운데에 실행, 아래쪽에 해석과 자막을 둔다. 경로 A/B는 교대로 보여준 뒤 작은 요약 비교로 모은다. 가독성이 확보되는 장면에만 좌우 비교를 쓴다.
- 가로형 롱폼을 별도 제작할 때 수학/실행 또는 경로 A/B의 좌우 비교를 적용한다. 세로 영상을 그대로 가로 프레임으로 늘리지 않는다.
- 제안 색상: 추적 원소 노랑, 일반 데이터 청록, Global Memory 분홍, Shared Memory 보라, 선택된 경로 초록. 색과 함께 문자·위치로도 구별한다.
- 화면 숫자·영문·수식은 원래 표기, 발음 변형은 TTS 원고에만 둔다.
- 애니메이션 속도와 화살표 길이는 실행 시간 측정치가 아니다. 개념 모형·추정·실측을 명확히 구분한다.

## 숏폼과 롱폼 연결

각 편은 독립된 질문과 결론을 갖는다. 내부 장면은 주장 하나 단위로 나눠 교체와 재사용이 가능하게 설계한다.

세로형 10편을 순서대로 연결한 합본과 별도 가로형 롱폼은 다른 산출물이다. 합본은 중복 도입·다음 편 예고를 정리하고 부 사이 연결 내레이션을 넣는다. 단순 concat만으로 최종 대본이 완성됐다고 보지 않는다.

별도 롱폼을 시작할 때는 `longforms/_template/`을 복사하고 `longforms/README.md`를 따른다. 순서는 `전체 대본 → 씬 분할·spec → 씬별 TTS와 길이 확정 → 화면 → 씬별 mux → concat`이다. 화면비는 프로젝트별로 명시하며, 씬 하나는 독립적으로 교체 가능한 완성 영상으로 만든다.
