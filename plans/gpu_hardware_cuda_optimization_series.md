# GPU 하드웨어 · CUDA · 최적화 — 쇼츠·롱폼 구성 계획

작성일: 2026-11-02. 상태: 사용자 검토용 기획 초안. 대본·발화시간 미확정.

> 방향 변경: 사용자의 추가 자료에 따라 현재 시작 계획은 [GPU 개론](gpu_introduction_series.md)으로 옮긴다. 아래 3개 시리즈·39편 구성은 이전 확장안으로 보존하며 현재 제작 범위로 간주하지 않는다.

## 1. 전체 방향

세 시리즈를 서로 다른 질문으로 구분한다.

| 시리즈 | 중심 질문 | 시청 후 할 수 있는 설명 |
| --- | --- | --- |
| HARDWARE | GPU는 왜 이런 구조를 갖는가? | 계산 장치·실행 상태·데이터 공급의 관계 |
| CUDA | 작성한 코드는 GPU에서 어떻게 실행되는가? | 논리 작업 공간과 물리 실행 자원의 대응 |
| OPTIMIZATION | 같은 결과를 내는데 왜 속도가 다른가? | 병목 가설을 세우고 측정으로 검증하는 방법 |

GPU 일반 설계 동기에서 시작하되, SM·Warp·세부 실행 구조는 NVIDIA GPU를 대상으로 한다고 명시한다. CUDA 문법으로 하드웨어의 존재 이유를 설명하지 않는다. 특정 세대의 수치·도식은 모델과 아키텍처를 표시한다.

모든 영상은 자체 질문과 결론으로 끝낸다. 이전 영상 복습과 다음 영상 예고를 넣지 않는다. 필요한 정의는 현재 사례를 이해하는 데 필요한 만큼 화면 안에서 제시한다. 첨부 원문의 마지막 CUDA 시리즈 예고는 채택하지 않는다.

## 2. 포맷과 규모

| 구분 | 쇼츠 | 롱폼 |
| --- | --- | --- |
| 역할 | 질문 하나와 핵심 원리 하나 | 하나의 큰 질문을 여러 실험과 구조로 설명 |
| 기획 목표 길이 | 60–120초, 복잡한 주제는 최대 180초 범위 검토 | 10–15분 |
| 화면비 제안 | 9:16 | 16:9 |
| 서사 | 현상 → 비교 또는 변화 → 원리 → 결론 | 문제 → 설명 모형 → 작동 추적 → 조건 변화 → 적용 범위와 결론 |
| 코드 | CUDA·최적화 편에서 필요한 부분만 | 실행 가능한 작은 예제와 검증 결과 |
| 제작 단위 | 질문 단위 독립 영상 | 주장 하나를 담는 독립 씬 |

길이는 편집·대본 분량을 위한 목표이며 실제 발화시간이 아니다. 문장별 초 단위 배분은 만들지 않는다. 롱폼은 쇼츠의 단순 연결본과 구별해 별도 대본을 작성한다. 애셋과 사례는 공유할 수 있지만 도입·설명 순서·화면 밀도는 각 포맷에 맞춘다.

기본 규모는 **쇼츠 30편 + 롱폼 9편**이다. 하드웨어·CUDA는 첨부안의 10편씩을 유지하고, 최적화는 10편으로 구체화한다. 이는 전체 로드맵이며 한 번에 제작을 시작하는 물량은 아니다.

| H06 | GPU는 왜 작업을 Warp로 묶을까? | 여러 실행 흐름을 그룹으로 관리하며 명령 실행을 조직한다. | 32개 Lane과 활성 마스크·분기 |
| H07 | 계산 중인 숫자는 어디에 있을까? | Register File은 여러 실행 흐름의 빠른 상태 저장을 담당한다. | 여러 Warp의 상태를 같은 SM에 유지 |

| H09 | GPU 안에 작은 공유 저장소가 필요한 이유는? | 가까운 저장소에서 데이터를 재사용하면 외부 접근을 줄일 수 있다. | 같은 데이터를 반복 읽는 두 방식 |
| H10 | 계산 장치가 많아도 왜 기다릴까? | 데이터 지연과 공급량이 연산 장치 활용을 제한할 수 있다. | 공급 속도·대기시간을 따로 바꾸는 실험 |

H04는 부품의 역할 관계까지만 다루고, Warp 실행은 H06, 상태 저장은 H07에서 독립 사례로 설명한다. H05는 FP32·정수·FMA 중심이며 Tensor Core와 행렬 연산은 최적화 O09에서 다룬다. FMA는 한 번 반올림한다는 점 때문에 별도 곱셈·덧셈과 비트 단위 결과가 달라질 수 있다.

## 4. CUDA 쇼츠 10편

| ID | 제목·질문 | 핵심 주장 | 중심 화면 |
| --- | --- | --- | --- |
| C01 | CUDA는 GPU의 무엇을 제어할까? | CUDA는 병렬 작업을 표현하고 실행하는 프로그래밍 플랫폼이다. | 코드의 작업 공간과 GPU 자원 지도 |
| C02 | CPU 함수와 GPU Kernel은 어떻게 다를까? | Host가 실행을 요청하고 여러 GPU Thread가 Kernel을 수행한다. | 할당·복사·Launch·완료 확인·결과 회수 |
| C03 | `<<<blocks, threads>>>`가 정하는 것은? | Launch 구성은 논리 작업 수와 묶음을 정한다. | 같은 배열을 서로 다른 Grid·Block으로 덮기 |
| C04 | `threadIdx.x`는 누가 정할까? | 실행 환경이 제공하는 식별자로 각 Thread가 담당 원소를 계산한다. | `blockIdx.x * blockDim.x + threadIdx.x`와 경계 검사 |
| C05 | Block 하나가 GPU 전체를 차지할까? | 일반적인 Thread Block은 한 SM에서 실행되고 여러 Block이 함께 상주할 수 있다. | 자원 예산에 따른 Block 배치 |
| C06 | Thread 32개는 항상 같은 일을 할까? | Warp 안에서도 활성 Thread와 실행 경로가 달라질 수 있다. | 조건문·활성 마스크·경로별 실행 |

| C08 | `c[i] = a[i] + b[i]` 한 줄의 여정 | 인덱스·주소 계산과 Load·연산·Store가 함께 필요하다. | 하나의 i와 값·주소를 끝까지 추적 |

C02에서 Device 메모리와 전송을 최소한 소개해 메모리 준비 없이 Kernel만 호출하는 인상을 피한다. C04의 PTX 특수 레지스터는 보조 설명으로 둔다. C07에서 PTX가 모든 실행에 반드시 파일로 나타난다고 설명하지 않는다. C10은 Block 전체에 일관된 장벽 도달 조건을 갖춘 예제로 만든다.

## 6. 롱폼 9편

각 행의 구성은 챕터의 논리 순서다. 실제 씬은 대본 확정 후 주장 단위로 더 나눈다. 쇼츠 ID는 제작 참고용이며 시청 선행 조건이 아니다.

HL 계열에는 CUDA 코드를 넣지 않는다. CL 계열에서는 최소 구조도를 그 영상 안에서 정의한다. OL 계열은 최적화 전후에 같은 수학적 작업과 허용 오차를 적용한다. Tensor Core를 비교할 때 정밀도와 누산 방식도 명시한다.

## 7. 대표 편의 장면 구성

### 쇼츠 H06 — GPU는 왜 작업을 Warp로 묶을까?

1. 여러 데이터에 같은 계산을 적용하는 상황을 제시한다.
2. 실행 흐름의 상태와 명령을 그룹으로 조직하는 개념을 보여준다.
3. NVIDIA의 Warp를 32개 Thread의 실행 그룹으로 정의한다.
4. 조건문으로 활성 Lane이 달라지는 예를 보여준다.
5. “그룹으로 실행을 조직하지만 각 Thread의 상태와 참여 여부는 구분된다”로 완결한다.

32개 물리 연산 유닛이 언제나 한 클록에 동시에 실행한다고 그리지 않는다. Lane 격자는 논리도이며 실제 칩 배치가 아니다.

### 롱폼 CL01 — 배열 덧셈 코드는 어떻게 GPU 전체에서 실행될까?

| 챕터 | 주장 | 중심 화면 |
| --- | --- | --- |
| 문제 | 동일한 식을 여러 원소에 적용해야 한다. | A·B·C 배열 |
| 실행 준비 | Host가 입력과 Device 저장공간을 준비한다. | Host·Device 경계와 복사 |
| Kernel | 각 Thread가 같은 코드로 자기 원소를 담당한다. | 코드와 선택된 i |
| 작업 공간 | Grid·Block·Thread는 논리적 조직이다. | 배열과 논리 좌표 대응 |
| 인덱스 | Block·Thread 식별자로 전역 인덱스를 만든다. | 한 원소의 식 계산 |
| 경계 | 배열 길이가 Launch 크기와 같지 않을 수 있다. | 범위 밖 Thread와 조건 검사 |
| 물리 실행 | Block의 실행은 SM 자원과 배치에 의해 진행된다. | 가정한 배치와 순차 진행 |
| 완료·검증 | 결과는 완료 확인과 회수 뒤 CPU 기준값과 비교한다. | 모든 원소 비교·오류 확인 |
| 결론 | 하나의 식을 논리 작업으로 나누고 GPU가 이를 실행한다. | 전체 경로를 한 사례로 마무리 |

전체 배열과 선택한 원소의 색을 유지한다. 각 챕터는 여러 독립 씬으로 나누며 아직 씬별 시간은 부여하지 않는다.

## 8. 시각화 기준

- 전체 지도는 GPU → SM → 상태 저장·명령 발행·실행 유닛·데이터 공급으로 확대한다.
- 논리 조직과 물리 자원은 별도 영역에 두고 대응선으로 연결한다. Grid 안에 물리 SM이 포함되는 식으로 중첩하지 않는다.
- 구조 색은 실행 유닛·저장소·제어 역할에 고정하고, 선택한 데이터는 별도 강조색을 쓴다.
- 데이터 이동·명령 발행·동기화는 화살표 모양과 라벨을 구분한다.
- 설명 모형, 실제 아키텍처 도식, 실측 결과를 화면에서 구별한다. 실제와 다른 수의 SM은 교육용 축소 모형이라고 표시한다.
- 실제 칩 사진은 전체 위치 파악에만 사용한다. 세부 기능 설명은 공식 자료를 토대로 다시 그린 개념도를 우선한다.
- 세로 화면은 한 대상에 집중해 확대하고, 가로 화면은 코드·논리 공간·물리 자원을 필요에 따라 함께 보여준다. 단순 크롭으로 두 버전을 만들지 않는다.

## 9. 기존 제작물과의 관계

실제 파일 확인 결과 `longforms/gpuh01_thread/`–`gpuh11_integrated/`, `gpuh_full_01_11/`가 존재한다. 기존 계층 구조 시리즈는 Thread에서 시작해 코드와 하드웨어를 연결한다. 새 기획은 하드웨어 설계 동기와 CUDA 사용법을 분리한다.

기존 Warp·SM·Register·Shared·Cache·DRAM 도식과 CUDA 검증 예제는 재사용 후보로 둔다. 사용 전 해당 소스·수치·설명 범위를 개별 확인한다. 기존 대본과 발화시간을 새 대본에 전용하지 않는다. 기존 통합 롱폼도 새 HL·CL·OL 구성과 구분해 보존한다.

## 10. 제작 순서와 산출물

1. 이 계획에서 시리즈 범위·질문·포맷을 검토한다.
2. H01–H03 쇼츠 대본과 HL01 전체 대본을 우선 작성해 두 포맷의 설명 밀도를 검토한다.

## 11. 기술 검토 기준과 공식 출처

- Thread와 물리 Core를 일대일 대응시키지 않는다. Kernel 하나가 여러 SM에서 실행될 수 있다. Warp·Block·Shared의 기본 설명은 [CUDA Programming Model](https://docs.nvidia.com/cuda/cuda-programming-guide/01-introduction/programming-model.html)을 기준으로 한다.
- 명시적 Shared 사용과 장벽의 목적은 [Using Shared Memory in CUDA C/C++](https://developer.nvidia.com/blog/using-shared-memory-cuda-cc/)를 참고한다. 기본 시리즈는 일반적인 Block 범위로 한정하며 Cluster 등 확장 기능은 범위 밖으로 명시한다.
- Coalescing·Bank 충돌·Occupancy·성능 측정은 [CUDA C++ Best Practices Guide](https://docs.nvidia.com/cuda/cuda-c-best-practices-guide/index.html)를 기준으로 검토한다. 높은 Occupancy를 성능 보장으로 표현하지 않는다.
- 세대별 실행 유닛 구성·Cache 정책·메모리 용량·명령어는 대본 작성 시 선택한 GPU의 공식 아키텍처 문서와 컴파일 결과로 추가 확인한다.
- 스케줄러의 정확한 순서·배치·캐시 적중을 실측 없이 실제 실행 기록처럼 제시하지 않는다. 최적화 비교는 GPU·툴킷·컴파일 옵션·입력 크기·정밀도·반복 측정 조건을 기록한다.
