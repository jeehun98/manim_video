# AI 컴파일러 02 — 신경망 코드가 실행되기까지, 컴파일러는 어디에 있을까?

## 제작 상태와 분량 제한

- 사용자 확정 19개 발화 구간·141초로 화면을 제작한다. 1편 161초보다 20초 짧다. 실제 음원 파일은 미제공이다.
- approved_segments.txt는 사용자 발음 원문이다. prepare.py가 narration.md·tts_script.txt·captions.srt·timing.json을 생성한다. scene.py의 렌더 ID는 aicomp02다.
- 사용자 요구: 최대 분량은 1편 최종 대본을 넘지 않는다. 1편 tts_script.txt와 동일한 발음 표기 기준으로 공백 제외 문자 수와 어절 수를 비교한다. 실제 발화 길이는 음원·종료 시각으로 확인하며 최종 161초를 상한으로 한다. 추정 타임코드는 만들지 않는다.
- 이전 편 복습과 다음 편 예고는 넣지 않는다.

## 중심 질문과 발견

하나의 신경망 프로그램이 실행되기까지 Framework·Compiler·Runtime이 어떤 역할을 맡고 연결되는가? 세 요소는 기능적 역할이며 반드시 독립된 프로그램이나 모든 실행의 고정 직렬 단계는 아니다. Eager/Compiled 비교는 후반의 보조 사례다.

## 사용자 피드백 반영: 개념이 먼저

세부 정보를 빠짐없이 설명하는 것보다 역할 차이를 확실하게 이해시키는 것을 우선한다. 핵심은 ‘컴파일러가 실행할 프로그램과 계획을 만들고, 런타임이 이를 실제 실행으로 연결한다’다. 정확성은 표현과 화면으로 지키되 Dispatcher·Execution Metadata·동기화 같은 용어를 추가로 나열하지 않는다.

- 그래프 포착의 주체는 ‘프레임워크와 연결된 그래프 포착 기능’으로 표현한다.
- 메모리는 준비와 기존 버퍼 재사용을 함께 보여준다. 관리 주체별 상세 분업은 제작 내부 기준으로 둔다.
- 실행 요청 표시 뒤에 GPU 작업이 진행되고 완료 표시가 나타나도록 한다. 요청 시점과 완료 시점을 구분하되 비동기 실행 강의로 확장하지 않는다.
- 중심 장면: Compiler → ‘실행할 프로그램 + 실행에 필요한 계획’ → Runtime → GPU 실제 계산. 코드·호출 정보·버퍼 정보는 필요할 때만 작은 보조 표기로 보여준다. 실행 산출물의 정확한 패키징은 시스템마다 다르다.
- Eager 장면에는 반드시 `Eager Execution · 즉시 실행`을 표시한다. 음성은 ‘즉시 실행 방식인 이거 실행’으로 읽는다. 구현 선택은 프레임워크 내부의 dispatcher 등과 협력할 수 있다는 제작 기준을 유지하되 용어 정의를 추가하지 않는다.
- 후반의 독립 프로그램·역할 구분 설명을 한 문단으로 압축했다. 마지막 두 문장은 사용자 추천대로 유지한다.

## 장면 구성

| 구간 | 화면 | 전달할 내용 |
|---|---|---|
| 도입 | Python: Y = ReLU(X @ W + b), 실행 버튼 | 코드에서 장치 실행까지 누가 무엇을 하는가 |
| 1 | 코드와 텐서·연산·모델, Framework 영역 | 사용자가 계산을 표현하고 실행을 요청하는 인터페이스 |
| 2 | 포착한 계산 → 분석·변환 → 코드·라이브러리 호출, Compiler 영역 | 실행 프로그램을 만드는 역할 |
| 3 | 생성된 프로그램에 입력 버퍼·출력 버퍼·커널 실행 요청 연결, Runtime 영역 | 준비된 작업을 실제 수행하도록 관리 |
| 3 보충 | 컴파일러의 메모리 계획 → 런타임의 실제 준비 | 계획과 실행의 협력 |
| 4 | 세 역할의 실선 경계를 점선으로 전환, 제품 영역과 역할 영역 중첩 | 제품 세 종류나 독립 프로그램 세 개가 아님 |
| 5 | 준비된 연산 구현 → 런타임 기능 → 하드웨어 경로를 짧게 추가 | 별도의 모델 그래프 컴파일이 필수는 아님 |
| 결론 | 세 역할을 같은 계산 위에 겹쳐 강조 | 고정 순서보다 책임과 협력으로 이해 |

## 기술·연출 기준

1. 처음부터 ‘컴파일 경로의 예’라고 표시한다. Framework → Compiler → Runtime → Hardware는 설명용 역할도이며 모든 시스템의 필수 순서가 아니다.
2. Y = ReLU(XW + b), X[M,K], W[K,N], b[N]를 공통 예시로 쓴다. 한 모델 전체가 언제나 한 그래프로 포착된다고 말하지 않는다.
3. 컴파일러의 변환과 실행 프로그램 생성, 런타임의 실제 실행 요청을 구분한다. 컴파일러도 실행 중 호스트 코드나 라이브러리 호출을 생성할 수 있으며 생성된 실행 코드에도 작업 순서·제어가 포함될 수 있다. Runtime만 실행 관련 로직을 독점한다고 그리지 않는다.
4. 런타임은 넓은 기능적 표현이다. 프레임워크의 실행 기능·메모리 할당기·장치 런타임·드라이버 등이 역할을 나누며 시스템마다 경계가 다르다. 런타임 자체가 수학 연산을 하드웨어 대신 수행한다고 설명하지 않는다.
5. 메모리 계획을 컴파일러가 정하고 런타임이 실행하는 것은 가능한 협력 예시다. 모든 메모리를 컴파일 단계에서 확정하거나 매 호출마다 새로 할당한다고 일반화하지 않는다.
6. Eager는 별도 그래프 컴파일을 사용하지 않는 보조 경로 예시다. ‘컴파일러 없는 실행’, ‘매 연산 직후 GPU 완료까지 대기’, ‘한 연산은 항상 한 커널’로 설명하지 않는다. 준비된 구현이 사전 컴파일 또는 내부 컴파일 기술을 사용할 수 있다.
7. AOT·JIT·컴파일 시점·캐싱·재컴파일 비교는 이번 편의 중심에 넣지 않는다. 1편 정의를 반복하기보다 각 역할의 입력·하는 일·결과를 같은 프로그램 위에서 보여준다.
