# 계산의 두 얼굴 01 — Transpose는 왜 계산하지 않아도 느릴까?

## 학습 목표

수학은 결과의 위치 관계를 정의하지만 실제 전치 배열을 만드는 GPU 실행에는 주소 계산과 데이터 읽기·쓰기가 필요함을 이해한다. 요청한 원소 개수와 메모리 접근 구간 수를 구별한다.

## 제작 기준

- 사용자 콘티의 74초, 6구간: 0–10 / 10–22 / 22–37 / 37–53 / 53–68 / 68–74.
- 1080×1920, 30fps, 미리보기 360×640. 기본 무음 영상. 실제 TTS 미제공으로 문장별 싱크는 미검증이다.
- 화면 자막은 짧은 문장 단위, 별도 SRT는 원문 내레이션. 발음 표기는 tts_script.txt에만 둔다.
- 3×4 입력 A의 값은 1–12. 출력 B는 4×3, 행 우선 저장 순서 `[1,5,9,2,6,10,3,7,11,4,8,12]`.
- 입력 첫 행 1,2,3,4는 노랑으로 추적한다. 첫 행의 원소 위치 0,1,2,3이 출력 0,3,6,9로 대응한다.
- 수식/실행 최종 비교는 좌우 카드, 나머지는 세로 화면의 상하 구조. 하단 자막 공간 확보.

## 기술 조건과 과장 방지

1. 서로 다른 연속 행 우선 입력·출력 배열 사이에 데이터를 실제 재배치하는 단순 전치 커널을 다룬다. 모든 transpose가 이동을 요구한다고 일반화하지 않는다. View는 03편에서 설명한다.
2. “계산하지 않는다”는 덧셈·곱셈 같은 값의 산술 연산이 없다는 뜻이다. 인덱스 계산·메모리 명령·실행 비용은 존재한다. 복잡도 0이나 실행 시간 0을 표시하지 않는다.
3. Warp는 32-thread 단위다. 접근 장면은 그중 4개 lane의 요청만 보여주는 부분 예시다. 정렬된 32B 구간, FP32 8개/구간에서 인덱스 `[0,1,2,3]`은 한 구간, `[0,8,16,24]`는 네 구간에 닿는다. 전체 warp의 트랜잭션 횟수로 표시하지 않는다.
4. 이 장면의 구간 수는 단순 주소 모형이다. 캐시와 실제 DRAM 트래픽·처리 시간은 별개다. 정량 속도나 보편적인 배속 주장을 하지 않는다.
5. 작은 3×4 전치 장면은 주소 대응을 설명한다. 이 작은 예시의 stride=3을 4개 트랜잭션으로 계산하지 않는다. 큰 행렬에서 간격이 커질 수 있다는 설명과 구별한다.
6. Shared Memory·Padding·Bank Conflict의 이름이나 최적화 구현은 이번 편에서 설명하지 않는다. 마지막은 이름 없는 GPU 내부 공간으로 다음 질문만 연다.

## 장면

| 시간 | 주장 / 화면 |
|---|---|
| 0–10 | 3×4 → 4×3, 12개 값의 위치 변경, `Bᵢⱼ = Aⱼᵢ` |
| 10–22 | 입력 행을 차례로 복사해 12개 원소의 주소 띠 구성 |
| 22–37 | 동일한 4개 요청이 한 구간 또는 네 구간을 건드리는 비교 |
| 37–53 | 연속 Load → 4개 Thread → 출력의 간격 Store, 출력 원소 위치 표시 |
| 53–68 | Mathematics: `B=Aᵀ` / Hardware: `Load → Store` |
| 68–74 | GPU 내부 공간을 경유하는 이동과 다음 편 질문 |

## 출처

- [CUDA Best Practices Guide — Coalesced Access](https://docs.nvidia.com/cuda/cuda-c-best-practices-guide/index.html#coalesced-access-to-global-memory): warp 주소와 32B 구간의 관계.
- [NVIDIA — An Efficient Matrix Transpose in CUDA C/C++](https://developer.nvidia.com/blog/efficient-matrix-transpose-cuda-cc/): 단순 전치에서 비연속 쓰기가 발생하는 접근 구조. 과거 성능 수치는 사용하지 않는다.
