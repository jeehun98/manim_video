# 계산의 두 얼굴 02

## 메모리를 더 사용하는데 왜 빨라질까? — Shared Memory와 GPU 최적화

사용자 제공 문장별 누적 종료 시각 기준 89초. 실제 음원 파일 대조는 미실시.

### 0–9초 | 더 많은 단계가 더 빠를까?

같은 행렬을 전치하는 두 가지 방법이 있습니다. 하나는 데이터를 바로 옮기고, 다른 하나는 중간 저장 공간을 한 번 더 거칩니다. 어느 쪽이 더 빠를까요?

### 9–24초 | Warp의 접근 구간

GPU에서는 여러 스레드가 함께 메모리에 접근합니다. 가까운 주소들을 읽고 쓰면 요청을 효율적으로 묶을 수 있습니다. 하지만 접근할 주소가 흩어져 있으면, 같은 양의 데이터를 옮기더라도 더 많은 메모리 트랜잭션이 필요할 수 있습니다.

### 24–36초 | 직접 Transpose

전치 행렬을 직접 만든다고 생각해 보겠습니다. 원본 행을 연속으로 읽으면 읽기는 효율적입니다. 하지만 전치된 출력 배열에서는 같은 값들이 열 방향으로 놓이기 때문에, 쓰기 주소가 멀리 떨어질 수 있습니다.

### 36–47초 | Shared Memory Tiling

그렇다면 작은 블록을 중간 저장 공간에 먼저 모으면 어떨까요? 원본에서는 연속으로 읽고, Shared Memory 안에서 접근 방향을 바꾼 뒤, 출력에도 연속으로 기록하는 것입니다.

### 47–59초 | Bank Conflict

하지만 Shared Memory도 아무 주소나 동시에 접근할 수 있는 것은 아닙니다. 내부에는 여러 메모리 bank가 있고, 서로 다른 주소가 같은 bank에 몰리면 접근이 나뉘어 처리될 수 있습니다.

### 59–69초 | Padding

해결 법은 의외로 단순합니다. 32칸짜리 행에 사용하지 않는 공간 하나를 추가하는 것입니다. 행의 길이가 33칸이 되면, 다음 행의 시작 주소가 다른 bank로 밀립니다.

### 69–78초 | 세 경로 비교

전치된 결과는 똑같습니다. 하지만 직접 기록하는 대신 중간 저장 공간을 거치고, 사용하지 않는 공간까지 추가하자 메모리 접근이 더 효율적으로 바뀐 것입니다.

### 78–89초 | 같은 결과, 다른 비용

GPU에서 중요한 것은 단순히 데이터를 얼마나 적게 옮겼느냐가 아닙니다. 같은 결과를 만들더라도, 하드웨어가 그 이동을 어떻게 처리할 수 있는지가 실제 비용을 결정합니다.
