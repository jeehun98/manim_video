# 계산의 두 얼굴 02 — 메모리를 더 사용하는데 왜 빨라질까?

부제: Shared Memory와 GPU 최적화.

## 학습 목표

데이터 이동 단계가 늘어도 Global Memory 요청을 효율적으로 묶으면 전체 실행 비용이 줄어들 수 있음을 이해한다. Shared Memory의 bank 충돌과 padding을 통해 저장 배치도 병렬 접근의 비용을 바꾼다는 것을 발견한다.

## 제작 기준

- 사용자 콘티의 장면별 시간 합계 105초를 적용한다. 권장 범위 85–100초보다 장면별 구간을 우선한다.
- 1080×1920, 30fps, 미리보기 360×640. 무음 영상이며 대본·발음 원고·SRT 별도. 실제 TTS 음원이 없어 발화 시간은 추정이다.
- 종료 시각: 12,28,42,59,74,88,98,105초. Scene.time 누적 gate로 관리한다.
- 이전 편 복습과 다음 편 예고 없이 질문과 결론으로 독립적으로 완결한다.
- 비교 순서: Naive Transpose → Shared Memory Tiling → Shared + Padding. 성능 숫자나 배속 비율은 표시하지 않는다.

## 기술 조건

1. 물리적인 전치 결과를 별도 행 우선 배열에 만드는 커널을 비교한다. View를 포함하는 모든 transpose의 필수 동작으로 일반화하지 않는다.
2. Global 접근 모형: FP32 원소, 시작 주소 32B 정렬, 32-thread warp, 캐시 생략. 연속 원소 0–31은 4개 32B 구간, stride=8 원소의 0,8,…,248은 32개 구간에 걸친다. 요청한 유효 데이터량은 둘 다 128B이지만 접근 구간과 실제 전송량은 다를 수 있다. 최신 CUDA 가이드의 일반적인 32B coalescing 모델이다.
3. 직접 전치의 32×32 모형: 입력 첫 행은 출력 첫 열. 출력 원소 위치 0,32,…,992는 128B 간격이다. 이 장면은 읽기·쓰기 주소 구조이며 정량 성능 측정이 아니다.
4. Tiling은 작은 4×4 확대 모형으로 데이터 정체성을 보여준다. 먼저 입력 행들을 Shared에 저장하고 block 동기화 후 저장된 열을 읽어 출력 행으로 쓴다. Shared 내부에서 값들을 다시 재배열하는 애니메이션은 하지 않는다. 실제 설명 대상은 32×32 타일이다.
5. FP32, 32 banks, 4B 단위에서 bank=(원소 위치 mod 32). 32×32의 열 c 접근은 (32r+c) mod 32=c라서 서로 다른 32개 주소가 한 bank에 몰린다. 같은 주소 broadcast와 구분한다.
6. 32×33 padding은 마지막 한 열에 미사용 공간을 추가해 row stride를 33으로 바꾼다. 열 c의 bank=(33r+c) mod 32=(r+c) mod 32이며 32개가 모두 다르다. 값 32×32개와 전치 결과는 유지된다. 전체 여분은 32개 FP32, 128B다.
7. 색상은 bank 대응을 돕는 보조 표현이다. 행과 bank 번호 및 주소식을 함께 표시한다. 32×33은 이 조건의 열 접근 충돌을 제거하는 사례이며 모든 dtype·벡터 명령·GPU에서 성능을 보장하지 않는다.
8. Shared 접근과 동기화 비용이 추가된다. Global 접근 개선이 이를 상쇄할 수 있다는 설명이며 Shared 사용이 무조건 빠르다는 주장이 아니다. 실제 향상률은 크기·커널·GPU에 따라 다르다.

## 장면별 구성

| 시간 | 내용 |
|---|---|
| 0–12 | Global→Output / Global→Shared→Output, 추가 단계의 역설 |
| 12–28 | Warp 32개 요청의 연속/간격 접근, 4/32개 32B 구간 |
| 28–42 | 32×32 입력 첫 행이 출력 첫 열로, 간격 쓰기 주소 |
| 42–59 | 4×4 확대 모형의 타일 적재 → 동기화 → 다른 인덱스로 읽기 |
| 59–74 | 32×32 첫 열의 서로 다른 주소들이 bank 0으로 몰림 |
| 74–88 | 32×33로 행 길이 변경, 미사용 열과 bank 분산 |
| 88–98 | 세 경로의 접근 구조 비교 |
| 98–105 | 하나의 같은 결과, 다른 실행 비용 |

## 출처

- [NVIDIA Efficient Matrix Transpose](https://developer.nvidia.com/blog/efficient-matrix-transpose-cuda-cc/): Naive, Shared, Padding 구현 비교. 과거 장치의 성능 수치는 사용하지 않는다.
- [CUDA Programming Guide](https://docs.nvidia.com/cuda/cuda-programming-guide/02-basics/writing-cuda-kernels.html): Shared bank, broadcast, transpose 예제.
- [CUDA Best Practices](https://docs.nvidia.com/cuda/cuda-c-best-practices-guide/index.html): 32B coalescing과 bank conflict 처리.

## 검증 기준

Global 구간 수, bank 대응, 타일 전치의 값 보존을 검산한다. 미리보기에서 한글·행 번호·bank 번호·padding 표시·자막의 겹침을 확인한다. 최종 파일의 해상도·프레임 수·길이·오디오 유무를 확인한다. 실제 음원과의 싱크 및 GPU 성능 실측은 별도다.

### 2026-10-14 제작 검증 결과

- Manim 0.21.0, FFmpeg, Malgun Gothic 확인. 미리보기 및 최종본 렌더 완료.
- 최종 1080×1920, 30fps 설정, 3,150프레임, 스트림 길이 약 104.997초로 목표 105초와 1프레임 이내 차이. 오디오 없음.
- 미리보기 8/25/39/57/72/86/95/104초 및 최종 57/72/86초 화면 확인. 모든 구간 종료 gate 통과.
- 32개 FP32 요청의 4/32개 Global 구간, 32개 모든 열의 padding 전후 bank 매핑, 4×4 타일 전치 값 보존을 검산했다.
- 실제 TTS 음원 발화 싱크와 GPU 성능은 실측하지 않았다.

## 89초 사용자 발화 경계 적용 — 현재 기준

- 사용자 제공 22개 문장 종료 시각: 2,7,9,13,17,24,26,30,36,40,42,47,52,54,59,60,64,69,70,78,83,89초.
- 장면 종료: 9,24,36,47,59,69,78,89초. 위의 105초 표기는 최초 콘티 및 제작 이력이다.
- 전체 배속 없이 누적 목표 시각과 대기 시간을 변경한다. 타일 적재는 행마다 0.3초로 조정해 40–42초의 발화 구간 안에 동기화를 표시한다. 세 경로 비교의 등장은 각각 0.2초로 조정한다.
- 대본의 해결 방법은 사용자 발화대로 해결 법으로 수정했다. 사용자 시각을 적용했으며 음원 파일 자체의 대조는 하지 않았다.
