# 계산의 두 얼굴 04 — 같은 행렬곱인데 왜 GPU의 병목이 달라질까?

부제: Arithmetic Intensity와 Roofline Model.

## 학습 목표

연산량과 GPU 활용도·처리량·실행 시간을 구분한다. DRAM에서 가져온 데이터의 재사용이 연산 밀도를 높이고, 메모리 대역폭 또는 산술 처리량이 상한을 결정할 수 있음을 이해한다. 같은 가중치의 행렬곱도 토큰 수·배치에 따라 최적화 목표가 달라질 수 있음을 발견한다.

## 제작 기준

- 사용자가 시간을 지정하지 않아 대본·시각화용 초기 예산 140초를 제안·적용한다. 실제 음원 미제공으로 문장별 시각은 추정이다.
- 1080×1920·30fps, 미리보기 360×640. 무음 영상. SRT·TTS 원고 별도.
- 9개 장면 종료: 10,24,40,54,76,90,108,126,140초. Scene.time 누적 gate 사용.
- 이전 편 복습과 후속 편 예고 없음. 원소별 덧셈 → 행렬곱 재사용 → AI → Roofline → 입력 형태의 병목 변화로 독립 완결.

## 기술 조건

1. FP32 원소별 add의 산술 1 FLOP, 논리적 최소 I/O는 두 4B 입력 읽기와 한 4B 결과 쓰기로 12B. 큰 DRAM 배열의 캐시·재사용·추가 트래픽을 생략한 모형이다. 12 bytes/FLOP와 1/12 FLOP/byte를 혼동하지 않는다.
2. 행렬곱은 산술이 많아도 높은 처리량·활용도를 얻을 수 있다는 설명이다. 덧셈보다 항상 절대 시간이 짧다는 주장이 아니다. FMA는 2 FLOPs로 센다. 정사각 GEMM의 약 2N³은 지배항이며 정확한 덧셈 수는 2N³−N²이다.
3. 재사용 모형은 A[0,0]=2가 B 첫 행 3,5,7과 곱해져 C의 첫 행에 6,10,14를 기여한다. 완성된 C 전체가 아니라 k=0 항의 누산 기여임을 표시한다. 가져온 입력의 사본은 레지스터 등 내부 재사용의 개념 표현이며 실제 DRAM을 다시 읽는 뜻이 아니다.
4. AI의 bytes는 이 영상에서 DRAM 이동량 기준이다. 다른 계층의 이동량과 섞지 않는다. 같은 FLOPs도 구현·캐시에 따라 AI가 다르며 행렬곱이라는 수식 자체가 빠른 것을 보장하지 않는다.
5. Roofline은 P≤min(P_peak,BW×AI)의 단순 상한 모형이다. 그래프는 log₂ 축, 정규화 처리량, 가상 peak=128·BW=16, ridge AI=8 FLOP/B. 실제 GPU의 사양이나 측정값이 아니다. 그래프의 점도 상한 위치이며 달성 성능이 아니다.
6. 실제 성능은 launch 비용, occupancy, 메모리 계층, Tensor Core 활용, instruction mix 등에 영향을 받는다. FP32 add와 저정밀 Tensor Core의 서로 다른 peak를 같은 실제 roofline으로 비교하지 않는다. 그래프는 같은 dtype·연산 경로의 개념 상한이다.
7. Softmax는 reduction과 exp, 데이터 이동이 포함되는 다른 성격의 연산이다. 항상 memory-bound라고 단정하거나 exp 비용을 일반 add와 동일한 FLOP로 취급하지 않는다. 자세한 Softmax 구현은 범위 밖이다.
8. LLM 비교는 선형층 Y=XW: X[M,K], W[K,N]. W 유지·FP32·입력 각 1회 읽기·출력 1회 쓰기·beta=0 이상 모형에서 FLOPs≈2MKN, bytes≈4(MK+KN+MN). 실제 중복 읽기·캐시·타일 자원·weight quantization·packing을 생략한다. FP32 수식을 모든 실제 LLM dtype에 적용하지 않는다.
9. 작은 배치 Decode는 가중치 이동당 계산이 적고 KV Cache 읽기도 병목일 수 있다. KV는 이 선형층 GEMM식에는 들어 있지 않은 별도 Attention 비용이다. 충분한 토큰/배치 Prefill은 weight 재사용을 높여 compute-bound에 가까워질 수 있다. 큰 batch Decode·작은 Prefill·prefix cache 등의 조건에서는 병목이 달라진다. 두 단계의 보편적인 고정 법칙으로 말하지 않는다.
10. AI 상승은 무조건적인 실행시간 단축이 아니다. 오른쪽 plateau에서는 AI만 더 올려도 상한이 올라가지 않는다. 전체 실행과 각 커널의 병목을 동일시하지 않는다.

## 검증

I/O와 FLOP 계산, GEMM k항 기여, 가상 Roofline의 ridge와 plateau, M 변화에 따른 이상 AI를 검산한다. 모든 시간 gate 및 미리보기의 그래프 축·식·자막·프레임을 확인한다. 최종 파일의 크기·프레임 수·길이·오디오 유무를 검사한다. TTS 싱크와 실제 GPU 성능 측정은 별도다.

## 발견 중심 재구성 — 현재 기준 (2026-10-15)

- 기존 원소별 Add→AI 도입 대신 같은 GPU·같은 W·다른 입력 개수의 병목 질문에서 시작한다.
- 0–14 질문 / 14–38 고정 W, X행 1→4→14 / 38–54 한 번 사용과 재사용 후 FP32 단순 수치 / 54–70 AI 이름 / 70–91 두 점의 Roofline과 병목 용어 / 91–111 상한과 실제 성능 / 111–127 Prefill·Decode / 127–140 결론. 기존 9장면 표는 최초 제작 이력이다.
- 14개 행에서 각 가중치의 14회 곱셈 참여는 밀집 행렬곱의 수학적 사용 횟수다. 14회 DRAM 읽기나 14행에서 compute-bound가 된다는 의미가 아니다. 고정 W와 선택 원소는 이동하지 않는다.
- Roofline 두 점은 AI=0.5와 AI=64인 가상 상한 예시다. 14행 장면의 수치 또는 실제 LLM 측정값이 아님을 표시한다.
- FP32 Add는 숫자 정의보다 사용 후 재사용의 차이를 먼저 관찰한다. 캐시 재사용 제외와 추가 트래픽 생략을 화면에 표시한다.
- 문장과 화면을 함께 재작성했으며 총 초기 예산은 140초 유지. 실제 음원 발화 경계 미제공이다.
