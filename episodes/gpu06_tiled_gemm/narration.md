# GPU 06 — Tiled GEMM: 한 번 가져와, 함께 다시 쓰기

174초. scene.py의 CAPTIONS가 실제 화면 전환, 자막, 대본의 단일 기준입니다. 발화 시간 추정이 아닌 화면 타임라인을 사용합니다.

## 00:00:00.000–00:00:06.000 / 6초 / recap

앞에서는 Thread 하나가 출력 하나를 계산하는
Naive GEMM을 살펴봤습니다.

## 00:00:06.000–00:00:12.000 / 6초 / repeat

계산은 맞지만 여러 Thread가 같은 A와 B의 값을
Global Memory에서 반복해서 읽었습니다.

## 00:00:12.000–00:00:18.000 / 6초 / intro

한 번 가져온 데이터를 함께 재사용할 수는 없을까요?
여기서 Tiling이 등장합니다.

## 00:00:18.000–00:00:24.000 / 6초 / tiles

행렬을 작은 영역으로 나눠 계산합니다. A와 B에서 잘라낸
작은 사각형을 Tile이라고 부릅니다.

## 00:00:24.000–00:00:30.000 / 6초 / block

하나의 Block이 C의 작은 영역을 맡습니다. 이
Block의 Thread들은 필요한 A와 B의 Tile을
함께 사용합니다.

## 00:00:30.000–00:00:36.000 / 6초 / cooperative

먼저 각 Thread가 Tile의 일부를 나눠 가져옵니다.
Global Memory에서 읽은 값을 Shared
Memory에 저장합니다.

## 00:00:36.000–00:00:42.000 / 6초 / loaded

이제 필요한 두 Tile이 Block 안에 있습니다.
가져온 데이터는 같은 Block의 Thread들이 함께 쓸
수 있습니다.

## 00:00:42.000–00:00:48.000 / 6초 / ready

단, 함께 읽기 전에 적재가 끝났는지 맞춰야 합니다.
필요한 동기화 뒤에 계산을 시작합니다.

## 00:00:48.000–00:00:54.000 / 6초 / reuse_a

A의 한 값은 여러 출력에 필요합니다. Shared
Memory에 한 번 올려두면 여러 Thread가
재사용합니다.

## 00:00:54.000–00:01:00.000 / 6초 / reuse_b

B의 값도 마찬가지입니다. 다른 출력 행을 맡은
Thread들이 같은 값을 함께 사용합니다.

## 00:01:00.000–00:01:06.000 / 6초 / multiply

각 Thread는 Shared Memory의 A와 B 값을
곱하고, 자신의 중간 합에 더합니다.

## 00:01:06.000–00:01:12.000 / 6초 / accumulate

첫 Tile의 부분 합이 만들어졌습니다. 중간 합은 각
Thread의 Register에 유지합니다.

## 00:01:12.000–00:01:18.000 / 6초 / before_overwrite

다음 Tile을 가져오기 전에는, 모든 Thread가 현재
Tile을 다 읽었는지 동기화로 맞춥니다.

## 00:01:18.000–00:01:24.000 / 6초 / next_tile

이제 A에서는 오른쪽 조각으로, B에서는 아래쪽 조각으로
이동합니다. 출력 영역은 그대로이고, 합산할 입력 구간만
바뀝니다.

## 00:01:24.000–00:01:30.000 / 6초 / reload

새 Tile을 Shared Memory에 올리고, 적재
완료를 맞춥니다. Register에 있던 중간 합은 지우지
않습니다.

## 00:01:30.000–00:01:36.000 / 6초 / add_next

새 조각에서도 곱셈과 덧셈을 이어갑니다. 첫 출력의 중간
합 4에 8을 더하면 12가 됩니다.

## 00:01:36.000–00:01:42.000 / 6초 / write

모든 입력 구간의 계산이 끝나면 각 Thread가 최종
결과를 C의 담당 위치에 씁니다.

## 00:01:42.000–00:01:48.000 / 6초 / all_blocks

다른 출력 영역도 각 Block이 같은 방식으로
계산합니다. 이 과정을 통해 전체 행렬곱 결과를
완성합니다.

## 00:01:48.000–00:01:54.000 / 6초 / same_math

수학적 계산은 바뀌지 않았습니다. 여전히 A의 한 행과
B의 한 열을 곱해서 더합니다.

## 00:01:54.000–00:02:00.000 / 6초 / contrast

Naive GEMM은 각 Thread가 직접 입력을
읽습니다. Tiled GEMM은 함께 쓸 데이터를 가져와
Block 안에서 재사용합니다.

## 00:02:00.000–00:02:06.000 / 6초 / reuse_count

이 예제의 한 출력 Tile에서는 입력 읽기 요청을 줄일
수 있습니다. 실제 메모리 이동과 속도 차이는 캐시 등에도
영향을 받습니다.

## 00:02:06.000–00:02:12.000 / 6초 / meaning

핵심은 단순히 작은 사각형으로 자르는 것이 아닙니다.
데이터 이동의 단위를 바꾸고, 여러 계산이 재사용하는
구조입니다.

## 00:02:12.000–00:02:18.000 / 6초 / small

그렇다고 Tile이 작을수록 좋은 것은 아닙니다. 너무
작으면 함께 재사용할 기회가 충분하지 않을 수 있습니다.

## 00:02:18.000–00:02:24.000 / 6초 / large

너무 크면 Shared Memory 사용량이 늘어납니다.
설계에 따라 Register 사용량과 Thread 배치에도
영향을 줍니다.

## 00:02:24.000–00:02:30.000 / 6초 / choices

그래서 Tile 크기, Thread당 출력 수,
Shared Memory와 Register 사용량을 함께
고민합니다.

## 00:02:30.000–00:02:36.000 / 6초 / execution

이제 Thread와 Block, Warp가 한 계산에
모입니다. Block 안의 Thread들은 Warp 단위로
실행됩니다.

## 00:02:36.000–00:02:42.000 / 6초 / coalescing

Tile을 가져올 때도 Warp의 접근 주소가 중요합니다.
Coalesced Memory Access를 고려해 읽기
작업을 나눕니다.

## 00:02:42.000–00:02:48.000 / 6초 / together

Shared Memory는 함께 쓰는 Tile을,
Register는 개인의 중간 합을 맡습니다. 이 구조들이
함께 데이터 재사용을 만듭니다.

## 00:02:48.000–00:02:54.000 / 6초 / ending

GPU 최적화에서 중요한 질문은 연산 수뿐만이 아닙니다.
한 번 가져온 데이터를 얼마나 많이 다시 사용할 수
있을까요?
