# GPU 05 — Naive GEMM: 같은 값을 몇 번 다시 읽을까?

전체 174초. scene.py의 CAPTIONS가 화면 전환·자막·대본의 기준입니다. 발화 시간 추정이 아닌 코드의 실제 전환 시각을 사용합니다.

## 00:00:00.000–00:00:06.000 / 6초 / recap

앞에서는 Global Memory, Shared Memory, Register가
서로 다른 역할을 가진다고 했습니다.

## 00:00:06.000–00:00:12.000 / 6초 / matrices

이번에는 실제 계산으로 보겠습니다.
두 행렬 A와 B를 곱해 행렬 C를 만드는 행렬곱입니다.

## 00:00:12.000–00:00:18.000 / 6초 / row_column

C의 한 원소를 계산하려면
A의 한 행과 B의 한 열이 필요합니다.

## 00:00:18.000–00:00:24.000 / 6초 / first_output

첫 번째 출력은 A의 첫 행과 B의 첫 열에서
같은 위치의 값들을 곱해서 더합니다.

## 00:00:24.000–00:00:30.000 / 6초 / dot_product

즉, 출력 원소 하나는
여러 번의 곱셈과 덧셈으로 만들어집니다.

## 00:00:30.000–00:00:36.000 / 6초 / thread_intro

GPU에서는 이 작업을 여러 Thread에 나눌 수 있습니다.
단순하게 Thread 하나가 출력 원소 하나를 맡습니다.

## 00:00:36.000–00:00:42.000 / 6초 / mapping

Thread 0은 첫 번째 출력, Thread 1은 그 옆의 출력.
각 Thread가 자신이 맡은 결과 하나를 계산합니다.

## 00:00:42.000–00:00:48.000 / 6초 / read_pair

각 Thread는 자신에게 필요한
A의 행과 B의 열을 따라 값을 하나씩 읽습니다.

## 00:00:48.000–00:00:54.000 / 6초 / accumulator

읽은 두 값을 곱하고, 결과를 계속 더합니다.
이 중간 합은 Register에 둘 수 있습니다.

## 00:00:54.000–00:01:00.000 / 6초 / first_terms

첫 두 곱셈의 결과는 각각 2입니다.
Register의 중간 합은 0에서 2, 다시 4가 됩니다.

## 00:01:00.000–00:01:06.000 / 6초 / last_terms

나머지 곱셈의 결과 0과 8도 더합니다.
모든 항을 더한 최종 값은 12입니다.

## 00:01:06.000–00:01:12.000 / 6초 / write_result

계산이 끝나면 Register의 최종 결과를
자신이 담당한 C의 위치에 씁니다.

## 00:01:12.000–00:01:18.000 / 6초 / independent

각 Thread가 출력 하나를 독립적으로 계산합니다.
구조는 단순하고 자연스럽습니다.

## 00:01:18.000–00:01:24.000 / 6초 / neighbor

하지만 옆의 Thread를 보겠습니다.
다른 출력을 계산하려고 이 Thread도 A와 B를 읽습니다.

## 00:01:24.000–00:01:30.000 / 6초 / repeat_a

같은 출력 행을 맡은 Thread들은
같은 A의 값을 반복해서 읽습니다.

## 00:01:30.000–00:01:36.000 / 6초 / repeat_b

같은 출력 열을 맡은 Thread들은
같은 B의 값도 다시 읽습니다.

## 00:01:36.000–00:01:42.000 / 6초 / growth

행렬이 커지면 한 입력값을 사용하는 출력도 많아집니다.
여러 Thread의 반복 읽기도 늘어납니다.

## 00:01:42.000–00:01:48.000 / 6초 / necessary_work

곱셈과 덧셈 자체는 필요한 연산입니다.
하지만 같은 입력값을 여러 Thread가 다시 요청하고 있습니다.

## 00:01:48.000–00:01:54.000 / 6초 / logical_loads

즉, 연산 수뿐 아니라 같은 데이터를 몇 번 읽는지도 중요합니다.
실제 메모리 이동 비용은 캐시 등에도 영향을 받습니다.

## 00:01:54.000–00:02:00.000 / 6초 / reuse_a

A의 한 값을 여러 출력에 쓴다면,
한 번 가져와 여러 Thread가 재사용할 수 있으면 좋겠습니다.

## 00:02:00.000–00:02:06.000 / 6초 / reuse_b

B의 원소도 마찬가지입니다.
여러 출력이 필요로 하는 값을 함께 재사용할 수 있습니다.

## 00:02:06.000–00:02:12.000 / 6초 / naive

지금의 단순한 Kernel은 각 Thread가
필요한 값을 Global Memory에서 직접 읽습니다.
이것이 Naive GEMM입니다.

## 00:02:12.000–00:02:18.000 / 6초 / correct

수학적으로는 올바른 행렬곱입니다.
하지만 빠른 메모리와 명시적인 공유 재사용은 충분히 활용하지 못합니다.

## 00:02:18.000–00:02:24.000 / 6초 / shared

여기서 Shared Memory가 다시 등장합니다.
같은 Block의 Thread들이 쓸 데이터를 함께 준비하는 공간입니다.

## 00:02:24.000–00:02:30.000 / 6초 / tile

행렬 전체 대신 필요한 작은 영역만 가져오면 어떨까요?
A와 B에서 작은 조각, Tile을 선택합니다.

## 00:02:30.000–00:02:36.000 / 6초 / stage_tile

선택한 조각들을 Shared Memory에 가져옵니다.
데이터 준비가 끝났는지 필요한 동기화도 맞춥니다.

## 00:02:36.000–00:02:42.000 / 6초 / reuse_tile

이제 같은 Block의 Thread들이 조각 안의 값을 함께 재사용합니다.
Global Memory에서 반복해서 읽는 일을 줄일 수 있습니다.

## 00:02:42.000–00:02:48.000 / 6초 / tiling

작은 조각을 가져와 여러 계산에 사용하는 방식.
이것이 다음 단계인 Tiling의 출발점입니다.

## 00:02:48.000–00:02:54.000 / 6초 / ending

같은 계산이라도 데이터를 몇 번 읽고 얼마나 재사용하느냐에 따라,
GPU의 실행 비용은 달라질 수 있습니다.
