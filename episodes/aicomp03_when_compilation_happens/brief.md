# AI 컴파일러 03 — AI 컴파일러는 언제 코드를 만들까?

## 제작 상태

사용자 확정 20개 발화 구간·142초 기준으로 화면을 제작한다. 1편 161초보다 19초 짧고 2편 141초보다 1초 길다. 실제 음원은 미제공이다. 1~2편처럼 쉬운 문장으로 개념을 이해시키며 이전 편 복습·후속 예고는 넣지 않는다.

approved_segments.txt는 사용자 발음 원문이며 prepare.py가 대본·TTS·SRT·timing.json을 생성한다. 원본 tts_script.txt에 들어 있던 종료 시각은 timing.json·자막·영상으로 옮기고, 발음 원고에는 읽을 문장과 구간 사이 빈 줄만 둔다. scene.py의 렌더 ID는 aicomp03이다.

## 질문과 핵심 발견

같은 신경망을 실행할 때마다 새 실행 프로그램을 만들어야 하는가? 생성·저장과 재사용·조건에 따른 선택·실행은 서로 다른 작업이다. AOT와 JIT는 컴파일 시점에 관한 개념이고 Runtime Dispatch는 준비된 코드 선택에 관한 개념이다. 성능 우열이나 장단점 비교가 중심이 되지 않도록 한다.

## 공통 계산과 장면

Y = ReLU(XW + b)를 유지한다. 화면 원문은 AOT, JIT, Runtime Dispatch, Shape, Dtype 등을 사용하고 한국어 발음은 TTS에만 둔다.

| 순서 | 화면 | 발견 |
|---|---|---|
| 도입 | 같은 모델 옆에 호출 1·2·3, 매번 코드가 필요한지 질문 | 생성과 호출의 관계를 묻기 |
| AOT | Model → Compiler → Executable을 준비 구간에 놓고 보관. 이후 입력 → 준비된 프로그램 → Runtime → GPU | 생성이 실제 사용보다 앞설 수 있음 |
| AOT 보충 | 준비 구간에 알려진 Shape·Dtype·Target 태그 | 실제 실행 입력 전에도 입력 조건을 활용할 수 있음 |
| JIT | 비어 있는 코드 보관함, 첫 입력·호출 → Compiler → Code → 실행 요청 | 호출 과정에서 생성할 수 있음 |
| 재사용 | 생성한 코드 카드를 보관함에 남기고 두 번째 호출은 보관함으로 연결. Compiler는 비활성 | 유효한 기존 코드가 있으면 다시 만들 필요 없음 |
| Dispatch | Code A: Batch=8, Code B: Batch=64. 입력 8 → 조건 확인 → A 강조 → 실행 | 코드를 생성하지 않고 선택하는 장면 |
| Dispatch 보충 | 선택 상자 위에 AOT·JIT 양쪽에서 화살표 | 생성 방식과 선택은 다른 축 |
| 결론 | 공통된 시간축 위 준비 구간·호출 1·호출 2 표시, AOT/JIT 행과 선택→실행 표시를 겹쳐 정리 | 생성·선택·실행의 시점 구분 |

## 개념을 선명하게 만드는 연출

- 코드 생성은 보라색, 저장·재사용은 청록색, 조건 확인·선택은 노란색으로 구분하고 텍스트·화살표도 함께 사용한다.
- 하나의 코드 카드를 생성 후 보관하고 다시 꺼내며 같은 산출물임을 보여준다. 재사용 장면에서 컴파일러를 재점등하지 않는다.
- 마지막 시간축의 막대 길이·간격은 순서를 나타내며 시간 측정치나 성능 비교가 아니다. ‘순서 개념도 · 소요 시간 비례 아님’을 작게 표시한다.
- Dispatch를 AOT/JIT와 나란한 세 번째 컴파일 방식으로 그리지 않는다. 실행 중 선택이라는 별도 표시를 두 행에 공통으로 연결한다.
- 생성·선택·실행이라는 세 동작을 이해시키는 데 집중한다. Guard 이름·실패·재컴파일·비용 상충·캐시 계층·AOT Autograd 상세는 범위 밖이다.

## 정확성을 위한 내부 기준

1. AOT는 대상으로 삼는 프로그램의 실행에 앞서 컴파일한다는 뜻이다. 실제 서비스 입력 도착 전 장면은 한 예이며 컴파일 중 예제 입력·메타데이터·사전 조건을 사용할 수 있다. 실제 입력값을 절대 사용할 수 없거나 모든 크기가 정적이어야 한다고 말하지 않는다.
2. JIT의 첫 호출 생성은 설명용 사례다. 모든 JIT가 첫 호출에 모델 전체를 한 번에 컴파일한다고 일반화하지 않는다. 더 늦은 시점·부분 컴파일·기존 캐시 사용도 가능하다.
3. 두 번째 호출 재사용은 보관된 산출물이 있고 유효 조건이 맞는 경우다. ‘두 번째 호출부터 항상 재사용’이라고 단정하지 않는다. 유효성 조건의 세부 실패 처리는 설명하지 않는다.
4. Batch 8/64 전용 코드는 가상의 명확한 예시다. 실제 시스템이 정확한 Shape 일치만 검사한다는 뜻이 아니며 여러 크기를 처리하는 동적 Shape 코드도 가능하다.
5. 여기서 Runtime Dispatch는 준비된 실행 구현을 조건에 따라 선택하는 개념이다. 그래프 컴파일 결과 선택·연산 dispatcher 등 서로 다른 구체적 메커니즘을 하나의 고정 구현으로 합치지 않는다. 조건 불일치가 새 컴파일로 이어질 수 있지만 본 영상의 선택 장면은 이미 맞는 코드가 준비된 경우다.
6. 실행은 런타임의 요청과 하드웨어 수행으로 표현한다. 생성 완료나 선택 완료가 GPU 계산 완료를 뜻하지 않는다. CPU·AI 가속기에도 적용 가능한 개념이며 GPU는 예시다.

## 공식 자료 확인

- [XLA GPU AOT compilation](https://openxla.org/xla/gpu_aot): 미리 컴파일한 산출물의 저장과 이후 런타임 로드·실행.
- [PyTorch torch.compile](https://docs.pytorch.org/docs/stable/generated/torch.compile): 컴파일 결과 캐싱과 이후 호출의 적용 가능 조건.
- [PyTorch 2 논문](https://docs.pytorch.org/assets/pytorch2-2.pdf): JIT 그래프 컴파일과 guard 기반 캐시 재사용. 제품명과 세부 구현은 본문에 추가하지 않고 개념 검증에 사용한다.

## 대본 검증

발음 원고와 대본의 발화 내용 일치를 확인하고, 기존 1편 최종 원고와 분량을 비교한다. 실제 길이는 사용자의 발화 종료 시각으로 확정한다.

- 대본·TTS 발화 20구간, 영문·숫자 발음 변환 일치 확인. 공백 제외 발음 원고는 1편 1,122자 대비 3편 981자(87.4%), 어절 수 311개. 사용자 제공 시각으로 142초를 확정했다.

## 사용자 종료 시각과 출력

- 발화 종료: 5,10,17,23,30,39,43,51,61,68,74,81,89,95,103,109,119,126,132,142초. 각 시작은 직전 종료 시각이다.
- Scene.time 누적 gate로 각 종료 시각에 맞추고 초과하면 오류를 발생시킨다. 전체 배속 조정은 하지 않는다.
- 미리보기 360×640, 최종 1080×1920, 30fps, 기본 무음. 음원 합성·mux는 하지 않는다.
- 화면 핵심 자막과 별도 SRT 전체 발화를 구분한다. 긴 발화는 SRT에서 2줄 단위로 나눠 내부 경계를 문자량에 따라 배분한다. 사용자 제공 최종 경계는 유지하지만 음원 기반 정렬 결과는 아니다.
- 실행: `python scripts/render.py aicomp03 --preview`, `python scripts/render.py aicomp03`.
