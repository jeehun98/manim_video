# 과학 한조각 — 학습과 추론, GPU가 해결하는 서로 다른 문제

Manim 상세 콘티

9:16 Shorts

약 2분 40초

수학·컴퓨터 구조 시각화

이번 영상은 단순히 학습과 추론을 비교하는 설명 영상이 아닙니다.

같은 GPU, 같은 신경망인데 왜 최적화해야 하는 대상이 달라지는지를 시청자가 시각적으로 이해하게 만드는 것이 목표입니다.

특히 영상 전체에 같은 신경망 도식을 재사용하겠습니다. 학습할 때는 가중치가 계속 변하고, 추론할 때는 가중치가 고정된 상태에서 입력과 KV Cache가 변하도록 구성합니다.

이렇게 해야 '학습과 추론의 차이'가 단순히 용어의 차이가 아니라 실제 데이터 흐름과 연산 구조의 차이로 전달됩니다.

시각적 구분을 위해 다음 원칙을 사용합니다.

- 가중치: 노란색의 고정된 행렬 블록. 학습 중에는 값과 색상 농도가 변화하며, 추론에서는 변하지 않습니다.
- 입력·출력 토큰: 작은 직사각형들이 한 방향으로 이동합니다.
- KV Cache: 초록색 블록이 오른쪽으로 하나씩 늘어나는 형태입니다.
- GPU 연산: 파란색 또는 보라색 점멸과 행렬 연산 애니메이션으로 표현합니다.
- 병목: 데이터 이동 통로에서 큐가 쌓이고 계산 유닛이 대기하는 모습으로 표현합니다.

### Scene 01 — 같은 GPU가 같은 일을 할까?

애니메이션

- 1.0초: 칩 내부에 수많은 연산 유닛이 밝아지고 `TRAINING`이라는 글자가 등장합니다.
- 2.0초: 화면에 대규모 데이터 블록들이 GPU로 들어갑니다.
- 3.5초: GPU의 형태는 유지한 채 `TRAINING`이 왼쪽으로 이동합니다.
- 4.5초: 오른쪽에 `INFERENCE`가 나타납니다.
- 5.5초: 오른쪽에는 사용자 프롬프트 말풍선이 GPU로 들어가고, 답변 토큰이 순서대로 나옵니다.
- 7.0초: 화면이 정지하며 두 흐름 사이에 `SAME GPU, DIFFERENT WORK?`가 나타납니다.

Manim 구현: `VGroup`, `Rectangle`, `RoundedRectangle`, `LaggedStart`, `TransformMatchingShapes`.

이 장면에서는 GPU를 두 개로 그리지 않는 것이 중요합니다. 하나의 동일한 GPU에서 서로 다른 작업이 실행된다는 느낌을 유지합니다.

### Scene 02 — 학습: 순전파, 역전파, 가중치 갱신

00:09–00:34

Training 계산 흐름

나레이션

“사실 학습과 추론은 같은 신경망을 사용하지만, 수행하는 연산과 해결해야 할 문제가 다릅니다.”

“학습은 데이터를 이용해 모델의 가중치를 바꾸는 과정입니다.”

“모델이 예측한 결과와 정답의 차이를 계산하고, 역전파를 통해 기울기를 구한 뒤 가중치를 수정합니다.”

“즉, 순전파뿐 아니라 역전파와 가중치 갱신까지 반복하며 막대한 양의 행렬 연산을 수행합니다.”

애니메이션 세부

00:09–00:15 — Forward

- 데이터 행렬 \\(X\\)가 왼쪽에 등장합니다.
- 중앙에 가중치 행렬 \\(W\\)가 나타납니다.
- `X × W`의 행렬곱을 표시합니다.
- 입력 데이터가 가중치 행렬을 통과하며 출력 행렬로 변환됩니다.
- 파란색 연결선이 왼쪽에서 오른쪽으로 순차 점등됩니다.

00:15–00:21 — Loss

- 오른쪽에 예측값 \\(\hat y\\)가 등장합니다.
- 아래에서 정답 \\(y\\)가 올라옵니다.
- 두 값이 비교되며 `Loss`가 생성됩니다.
- 예시로 `Prediction: 0.7 / Target: 1.0`처럼 작은 숫자 표시.
- 최종 손실값이 붉은색으로 강조됩니다.

00:21–00:28 — Backward

- 손실값에서 가중치 행렬 방향으로 보라색 화살표가 역방향 이동합니다.
- 가중치 행렬 위에 `∂L/∂W`가 생성됩니다.
- 개별 가중치 원소마다 기울기 값이 표시됩니다.
- 오른쪽에서 왼쪽으로 흐르는 연산을 강조합니다.

00:28–00:34 — Update

- `W ← W − η∇W` 수식이 나타납니다.
- 원래 행렬의 숫자들이 새로운 숫자로 변합니다.
- `0.30 → 0.27`, `0.80 → 0.84`처럼 가중치의 실제 변화가 보이게 합니다.
- 전체 과정을 압축해 한 번 더 반복합니다.
- 반복할 때마다 행렬의 값이 변화합니다.

핵심: 학습 장면에서는 순전파와 역전파에 따라 연산 방향이 달라지고, 최종적으로 가중치 자체가 갱신되는 모습을 반드시 보여줍니다.

### Scene 04 — 모델은 그대로인데 대화는 기억한다?

모델 가중치와 문맥의 차이

나레이션

“그렇다면 AI는 어떻게 이전 대화를 기억하고, 새로운 질문에 활용할 수 있을까요?”

“모델이 다시 학습하는 것이 아니라, 이전 대화가 다음 입력의 문맥으로 제공되기 때문입니다.”

연출

- 00:51: 기존의 가중치 행렬을 화면 상단으로 이동합니다.
- 00:53: 아래쪽에 첫 번째 사용자 메시지가 나타납니다.
- 00:56: AI 답변이 추가됩니다.
- 00:59: 사용자가 새로운 질문을 입력합니다.
- 01:02: 이전 메시지들이 하나의 문맥 묶음으로 합쳐집니다.
- 01:04: 문맥 묶음은 모델을 향해 이동하지만 상단의 가중치 숫자는 그대로입니다.

특히 강조할 연출

가중치 블록은 화면 상단에 고정하고, 그 아래에 대화 메시지들이 계속 쌓이게 합니다.

시청자에게 \*\*“이전 대화를 참고하는 것과 모델이 학습되는 것은 다르다”\*\*는 차이를 직관적으로 전달합니다.

단, 이전 대화가 문맥에 포함되어야 모델이 참고할 수 있습니다. 실제 서비스의 영구 메모리 기능이나 서버의 대화 기록 저장은 KV Cache와 별개이므로 이 장면에 혼합하지 않습니다.

### Scene 05 — 대화가 길어질수록 계산할 정보가 증가한다

01:06–01:13

문맥 길이 증가

나레이션

“하지만 대화가 길어질수록 처리해야 할 문맥도 늘어납니다.”

“이전 내용을 매번 처음부터 계산한다면 매우 비효율적이겠죠.”

연출

- 첫 메시지를 4개의 토큰 칸으로 변환합니다.
- 다음 메시지가 더해지며 토큰 칸이 오른쪽으로 늘어납니다.
- 토큰의 개수가 4개에서 8개, 16개, 32개로 증가합니다.
- 화면의 모델 아래에 동일한 연산을 반복하는 화살표를 여러 개 그립니다.
- 이전 토큰의 계산 결과를 매번 처음부터 생성하는 모습을 보여줍니다.
- 반복되는 화살표가 많아질수록 화면이 복잡해집니다.
- 마지막에 중복된 화살표를 지우고 다음 KV Cache 장면으로 전환합니다.

핵심 의도: 문맥이 길어질수록 필요한 작업이 증가하는 문제를 먼저 보여준 뒤, KV Cache가 왜 필요한지 설명합니다.

### Scene 06 — KV Cache: 계산 결과 일부를 재사용한다

01:13–01:29

핵심 시각화

이 장면은 영상의 두 번째 중심 장면입니다.

단순한 메모리 창 그림보다 입력 토큰 → Key·Value 생성 → Cache 저장 → 다음 토큰에서 재사용의 과정이 실제로 이어져야 합니다.

나레이션

“그래서 언어모델은 이전 토큰에서 계산한 Key와 Value를 저장하고, 다음 토큰을 생성할 때 재사용합니다.”

“이것이 KV Cache입니다.”

“모델의 가중치는 그대로인데, 대화가 길어질수록 필요한 계산 상태는 증가할 수 있는 것입니다.”

01:13–01:19 — Key와 Value 생성

- 왼쪽에 토큰 `A`가 나타납니다.
- 토큰이 `Linear Projection` 블록을 통과합니다.
- 내부에서 `Q`, `K`, `V` 세 가지 벡터가 생성됩니다.
- `Q`는 Attention 계산 방향으로 이동합니다.
- `K`, `V`는 아래쪽 메모리 영역에 저장됩니다.
- 메모리 영역에 `K₁`, `V₁`이 생성됩니다.

01:19–01:24 — 다음 토큰 처리

- 다음 토큰 `B`가 입력됩니다.
- 새로운 `Q₂`, `K₂`, `V₂`가 생성됩니다.
- `Q₂`가 이전 `K₁`과 새로운 `K₂`를 참조하는 Attention 계산을 수행합니다.
- 그에 대응하는 `V₁`, `V₂`를 이용하여 출력을 계산합니다.
- 새로운 `K₂`, `V₂`가 캐시에 추가됩니다.

01:24–01:29 — 누적

- 화면 중앙에 `t = 1 → 2 → 3 → …` 표시.
- 각 단계마다 캐시 블록이 하나씩 오른쪽으로 추가됩니다.
- 상단의 `Model Weights` 블록은 크기와 값이 그대로 유지됩니다.
- 아래쪽의 KV Cache만 길어집니다.

Manim 구성

`TokenBlock`, `LinearProjection`, `KVCacheGrid`, `AttentionFlow` 클래스로 분리하는 것을 권장합니다. 이후 다른 GPU·CUDA 콘텐츠에서도 재사용하기 좋습니다.

주의할 점은 KV Cache가 모든 과거 계산을 저장하는 공간은 아니라는 사실입니다. 일반적인 Transformer의 각 Attention 계층에서 재사용할 Key와 Value 텐서를 저장합니다. Query나 모든 중간 Activation을 무조건 저장하는 것으로 표현하지 않습니다.

### Scene 07 — 추론은 Prefill과 Decode로 나뉜다

01:29–01:46

병렬 계산과 순차 생성의 차이

나레이션

“여기서 추론은 다시 두 단계로 나뉩니다.”

“사용자의 프롬프트를 처리하는 Prefill 단계에서는 여러 토큰의 연산을 병렬로 수행합니다.”

“반면 답변을 생성하는 Decode 단계에서는 토큰을 하나씩 만들면서 모델의 가중치와 기존 KV Cache를 사용합니다.”

01:29–01:36 — Prefill

- 프롬프트 `"GPU는 어떻게 계산할까?"`가 토큰 블록 여러 개로 분리됩니다.
- 모든 토큰이 행렬 형태로 정렬됩니다.
- GPU 내부의 여러 연산 유닛이 동시에 활성화됩니다.
- 큰 행렬 연산이 수행됩니다.
- 입력 문맥의 K와 V가 캐시에 채워집니다.
- `PREFILL / PARALLEL` 표시.

01:36–01:46 — Decode

- GPU가 하나의 토큰을 출력합니다.
- 출력한 토큰이 다음 계산의 입력으로 되돌아갑니다.
- 다시 하나의 토큰을 생성합니다.
- `토큰 1 → 토큰 2 → 토큰 3 → …`처럼 순차적으로 나타납니다.
- 매번 기존 KV Cache에 접근하는 화살표가 반복됩니다.
- `DECODE / SEQUENTIAL DEPENDENCY` 표시.

중요한 표현상의 차이

Decode가 GPU에서 연산을 하나씩만 실행한다는 뜻은 아닙니다. 한 토큰을 생성하는 내부 연산은 여전히 병렬로 실행됩니다.

순차적이라는 것은 다음 출력 토큰이 이전에 생성한 토큰에 의존한다는 의미입니다. 이 차이는 GPU 시각화에서 반드시 유지해야 합니다.

### Scene 08 — GPU가 계산보다 데이터를 기다리는 순간

01:46–02:04

핵심 병목 시각화

이 장면은 이번 영상에서 가장 인상적으로 만들 수 있는 부분입니다.

GPU의 연산 유닛은 매우 빠른데, 필요한 데이터를 가져오는 통로가 상대적으로 좁다는 사실을 애니메이션으로 표현합니다.

나레이션

- KV Cache에서도 데이터 블록이 이동합니다.
- 처음에는 계산 유닛들이 활발하게 움직입니다.

01:53–01:59 — 데이터 공급의 병목

- HBM에서 연산 유닛으로 향하는 통로를 좁게 표시합니다.
- 이동해야 할 데이터 블록이 통로 앞에 쌓입니다.
- GPU 연산 유닛 중 일부는 데이터가 도착할 때만 잠시 활성화됩니다.
- 다른 유닛은 회색으로 전환됩니다.

- 데이터 공급량이 연산 처리 능력을 충분히 채우지 못하는 모습을 보여줍니다.

01:59–02:04 — 핵심 반전

- GPU 연산 유닛을 크게 확대합니다.
- 연산 유닛이 빨리 움직일 준비가 된 모습과 느린 데이터 도착을 대비합니다.
- 화면을 멈추며 `WAITING FOR DATA`가 등장합니다.
- 이어서 `MEMORY BOTTLENECK`으로 전환합니다.

Manim 구현

`MemoryBlock`, `BandwidthChannel`, `ComputeUnit`, `DataPacket`을 독립적인 컴포넌트로 제작합니다.

데이터 패킷은 일정한 속도로 움직이고, GPU 연산 유닛은 패킷이 도착했을 때만 활성화되는 애니메이션이 좋습니다.

실제 GPU에서 연산 유닛 전체가 항상 멈춘다는 뜻은 아닙니다. 처리량을 메모리 대역폭이 제한하는 상황을 단순화한 개념도로 사용합니다.

## 3. 제작 시 반드시 유지할 기술적 정확성

| 표현 대상    | 정확한 연출                      |
| -------- | --------------------------- |
| 학습       | 순전파·역전파·가중치 갱신이 존재          |
| 추론       | 일반적인 답변 생성 중 가중치는 고정        |
| 문맥 유지    | 이전 메시지가 입력 문맥에 제공됨          |
| KV Cache | Attention 계층의 Key·Value 재사용 |
| Prefill  | 여러 입력 토큰을 병렬로 처리            |
| Decode   | 출력 토큰 사이에 순차적 의존성 존재        |
| 메모리 병목   | 특정 추론 조건에서 대역폭이 처리량을 제한     |
| HBM      | 용량과 대역폭을 별도 지표로 표현          |
| GPU 최적화  | 연산·메모리·오버헤드 중 병목을 찾아 개선     |

특히 KV Cache에 관해서는 영상에 표시할 수 있는 관계식이 하나 있습니다.

일반적인 캐시 구조에서 저장 토큰 수에 따른 KV Cache의 대략적인 메모리 사용량은 다음과 같습니다.

\\[ M\_{\mathrm{KV}}\approx 2BLTHd\\,s \\]

여기서 \\(B\\)는 배치 크기, \\(L\\)은 계층 수, \\(T\\)는 저장된 토큰 수, \\(H\\)는 KV 헤드 수, \\(d\\)는 헤드 차원, \\(s\\)는 원소당 바이트 수입니다.

이 관계에서 보여줄 핵심은 다른 조건이 일정할 때 토큰 수가 늘어나면 KV Cache 메모리도 선형적으로 증가한다는 사실입니다.

수식 전체를 영상에 넣을 필요는 없습니다. Scene 06에서 토큰이 하나씩 늘어날 때 캐시 블록도 하나씩 늘어나는 연출이면 충분합니다.

## 5. 최종 제작에서 가장 투자할 가치가 있는 장면

## 01

가중치가 변하는 학습과 변하지 않는 추론

같은 행렬을 재사용하는 시각적 대비가 가장 중요합니다. 이번 영상의 기본 개념이 여기에서 결정됩니다.

문맥이 길어질수록 증가하는 KV Cache

## 03

데이터를 기다리는 GPU

GPU의 연산 성능이 충분해도 메모리 대역폭이 병목이 될 수 있다는 사실을 직접 시각화합니다. HBM과 CUDA 최적화의 필요성까지 연결되는 장면입니다.

마지막으로 이번 영상은 처음과 끝을 연결하는 것이 중요합니다.

처음에는 \*\*“같은 GPU가 왜 서로 다른 문제를 해결할까?”\*\*라고 질문합니다. 그리고 마지막에는 \*\*“최적화하려면 지금 어떤 연산을 수행하는지부터 이해해야 한다”\*\*는 결론에 도달합니다.

이렇게 구성하면 단순한 학습·추론 개념 소개가 아니라, GPU 최적화 공부에서 왜 연산의 구조와 실행 환경을 먼저 구분해야 하는지 전달하는 독립적인 「과학 한조각」 영상이 됩니다.
