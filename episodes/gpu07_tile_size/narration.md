# GPU 07 — Tile 크기: 왜 16×16, 32×32일까?

174초. scene.py의 실제 화면 전환 시각과 CAPTIONS 문구가 대본 및 자막의 기준입니다. 발화 시간 예측으로 타이밍을 만들지 않습니다.

## 00:00:00.000–00:00:06.000 / 6초 / recap

앞에서는 Tile을 Shared Memory에 올리고,
여러 Thread가 함께 재사용하는 Tiled GEMM을
봤습니다.

## 00:00:06.000–00:00:12.000 / 6초 / question

그렇다면 Tile은 얼마나 커야 할까요? 예제의
16×16이나 32×32가 특별한 정답일까요?

## 00:00:12.000–00:00:18.000 / 6초 / balance

그렇지는 않습니다. Tile 크기는 데이터 재사용과 GPU
자원 사용 사이의 균형으로 결정됩니다.

## 00:00:18.000–00:00:24.000 / 6초 / tile16

먼저 Thread 하나가 출력 하나를 맡는 단순한
구조입니다. 16×16 출력 Tile은 Thread
256개가 됩니다.

## 00:00:24.000–00:00:30.000 / 6초 / warps16

NVIDIA GPU에서 Warp 하나는 Thread
32개입니다. 따라서 Thread 256개는 Warp
8개로 나뉩니다.

## 00:00:30.000–00:00:36.000 / 6초 / tile32

같은 방식으로 32×32 출력 Tile을 맡기면,
Thread는 1024개가 필요합니다.

## 00:00:36.000–00:00:42.000 / 6초 / warps32

이것은 Warp 32개입니다. Tile의 가로와 세로를 두
배로 키우면 출력과 Thread 수는 네 배가 됩니다.

## 00:00:42.000–00:00:48.000 / 6초 / limit

1024개는 현재 NVIDIA GPU의 Block당 최대
Thread 수이기도 합니다. 다른 자원 제한도 만족해야
합니다.

## 00:00:48.000–00:00:54.000 / 6초 / reuse16

큰 Tile의 장점은 재사용입니다. 16×16 예제에서
A의 한 값은 같은 출력 행의 계산 16곳에 쓰입니다.

## 00:00:54.000–00:01:00.000 / 6초 / reuse32

32×32라면 같은 A의 값을 출력 32곳에 쓸 수
있습니다. B의 값도 같은 출력 열에서 재사용됩니다.

## 00:01:00.000–00:01:06.000 / 6초 / reuse_math

한 번 가져온 데이터로 더 많은 곱셈과 덧셈을 합니다.
하지만 재사용만 보고 크기를 계속 늘릴 수는 없습니다.

## 00:01:06.000–00:01:12.000 / 6초 / shared16

A와 B를 각각 정사각 Tile로 한 번씩 저장한다고
합시다. 같은 자료형에서 Shared Memory 사용량을
비교하겠습니다.

## 00:01:12.000–00:01:18.000 / 6초 / shared32

16×16에서 32×32로 바꾸면, 두 입력 Tile의
원소 수와 저장 용량은 네 배가 됩니다.

## 00:01:18.000–00:01:24.000 / 6초 / register

한 Thread가 여러 출력을 맡는 설계라면, 출력마다
중간 합이 필요합니다. Register 사용량도 늘어날 수
있습니다.

## 00:01:24.000–00:01:30.000 / 6초 / sm

SM은 Block들이 올라가 실행되는 GPU의 계산
장치입니다. Shared Memory와 Register
자원은 한정되어 있습니다.

## 00:01:30.000–00:01:36.000 / 6초 / resident

Block의 자원 사용량이 커지면, 한 SM에 동시에
유지할 수 있는 Block이나 Warp 수가 줄어들 수
있습니다.

## 00:01:36.000–00:01:42.000 / 6초 / small

작은 Tile은 자원 부담이 적을 수 있습니다. 더 많은
작업을 유지하기 쉽지만, 데이터 재사용 기회는 줄 수
있습니다.

## 00:01:42.000–00:01:48.000 / 6초 / large

큰 Tile은 재사용에 유리할 수 있지만 자원 부담이
커집니다. 어느 쪽이 빠른지는 이것만으로 정할 수
없습니다.

## 00:01:48.000–00:01:54.000 / 6초 / summary

동시에 유지하는 작업이 많다고 항상 빠른 것도 아닙니다.
재사용과 자원 사용을 함께 봐야 합니다.

## 00:01:54.000–00:02:00.000 / 6초 / numbers

그래서 16과 32는 마법의 숫자가 아닙니다. Warp
크기와 작업 배치, 자원 제한을 고려할 때 등장하는
선택지입니다.

## 00:02:00.000–00:02:06.000 / 6초 / hierarchy

실제 고성능 GEMM에서는 Tile이 한 종류만 있는 것도
아닙니다. 여러 단계의 Tile을 함께 사용합니다.

## 00:02:06.000–00:02:12.000 / 6초 / block128

전체 행렬에서 Block이 맡는 출력 영역을 Block
Tile이라고 합니다. 예를 들어 128×128 영역을
맡을 수 있습니다.

## 00:02:12.000–00:02:18.000 / 6초 / warp_tiles

그 안을 다시 Warp들이 나눠 맡습니다. 이 예에서는
Block Tile을 더 작은 Warp Tile 여덟 개로
나눴습니다.

## 00:02:18.000–00:02:24.000 / 6초 / thread_tiles

각 Warp 안에서도 Thread마다 여러 출력값을 맡길
수 있습니다. 한 Thread가 담당하는 작은 영역이
Thread Tile입니다.

## 00:02:24.000–00:02:30.000 / 6초 / not_threads

따라서 128×128 Block Tile이 Thread
16384개를 뜻하지는 않습니다. 출력 영역과 Thread
수를 구분해야 합니다.

## 00:02:30.000–00:02:36.000 / 6초 / design

Tile 크기를 정할 때는 재사용, Shared
Memory, Thread와 Warp 배치,
Register 사용량을 함께 결정합니다.

## 00:02:36.000–00:02:42.000 / 6초 / hardware

좋은 선택은 행렬의 크기와 자료형, GPU 자원에 따라
달라집니다. 다른 계산에서는 다른 Tile이 유리할 수
있습니다.

## 00:02:42.000–00:02:48.000 / 6초 / measure

후보를 비교할 때는 실제 실행 시간도 측정해야 합니다.
재사용이나 자원 수치 하나만으로 성능을 단정할 수
없습니다.

## 00:02:48.000–00:02:54.000 / 6초 / ending

좋은 Tile 크기는 언제나 하나로 정해져 있지 않습니다.
계산과 하드웨어 자원 사이에서 좋은 균형을 만드는
크기입니다.
