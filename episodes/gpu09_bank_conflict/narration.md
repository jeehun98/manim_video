# GPU 09 — Shared Memory Bank Conflict

174초. scene.py의 CAPTIONS가 실제 화면 자막·전환 시각·대본의 기준입니다. 발화 시간 예측이 아닌 화면 타임라인을 사용합니다.

## 00:00:00.000–00:00:06.000 / 6초 / recap

Shared Memory는 같은 Block의
Thread들이 데이터를 재사용하는 공간입니다. 하지만
사용한다고 언제나 빠른 것은 아닙니다.

## 00:00:06.000–00:00:12.000 / 6초 / structure

Shared Memory 안에서도 어떤 위치를 함께
읽느냐가 중요합니다. 내부 저장 공간은 여러 Bank로
나뉩니다.

## 00:00:12.000–00:00:18.000 / 6초 / banks32

NVIDIA GPU의 일반적인 구조에서는 Bank가
32개입니다. 여러 통로로 나눠 요청을 처리하는 모습으로
생각해봅시다.

## 00:00:18.000–00:00:24.000 / 6초 / warp32

Warp도 Thread 32개입니다. 여기서는 각
Thread가 4바이트 원소 하나를 읽는 경우를
보겠습니다.

## 00:00:24.000–00:00:30.000 / 6초 / contiguous

Thread 0은 0번 원소, Thread 1은 1번,
Thread 2는 2번 원소를 읽습니다. 연속된 원소에
접근합니다.

## 00:00:30.000–00:00:36.000 / 6초 / spread

이 조건에서는 요청이 서로 다른 Bank로 나뉩니다. 여러
요청을 함께 처리하기 좋은 패턴입니다.

## 00:00:36.000–00:00:42.000 / 6초 / stride

이번에는 간격을 32개 원소로 바꿉니다. Thread들이
0번, 32번, 64번, 96번 원소를 읽습니다.

## 00:00:42.000–00:00:48.000 / 6초 / mapping

주소는 서로 다르지만, Bank 번호는 모두 같습니다. 이
예제에서는 Bank 0으로 몰립니다.

## 00:00:48.000–00:00:54.000 / 6초 / conflict

Warp의 여러 Thread가 같은 Bank의 서로 다른
주소를 함께 요청합니다. 이런 상황을 Bank
Conflict라고 합니다.

## 00:00:54.000–00:01:00.000 / 6초 / serialized

같은 Bank가 요청들을 한 번에 처리하지 못하면, 요청을
나눠 처리해야 합니다. 접근이 여러 단계로 나뉘는
것입니다.

## 00:01:00.000–00:01:06.000 / 6초 / same_work

같은 Shared Memory, 같은 Thread 수,
같은 데이터 양입니다. 그래도 Bank 매핑에 따라 처리
비용이 달라질 수 있습니다.

## 00:01:06.000–00:01:12.000 / 6초 / look_bank

따라서 주소가 다른지만 볼 것이 아니라, 그 주소가 어느
Bank에 연결되는지를 함께 봐야 합니다.

## 00:01:12.000–00:01:18.000 / 6초 / matrix

Shared Memory를 행마다 32개의 원소가 있는
배열로 사용해봅시다. 화면에는 일부 행과 열만 펼쳐
보겠습니다.

## 00:01:18.000–00:01:24.000 / 6초 / row

같은 행의 옆 원소들을 읽으면, Bank 번호도 차례로
달라집니다. Warp의 요청이 여러 Bank로 분산됩니다.

## 00:01:24.000–00:01:30.000 / 6초 / column

반대로 같은 열을 읽으면 원소 번호가 32씩 증가합니다.
서로 다른 주소가 다시 같은 Bank에 몰립니다.

## 00:01:30.000–00:01:36.000 / 6초 / transpose

그래서 행렬 전치처럼 읽는 방향이 바뀌는 계산에서는,
Shared Memory 접근에도 Bank
Conflict가 생길 수 있습니다.

## 00:01:36.000–00:01:42.000 / 6초 / padding

해결 방법 하나는 Padding입니다. 32×32 대신
32×33으로 저장 공간을 만들고, 각 행 끝에 한 칸을
더 둡니다.

## 00:01:42.000–00:01:48.000 / 6초 / shift

계산할 값은 그대로지만 다음 행의 시작 위치가 달라집니다.
첫 열의 원소 번호가 0, 33, 66, 99가 됩니다.

## 00:01:48.000–00:01:54.000 / 6초 / scatter

이제 첫 열의 Bank 번호도 0, 1, 2, 3으로
달라집니다. 이 패턴에서는 Warp 전체가 서로 다른
Bank를 사용합니다.

## 00:01:54.000–00:02:00.000 / 6초 / unchanged

Padding은 필요한 계산 값을 바꾸지 않습니다. 저장
간격을 바꿔 Bank 매핑을 바꾸는 것입니다.

## 00:02:00.000–00:02:06.000 / 6초 / broadcast

한 가지 예외도 있습니다. 여러 Thread가 정확히 같은
주소를 읽는 경우입니다.

## 00:02:06.000–00:02:12.000 / 6초 / same_address

이때는 하나의 값을 여러 Thread에 전달하는
Broadcast가 가능합니다. 서로 다른 주소가 충돌하는
경우와 구분해야 합니다.

## 00:02:12.000–00:02:18.000 / 6초 / distinguish

핵심은 같은 Bank의 서로 다른 주소입니다. 같은
Bank를 본다는 이유만으로 모든 읽기를
Conflict라고 부르지는 않습니다.

## 00:02:18.000–00:02:24.000 / 6초 / global_memory

앞에서 Coalesced Memory Access는
Global Memory의 요청을 어떻게 묶는지에 관한
이야기였습니다.

## 00:02:24.000–00:02:30.000 / 6초 / shared

Bank Conflict는 Shared Memory 안의
문제입니다. Warp의 서로 다른 주소 요청이 Bank에
어떻게 분산되는지를 봅니다.

## 00:02:30.000–00:02:36.000 / 6초 / compare

Global Memory에서는 메모리 트랜잭션을,
Shared Memory에서는 Bank 매핑을 봅니다.
분석하는 대상이 다릅니다.

## 00:02:36.000–00:02:42.000 / 6초 / design

즉, 빠른 저장 공간을 고르는 것만으로는 충분하지
않습니다. Warp가 어떤 주소를 함께 읽고 쓰는지도
설계해야 합니다.

## 00:02:42.000–00:02:48.000 / 6초 / scope

오늘의 Padding 효과는 이 자료형과 접근 패턴의
예입니다. 자료형과 명령, 배치가 바뀌면 Bank 매핑도
다시 확인해야 합니다.

## 00:02:48.000–00:02:54.000 / 6초 / ending

데이터를 어디에 둘지, 그리고 Thread들이 어떤
패턴으로 접근할지. GPU 최적화에서는 두 가지를 함께
봐야 합니다.
