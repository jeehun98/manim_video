# GPU 03 — 같은 계산인데 왜 메모리 접근에 따라 속도가 달라질까?

기준: scene.py의 CAPTIONS 화면 전환 시각과 실제 자막 원문. 전체 175초. 대본에는 의역이나 별도의 설명을 넣지 않습니다. TTS 파일만 같은 내용을 한글 발음으로 변환합니다.

## 00:00:00.000–00:00:06.000 / 6초 / recap

앞에서는 32개의 Thread가 하나의 Warp를 이루고,
같은 명령을 함께 실행한다고 했습니다.

## 00:00:06.000–00:00:10.000 / 4초 / memory

이번에는 이 Thread들이
메모리에서 데이터를 읽는 모습을 보겠습니다.

## 00:00:10.000–00:00:14.000 / 4초 / contiguous

하나의 Warp가
연속된 배열을 읽는다고 해보겠습니다.

## 00:00:14.000–00:00:21.000 / 7초 / neighbors

Thread 0은 x₀, Thread 1은 x₁, Thread 2는 x₂.
각 Thread가 바로 옆의 값을 읽습니다.

## 00:00:21.000–00:00:25.000 / 4초 / nearby

Thread들이 요청하는 주소도
메모리에서 서로 가깝게 모여 있습니다.

## 00:00:25.000–00:00:31.000 / 6초 / merge_requests

GPU는 이렇게 모인 요청을
효율적인 메모리 접근으로 묶어 처리할 수 있습니다.

## 00:00:31.000–00:00:37.000 / 6초 / coalesced

이런 형태를 보통
Coalesced Memory Access라고 합니다.

## 00:00:37.000–00:00:42.000 / 5초 / change_pattern

이번에는 계산은 그대로 두고,
Thread들이 읽는 위치만 바꿔보겠습니다.

## 00:00:42.000–00:00:49.000 / 7초 / stride_indices

Thread 0은 x₀, Thread 1은 x₃₂,
Thread 2는 x₆₄, Thread 3은 x₉₆을 읽습니다.

## 00:00:49.000–00:00:53.000 / 4초 / same_compute

각 Thread가 수행하는 계산은 이전과 같습니다.
읽은 값에 1을 더합니다.

## 00:00:53.000–00:00:57.000 / 4초 / scattered

하지만 이번에는 요청하는 주소들이
메모리에서 서로 멀리 떨어져 있습니다.

## 00:00:57.000–00:01:01.000 / 4초 / same_work

Thread 수는 같고, 계산도 같습니다.
달라진 것은 데이터를 읽는 위치입니다.

## 00:01:01.000–00:01:08.000 / 7초 / few_transactions

연속된 주소를 읽을 때는 여러 Thread의 요청을
비교적 적은 메모리 트랜잭션으로 처리할 수 있습니다.

## 00:01:08.000–00:01:15.000 / 7초 / many_transactions

주소가 멀리 흩어지면
더 많은 메모리 트랜잭션이 필요할 수 있습니다.

## 00:01:15.000–00:01:20.000 / 5초 / same_bytes

같은 양의 값을 읽어도,
요청이 걸치는 메모리 영역 수는 달라집니다.

## 00:01:20.000–00:01:25.000 / 5초 / not_only_compute

즉, GPU에서 성능을 결정하는 것은
계산량만이 아닙니다.

## 00:01:25.000–00:01:30.000 / 5초 / read_write

Thread들이 어떤 주소의 데이터를
읽고 쓰는지도 중요합니다.

## 00:01:30.000–00:01:36.000 / 6초 / matrix_intro

이 차이는 배열뿐 아니라,
행렬이나 이미지 같은 큰 데이터를 다룰 때도 중요합니다.

## 00:01:36.000–00:01:42.000 / 6초 / row_major

예를 들어 한 행이 32개인 행렬을
행 순서대로 메모리에 저장했다고 해보겠습니다.

## 00:01:42.000–00:01:49.000 / 7초 / read_row

Warp의 Thread들이 같은 행의 옆 원소들을 읽으면,
연속된 메모리 주소에 접근할 수 있습니다.

## 00:01:49.000–00:01:56.000 / 7초 / read_column

반대로 같은 열을 따라 읽으면,
이 예제에서는 주소가 32개 원소 간격으로 떨어집니다.

## 00:01:56.000–00:02:03.000 / 7초 / same_matrix

결국 같은 행렬 원소들을 모두 읽더라도,
한 번의 Warp 요청에 묶이는 주소는 달라질 수 있습니다.

## 00:02:03.000–00:02:09.000 / 6초 / warp_view

여기서는 Thread 하나의 접근만 보지 말고,
Warp 전체가 어떤 주소들을 함께 요청하는지 봐야 합니다.

## 00:02:09.000–00:02:15.000 / 6초 / close_again

Warp 안의 Thread들이 가까운 주소를 읽으면,
메모리 접근을 더 효율적으로 처리할 수 있습니다.

## 00:02:15.000–00:02:21.000 / 6초 / far_again

반대로 접근 주소가 흩어져 있다면,
같은 양을 읽더라도 더 많은 비용이 들 수 있습니다.

## 00:02:21.000–00:02:27.000 / 6초 / no_speed_claim

실제 속도 차이는 캐시와 정렬 상태 등에도
영향을 받지만, 접근 패턴은 중요한 출발점입니다.

## 00:02:27.000–00:02:33.000 / 6초 / layout

GPU 최적화에서는 무엇을 계산하는지만큼
데이터를 어떤 순서로 배치하는지도 중요합니다.

## 00:02:33.000–00:02:38.000 / 5초 / thread_order

그리고 Warp의 Thread들이
어떤 순서로 읽고 쓰게 할지도 중요합니다.

## 00:02:38.000–00:02:43.000 / 5초 / same_kernel

같은 Kernel, 같은 Thread 수,
같은 계산이라도,

## 00:02:43.000–00:02:49.000 / 6초 / pattern

Warp가 요청하는 주소의 배치가 달라지면
메모리에서 처리해야 할 일이 달라집니다.

## 00:02:49.000–00:02:55.000 / 6초 / ending

메모리 접근 패턴 하나만으로도
GPU의 실행 성능은 달라질 수 있습니다.
