# AI 컴파일러 05 — AI 컴파일러는 왜 계산을 여러 번 바꿔 표현할까?

## 제작 상태

대본 검토 단계. narration.md·tts_script.txt·brief.md를 작성한다. 사용자 검토와 대본 확정 후 TTS 음원 또는 발화 종료 시각으로 길이를 정한다. 화면·SRT·timing.json·렌더 ID는 만들지 않는다. 이전 편 복습과 이후 편 예고 없이 하나의 질문으로 완결한다.

## 중심 발견

같은 계산을 여러 표현으로 바꾸는 이유는 각 단계에서 필요한 정보를 드러내고 적합한 분석·변환을 하기 위해서다. 의미 보존과 높은 수준의 구조가 명시적으로 남는 것은 구분한다. 추상화 수준을 관리하는 문제에 집중하며 AST 구성·그래프 포착·GPU 최적화 기법 강의를 반복하지 않는다.

사용자 연출 원칙: 추상 개념을 상자에 적는 데서 멈추지 않고 **정보가 드러나거나 명시적 구조가 사라져, 컴파일러가 하기 쉬운 일이 달라지는 순간**을 보여준다.

## 하나의 계산과 세 표현

공통 계산은 `C = AB`, A[M,K], B[K,N], C[M,N]이다. 텐서 연산·인덱스/반복·메모리 접근 표현의 대응을 유지한다.

```text
Tensor-level: C = MatMul(A, B)

Index-level: C[i,j] = sum_k A[i,k] * B[k,j]

Loop/access-level conceptual pseudocode:
for i in range(M):
    for j in range(N):
        acc = 0
        for k in range(K):
            a = load A[i,k]
            b = load B[k,j]
            acc = acc + a*b
        store C[i,j] = acc
```

위 코드는 개념 설명용이며 실제 IR 구문이 아니다.

## 장면 설계

| 구간 | 화면 변화 | 드러나는 정보와 가능한 판단 |
|---|---|---|
| 도입 | 큰 MatMul 노드와 ‘곧바로 명령으로?’ 질문 | 하나의 계산을 끝까지 추적 |
| 1 | A·B → MatMul → C, 행렬곱 전체를 감싼 테두리 | 행렬곱 의미, 구현 선택·블록 분할 후보 |
| 2 | C의 한 칸 C[i,j] 확대 → A의 행·B의 열 → k를 따라 곱·합산 | 출력 인덱스 i·j, 합산 축 k |
| 2 확장 | 같은 색의 i·j·k가 인덱스 수식에서 반복문으로 이동 | 반복 구조와 변환 대상 |
| 3 | 같은 원소 접근이 Load A·Load B → Multiply → Accumulate → Store로 구체화 | 메모리 접근과 구체적 계산 |
| 4 · 핵심 | 장면을 되짚는 별도 비교: MatMul을 바로 작은 명령으로 분해하고 MatMul 이름·테두리를 제거 | 의미는 유지해도 행렬곱 구조가 명시적으로 남지 않을 수 있음 |
| 4 확장 | 흩어진 명령들을 다시 묶으려는 점선 테두리 | 변환 전에 구조를 다시 인식해야 할 수 있음 |
| 결론 | 같은 계산의 세 표현을 나란히 놓고 각 정보만 색으로 강조 | 수준마다 드러나는 정보와 하기 쉬운 분석이 달라짐 |

## 기술·연출 기준

1. 위 세 단계는 설명용 Lowering 경로다. 모든 컴파일러가 고정된 세 IR을 순서대로 지나거나 중간 단계를 모두 만들 필요는 없다. Linalg는 자체로도 반복·인덱싱·reduction 정보를 가진 구조화된 연산을 표현할 수 있다. 텐서 수준에는 이런 정보가 전혀 없고 loop 수준에서 처음 생긴다고 설명하지 않는다. ‘직접 드러난다’와 ‘계산 방법이 더 구체화된다’로 표현한다.
2. 실제 IR과 ISA 덤프가 아닌 개념 수식·의사코드다. Load/Multiply/Add/Store는 실제 하드웨어 명령과 1:1 대응하지 않는다. 벡터·행렬 명령·FMA·타깃별 명령이나 최적화 라이브러리 호출도 가능하다. Library Call 대안은 작은 보조 경로로만 표시한다.
3. 출력 C[i,j]의 누적은 0으로 초기화하고 k를 따라 더한 후 저장한다. C=AB를 초기값이 있는 C+=AB와 혼동하지 않는다. A·B의 공유·alias 문제는 단순화한 순수 행렬곱 예시다.
4. 수식의 실수 의미와 실제 부동소수점 계약을 구분한다. 합산 순서·재결합·정밀도·FMA 등이 달라지면 bitwise 결과가 달라질 수 있다. ‘의미 유지’는 해당 프로그램이 요구하는 수치 계약 안의 변환을 뜻한다. 모든 반복 순서 변경이 무조건 허용된다고 하지 않는다.
5. 타일링·반복 변환은 높은 수준 또는 낮은 수준에서도 가능하다. 특정 최적화가 한 IR 수준에서만 가능하다는 이분법을 피하고, 정보가 명시적일 때 해당 변환을 검토하기 쉽다는 점을 보여준다.
6. 너무 이른 Lowering은 구조를 활용하기 어렵게 만들 수 있으나 낮은 수준 IR이 항상 정보를 잃거나 낮출수록 최적화가 나쁘다는 뜻은 아니다. 하위 수준 분석으로 구조를 복원하거나 속성·다른 IR 형태로 유지할 수도 있다. 실선 테두리 제거는 명시적 행렬곱 구조의 소실 가능성을 표현하며 계산 의미 소실·잘못된 계산으로 그리지 않는다.
7. MLIR은 여러 추상화 수준을 다루는 인프라의 실제 사례다. 본문에 제품명·dialect를 나열하지 않고 필요하면 결론의 작은 사례 표기로만 사용한다. multi-level IR이라는 일반 개념과 특정 프로젝트 MLIR을 동일시하지 않는다.
8. 1편의 ‘고수준 구조 활용’은 정의의 근거였고, 이번 편은 한 MatMul의 정보가 IR 수준에 따라 어떻게 드러나는지와 언제 구조를 보존할지에 집중한다. 12편의 실제 코드 생성·타깃 실행 세부 사항과 구분한다.

## 확인한 공식 자료

- [MLIR Linalg](https://mlir.llvm.org/docs/Dialects/Linalg/): 구조화된 연산이 유지하는 인덱싱·반복·reduction 정보, 하위 수준에서 추론하기 어려운 성질의 명시적 표현.
- [Linalg Dialect Rationale](https://mlir.llvm.org/docs/Rationale/RationaleLinalgDialect/): 구조적 정보와 추상화 간격, 하위 표현 및 라이브러리 구현으로의 연결.
- [MLIR Rationale](https://mlir.llvm.org/docs/Rationale/Rationale/): 여러 수준의 표현에서 계산·변환을 다루는 설계.
- [MLIR Passes](https://mlir.llvm.org/docs/Passes/): 구조화된 연산에서 반복문 등으로의 변환 경로.

## 검증 기준

대본과 발음 원고의 내용·문단 구분이 일치하는지 확인한다. 영문·변수·숫자는 대본과 화면에 유지하며 발음 원고에만 한글 표기를 둔다. 영상 길이는 임의로 정하지 않는다. 제작 단계에서는 출력 칸·행·열·합산 축의 대응, 누적 초기화, 명시적 구조와 계산 의미의 구분을 확인한다.

- 발화 19구간, 대본·TTS 표기 변환 일치 확인. 발음 원고는 공백 제외 991자로 1편 1,122자의 88.3%, 어절 수 312개다. 실제 발화 시간은 미확정이다.
