# GPU 08 — Register Pressure와 Occupancy

174초. 화면 전환 시각과 CAPTIONS의 실제 자막을 대본 기준으로 사용합니다. 발화 시간 예측으로 만든 타이밍이 아닙니다.

## 00:00:00.000–00:00:06.000 / 6초 / recap

앞에서는 Tile과 Thread당 출력이 커지면
Register 사용량도 늘어날 수 있다고 했습니다.
이번에는 그 영향을 보겠습니다.

## 00:00:06.000–00:00:12.000 / 6초 / register

Register는 각 Thread가 계산에 필요한 값을
보관하는 가까운 저장 공간입니다.

## 00:00:12.000–00:00:18.000 / 6초 / one_output

Thread 하나가 출력 하나를 계산한다면, 그 중간 합을
Register에 둘 수 있습니다.

## 00:00:18.000–00:00:24.000 / 6초 / many_outputs

여러 출력을 동시에 계산하면, 여러 중간 합을 보관해야 할
수 있습니다. 필요한 Register도 늘어날 수
있습니다.

## 00:00:24.000–00:00:30.000 / 6초 / pressure

이처럼 한 Thread가 많은 Register를 필요로
하는 상황을 Register Pressure가 높다고
표현합니다.

## 00:00:30.000–00:00:36.000 / 6초 / sm

하지만 Register는 무한하지 않습니다. Block들이
실행되는 SM 안에는 Register의 총량이 정해져
있습니다.

## 00:00:36.000–00:00:42.000 / 6초 / budget

여기서는 최대 Warp 64개와 Register
65536개를 가진 SM을 가정하겠습니다. Block당
Thread는 256개입니다.

## 00:00:42.000–00:00:48.000 / 6초 / sixteen

Thread마다 Register 16개를 쓰면, 이 단순
모델에서는 Warp 64개를 유지할 수 있습니다.

## 00:00:48.000–00:00:54.000 / 6초 / sixtyfour

Thread마다 64개를 쓰면 같은 작업 수에 네 배의
Register가 필요합니다. Register 용량이 먼저
한계에 닿습니다.

## 00:00:54.000–00:01:00.000 / 6초 / resident

이 조건에서는 상주 Block이 여덟 개에서 네 개로,
Warp는 64개에서 32개로 줄어듭니다.

## 00:01:00.000–00:01:06.000 / 6초 / occupancy

Occupancy는 SM의 최대 상주 Warp 수에 대한
현재 상주 Warp 수의 비율입니다. 모두가 같은 순간
명령을 실행한다는 뜻은 아닙니다.

## 00:01:06.000–00:01:12.000 / 6초 / half

최대 Warp 64개 중 32개가 올라가 있다면
Occupancy는 50퍼센트입니다.

## 00:01:12.000–00:01:18.000 / 6초 / full

64개가 모두 올라가 있다면 100퍼센트입니다. 최대
Warp 수는 GPU 종류에 따라 달라집니다.

## 00:01:18.000–00:01:24.000 / 6초 / question

그렇다면 Occupancy가 높으면 항상 빠를까요?
그렇지는 않습니다. 먼저 왜 중요한지 보겠습니다.

## 00:01:24.000–00:01:30.000 / 6초 / waiting

어떤 Warp가 Global Memory의 데이터를
기다리고 있습니다. 이 Warp는 아직 다음 계산을 진행할
수 없습니다.

## 00:01:30.000–00:01:36.000 / 6초 / ready

그동안 다른 준비된 Warp의 명령을 실행할 수 있다면,
계산 장치를 계속 사용할 수 있습니다.

## 00:01:36.000–00:01:42.000 / 6초 / hiding

이렇게 준비된 Warp들의 명령을 번갈아 실행해 대기
시간을 숨기는 것을 Latency Hiding이라고
합니다.

## 00:01:42.000–00:01:48.000 / 6초 / few

상주 Warp가 너무 적으면, 기다리는 작업을 대신할
준비된 Warp가 부족해질 수 있습니다.

## 00:01:48.000–00:01:54.000 / 6초 / not_max

하지만 Occupancy 100퍼센트가 최고 성능을
보장하지는 않습니다. Thread 안의 계산 효율도
중요합니다.

## 00:01:54.000–00:02:00.000 / 6초 / more_work

Register를 더 써서 필요한 값을 유지하면, 메모리
접근을 줄이거나 여러 계산을 효율적으로 이어갈 수
있습니다.

## 00:02:00.000–00:02:06.000 / 6초 / benefit

이런 이득이 크다면 Occupancy가 조금 낮아져도 전체
실행 시간은 더 짧아질 수 있습니다.

## 00:02:06.000–00:02:12.000 / 6초 / cap

반대로 Occupancy를 높이려고 Register를
지나치게 제한하면, 필요한 값을 모두 보관하지 못할 수도
있습니다.

## 00:02:12.000–00:02:18.000 / 6초 / spill

일부 값이 메모리로 밀려나 저장되는 것을 Register
Spill이라고 합니다. 보통 Local Memory를
사용합니다.

## 00:02:18.000–00:02:24.000 / 6초 / reload

밀려난 값이 다시 필요하면 메모리에서 읽어야 합니다. 이런
추가 읽기와 쓰기가 실행 비용을 늘릴 수 있습니다.

## 00:02:24.000–00:02:30.000 / 6초 / balance

따라서 Register를 적게 쓰는 것도, 많이 쓰는 것도
무조건 좋지는 않습니다. 재사용과 상주 작업 사이의 균형이
필요합니다.

## 00:02:30.000–00:02:36.000 / 6초 / tile

Tile 설계에서 Thread당 출력을 늘리면 중간 합도
늘어납니다. Register Pressure와
Occupancy가 함께 달라질 수 있습니다.

## 00:02:36.000–00:02:42.000 / 6초 / chain

Tile 크기, Thread당 계산량, Register
사용량, Occupancy는 서로 연결된 선택입니다.

## 00:02:42.000–00:02:48.000 / 6초 / measure

목표는 Occupancy 숫자의 최대화가 아닙니다. 충분한
Register와 준비된 Warp를 확보하고 실제 실행
시간을 확인해야 합니다.

## 00:02:48.000–00:02:54.000 / 6초 / ending

한 Thread에 얼마나 많은 일을 맡길지, 대신 얼마나
많은 Warp를 함께 유지할지. GPU 성능은 이 균형에
달려 있습니다.
